Cards & Rules

Before a game can be played, it needs an unambiguous definition of what a card is and what moves are legal. This module builds frontend/lib/engine/card.dart and frontend/lib/engine/rules.dart — the two files everything else in the project is built on top of.

Where this fits

Prerequisite terms

enum, extension, switch expression, const constructor. See the Glossary for the full list.

engine/card.dart

frontend/lib/engine/card.dart
Purpose

Every other file in the project needs to talk about "the ace of spades" or "a card this seat may legally play" — but there has to be one canonical, comparable, serializable representation of a card first, or the engine, the bot, the UI, and the network protocol would each invent their own and drift apart. This file is that single representation. Without it, there is no shared vocabulary between "what the rules allow" (rules.dart), "what the state machine tracks" (game.dart), and "what crosses the wire" (the id string documented in backend/PROTOCOL.md: "AS", "10H").

Decision

A plain immutable class with hand-rolled ==/hashCode, instead of a code-generation package like freezed or equatable. The project-wide convention (see docs/CONCEPT_MAP.md) is "hand-written JSON, deliberately no codegen" — no build_runner step means anyone can clone the repo and run it immediately, with nothing to regenerate after a model changes. The cost: every model class carries a few lines of boilerplate (operator ==, hashCode, toJson) that a codegen tool would otherwise write for you, and it's on the author to keep them in sync if a field is added.

A human-readable wire id ("AS", "10H") instead of a compact numeric encoding (e.g. rank * 4 + suit.index). The string is self-describing in a network capture or a server log — you can read backend/PROTOCOL.md's example JSON and know exactly which card is meant. The cost is a few extra bytes per card and a string-parse instead of an array index on every decode; at 52 cards a hand this is not a real performance concern.

Explanation

Suit and its metadata (lines 4–33):

enum Suit { spades, hearts, diamonds, clubs }

extension SuitInfo on Suit {
  String get code => switch (this) {
    Suit.spades => 'S',
    Suit.hearts => 'H',
    Suit.diamonds => 'D',
    Suit.clubs => 'C',
  };
  ...
  bool get isTrump => this == trumpSuit;
}

const Suit trumpSuit = Suit.spades;

Suit itself is just four bare names. All of its behaviour — the one-letter wire code, the display symbol (♠♥♦♣), whether it's red, whether it's the permanent trump suit — is attached afterward via extension SuitInfo on Suit. This keeps the enum itself trivial to pattern-match on everywhere, while still giving it rich, discoverable .code/.symbol/.isTrump getters at every call site, as if they were built in. trumpSuit is a single const — Call Break always plays spades as trump, so this is the one place that fact lives.

Ranks are plain integers, not another enum (lines 38–56):

const int minRank = 2;
const int maxRank = 14;

String rankLabel(int value) => switch (value) {
  14 => 'A',
  13 => 'K',
  12 => 'Q',
  11 => 'J',
  _ => '$value',
};

Rank runs 2–14 with the ace high (14, not 1) — that single choice is what makes every comparison in rules.dart a plain integer >/<, with no special-casing "unless it's an ace." rankLabel/rankFromLabel are the only two places that translate between that integer and the human label ("A", "K", "10") — including on the wire, since rankLabel feeds PlayingCard.id below.

Try it yourself — write PlayingCard before looking

Write an immutable PlayingCard class with a final rank (int) and suit (Suit), a const constructor, value equality (two cards with the same rank+suit are ==), a label getter using rankLabel, and an id getter that concatenates label and suit.code (e.g. "AS"). Add a factory PlayingCard.fromId(String id) that reverses it — careful, the rank label can be one character ("A") or two ("10"), but the suit code is always the last character.

Show solution 
class PlayingCard {
  const PlayingCard(this.rank, this.suit);

  final int rank;
  final Suit suit;

  bool get isTrump => suit == trumpSuit;

  String get label => rankLabel(rank);

  /// Stable wire id, e.g. `AS`, `10H`. Used by the network protocol.
  String get id => '$label${suit.code}';

  factory PlayingCard.fromId(String id) {
    final suit = suitFromCode(id.substring(id.length - 1));
    return PlayingCard(rankFromLabel(id.substring(0, id.length - 1)), suit);
  }

  @override
  bool operator ==(Object other) =>
      other is PlayingCard && other.rank == rank && other.suit == suit;

  @override
  int get hashCode => Object.hash(rank, suit);

  @override
  String toString() => id;
}

The trick in fromId: slice off the last character as the suit code first (id.substring(id.length - 1)), then whatever's left is the rank label, one or two characters either way. Slicing from the front would break on "10H".

Notice what == and hashCode are doing: two PlayingCard instances built separately (one in a hand, one decoded from JSON) are equal exactly when their rank and suit match — not when they're the same object in memory. This is what lets hand.contains(card) and Set<PlayingCard> work the way you'd expect from a value type. Forget to override hashCode to match == and a PlayingCard silently stops working correctly inside any Set or as a Map key — Dart's default is identity-based.

Dealing and display order (lines 87–110):

List<PlayingCard> fullDeck() => [
  for (final suit in Suit.values)
    for (var rank = minRank; rank <= maxRank; rank++) PlayingCard(rank, suit),
];

List<List<PlayingCard>> dealHands(Random random) {
  final deck = fullDeck()..shuffle(random);
  return [
    for (var seat = 0; seat < 4; seat++)
      sortForDisplay(deck.sublist(seat * 13, seat * 13 + 13)),
  ];
}

dealHands takes a Random instead of creating its own. That's a small but important seam: whoever calls it (the engine, in module 2) controls the seed, which is what makes a whole game replayable — deal the same seed twice and you get the same four hands. sortForDisplay (trumps first, then each suit high-to-low) is purely cosmetic — it's what a human sees in their hand fan, and has no bearing on legality.

Improvement note
No known weakness in this file — it's small, has no I/O, and every branch is a one-line pure function that's trivially unit-testable (frontend/test/engine_test.dart exercises it). Nothing to flag.

engine/rules.dart

frontend/lib/engine/rules.dart
Purpose

This file answers three questions the rest of the app can't function without: which cards may I legally play right now, who wins a finished trick, and what is a hand worth once bidding and tricks-won are known. If this logic lived scattered inside the UI or the state machine, "what's a legal move" could end up defined differently in two places — exactly the class of bug the project's own README calls out as the one thing the Go port cannot afford to get wrong later.

Decision

Free top-level functions taking plain data (List<PlayingCard>, List<TrickPlay>) instead of methods on a Rules class or directly on the game object. A free function with no hidden state is the easiest possible thing to unit test (call it, assert the output) and — critically for this project — the easiest thing to port line-for-line to Go, which is exactly what backend/internal/engine/rules.go does in module 12. The cost: every call site has to pass the hand and trick in explicitly rather than the function reaching into self/this for them, which reads slightly more verbose at each call site.

estimateTricks is a hand-tuned weighted heuristic, not a simulation-based estimator (e.g. Monte-Carlo dealing out thousands of plausible opponent hands and averaging trick counts). The heuristic is deterministic and runs in microseconds, which matters because it's called on every bot bid and live, on every keystroke, to show the human a bid suggestion. The cost: it's an approximation tuned by feel, not provably optimal — a hand shape the weights don't anticipate could get a noticeably wrong suggestion, and there's no way to know without playing thousands of hands past it.

Explanation

Legal moves — the actual rules of Call Break (lines 66–100):

List<PlayingCard> legalMoves(List<PlayingCard> hand, List<TrickPlay> trick) {
  if (trick.isEmpty) return [...hand];

  final led = trick.first.card.suit;
  final inSuit = hand.ofSuit(led);

  if (inSuit.isNotEmpty) {
    final bestLed = trick
        .where((p) => p.card.suit == led)
        .map((p) => p.card.rank)
        .reduce((a, b) => a > b ? a : b);
    final higher = inSuit.where((c) => c.rank > bestLed).toList();
    return higher.isNotEmpty ? higher : inSuit;
  }
  ...

Read this as three cases, in order: (1) you're leading — anything goes. (2) You hold the led suit — you must follow it, and specifically with a card that beats the best one already played, if you have one ("heading" — the comment above the function calls this out explicitly). Only if you can't beat it are you allowed to underplay in that suit. (3) You're void in the led suit — you must trump if you hold any, and must overtrump an already-trumped trick if you can beat the best trump played so far. Only genuinely stuck (no trumps, or can't beat the trump on the table) can you discard anything.

Try it yourself — write trickWinner before looking

Given a completed 4-play trick (List<TrickPlay>), write a function that returns the winning seat. Rule: the highest trump wins if any trump was played; otherwise the highest card of the led suit wins (a card of a different, non-trump suit can never win).

Show solution 
int trickWinner(List<TrickPlay> trick) {
  final led = trick.first.card.suit;
  final trumps = trick.where((p) => p.card.isTrump).toList();
  final contenders = trumps.isNotEmpty
      ? trumps
      : trick.where((p) => p.card.suit == led).toList();
  return contenders.reduce((a, b) => b.card.rank > a.card.rank ? b : a).seat;
}

The whole function is "narrow the field to whoever could possibly win (trumps if any were played, else the led suit), then reduce to the highest rank in that field." wouldWin just below it reuses this exact function by hypothetically appending the candidate card with a sentinel seat (-1) and checking whether -1 comes back as the winner — rather than duplicating the winner logic.

Scoring (lines 121–126):

double scoreHand(int bid, int tricksWon) {
  final raw = tricksWon >= bid ? bid + (tricksWon - bid) * 0.1 : -bid.toDouble();
  return (raw * 10).round() / 10;
}

Make your bid exactly and you score the bid; every trick beyond it is worth 0.1 more (an "overtrick"); fall short by even one trick and you lose the whole bid as a negative score, regardless of how close you got. The (raw * 10).round() / 10 dance is rounding to one decimal place without floating-point drift accumulating over a multi-hand game — a real, if small, correctness concern given totals in game.dart keeps adding these up hand after hand.

Improvement note
No known weakness tied to this exact file — it's pure, deterministic, and has a dedicated test file (frontend/test/engine_test.dart) plus a byte-for-byte Go port (module 12) that's tested case-for-case against it, which is about as much safety net as a rules engine can reasonably have.

Checkpoint

Why does PlayingCard hand-roll ==/hashCode instead of using a codegen package, and what does that decision cost the project long-term?
The project's convention is zero build steps — no build_runner means the repo runs immediately after git clone with nothing to regenerate. The cost is manual boilerplate that must be kept in sync by hand: add a field to PlayingCard and forget to touch operator ==/hashCode, and equality silently goes stale with no compiler error to catch it.
Why are legalMoves and trickWinner free functions that take a hand/trick as arguments, rather than methods on the game object?
Two reasons that both matter here: they're trivially unit-testable in isolation (no game object to construct first), and — the bigger one for this specific project — they need to be ported to Go nearly line-for-line in module 12. A pure function with explicit inputs and no hidden state is the easiest possible shape to translate faithfully between two languages.
Why does rank run 2–14 (ace high) instead of the more common 1–13?
So every rank comparison in the rules is a plain integer >, with the ace naturally outranking everything with no special-case branch for "unless it's an ace." rankLabel/rankFromLabel are the only two places that ever need to know 14 displays as "A".
estimateTricks is a heuristic, not a simulation. What real failure mode does that trade-off open up, and where would you feel it?
It's a set of hand-tuned weights, not a provably optimal estimate — a hand shape the weights don't model well (e.g. an unusual void distribution) can get a bid suggestion that's off, and because it's deterministic, that same hand shape will be wrong the same way every time rather than averaging out. You'd feel it as the on-screen bid suggestion (and bot bidding) occasionally looking overconfident or underconfident on specific hands, with no way to detect it short of manual review.
