Persistent App State

The game is playable, but everything about it resets on every restart — theme, player name, even who this player is. This module builds state/app_settings.dart, state/identity_store.dart, and state/active_game_binding.dart — the layer that survives a restart.

state/app_settings.dart

frontend/lib/state/app_settings.dart
Purpose

Dozens of widgets need to read (and a few need to change) the same handful of preferences — theme, card style, difficulty, animation speed. Without one shared, observable store, every screen would need its own copy, and a change on the settings sheet would never be seen by the table screen already on the navigation stack.

Decision

Two different mutation philosophies live on the same class, on purpose. Display preferences (theme, animationSpeed, ...) are plain in-memory fields that call notifyListeners() on every change — cheap to lose on reinstall, so no persistence effort is spent on them here. Anything that identifies the player is instead delegated to identity (an IdentityStore, below), which is backed by disk — per the file's own doc comment, "a theme is cheap to pick again after a reinstall, an account is not." The cost of splitting it this way: two different code paths for "change a setting" exist in one class, and a future field has to be consciously assigned to the right one.

Explanation
class AppSettings extends ChangeNotifier {
  AppSettings({IdentityStore? identity})
    : _identity = identity ?? IdentityStore.inMemory();
  ...
  set theme(TableTheme value) {
    if (_theme == value) return;
    _theme = value;
    notifyListeners();
  }
  ...
  String? get guestToken => _identity.guestToken;

  set guestToken(String? value) {
    if (value == null || value.isEmpty || value == _identity.guestToken) return;
    unawaited(_identity.saveGuestToken(value));
    // Deliberately no notifyListeners: this is a credential, not UI state, and
    // rebuilding the tree on every join would be pure noise.
  }
}

Compare the two setters directly: theme mutates a local field and notifies — a normal ChangeNotifier setter, with the early-return-if-unchanged guard repeated on every setter in this file (a small but consistent discipline: never rebuild the tree for a no-op write). guestToken instead writes straight through to disk via identity and explicitly does not call notifyListeners() — the comment states why directly: nothing on screen needs to rebuild because a credential changed behind the scenes.

/// Debug-only override for the game server URL. Empty means "no override
/// set", in which case [effectiveServerUrl] falls back to
/// [kDefaultServerUrl]. This is not a user-facing setting in release
/// builds — see the developer section in the settings sheet, which is
/// tree-shaken out of release builds via `kDebugMode`.
String get serverUrl => _serverUrl;

String get effectiveServerUrl =>
    (kDebugMode && _serverUrl.trim().isNotEmpty) ? _serverUrl : kDefaultServerUrl;

serverUrl is the raw override a developer typed into a debug-only settings field; effectiveServerUrl is what RemoteSession (module 9) actually connects to. The split exists so release builds can never accidentally point at a stray debug URL — the override is only honoured when kDebugMode is true, a compile-time constant that gets tree-shaken out of release builds entirely, per the doc comment.

Improvement note
kDefaultServerUrl (line 15) is hard-coded to 'ws://192.168.1.133:8080/ws' — a specific developer's LAN IP address baked directly into the shipped source, not a placeholder like localhost. Anyone who builds this project without also setting a debug override will have their app try to reach a machine on someone else's home network. A safer default (localhost, or a build-time --dart-define) would fail obviously instead of silently pointing at the wrong host.

state/identity_store.dart

frontend/lib/state/identity_store.dart
Purpose

The server needs to recognise the same device across restarts — to resolve a POST /v1/auth/device call to the same account, and to let a player reclaim a seat after the app was killed mid-game (module 16's docs/PERSISTENCE.md covers the server side). This file is the one place that identity lives on disk.

Decision

A hand-rolled UUID v4 generator instead of the uuid pub package — the file's own comment states the reasoning plainly: "this is the only thing the app would use one for, and the whole specification is the two bit-twiddles below." Pulling in a dependency for a fifteen-line algorithm the project needs exactly once is a real cost/benefit call, made explicitly rather than by default.

Random.secure(), not the plain Random(), generates the device id — again spelled out directly: "two ids that collide would silently merge two games on the server... Random() is seeded from the clock, and phones start games at round numbers of milliseconds far more often than a uniform distribution would suggest." A cryptographically secure generator costs a little more CPU per call (called exactly once per install) in exchange for closing a real, if narrow, collision risk that a clock-seeded generator has.

Every decode path swallows its own errors and returns null instead of throwing (cachedUser, activeGame, pendingAbandoned) — the comment on cachedUser: "A profile written by an older build that no longer decodes is not worth a crash — the next /v1/me replaces it." This mirrors the backend's own persistence philosophy (module 16): storage failures degrade gracefully rather than crashing the thing they support. The cost is the same one graceful degradation always has — a real bug in the decode path looks identical to "an old build's data," silently, with nothing surfaced to notice the difference.

static Future<IdentityStore> open() async {

    if (deviceId == null || deviceId.isEmpty) {

      await prefs.setString(_kDeviceId, deviceId);

The device id is minted exactly once — read it if it's already there, mint and persist a fresh one if not, and never touch it again afterward (the class doc comment: "written exactly once, on first launch, and only ever read afterwards"). If anything in that whole block throws — the platform denies storage, the plugin isn't available — the fallback isn't a crash, it's IdentityStore.inMemory(): the same public API, but nothing behind it actually persists. Per its own doc comment: "Losing history is bad; refusing to launch the game over it would be worse."

Why ActiveGame stores mode as a string (lines 249–251):

/// [mode] is stored as [GameMode.name] rather than the enum itself so this

/// reconstructs a session converts it back with `GameMode.values.byName`.

This is a dependency-direction decision, not a data-format one: the state layer deliberately does not import the net layer, even though the enum itself lives there. Storing the enum's plain string name instead keeps that boundary intact — the cost is one extra GameMode.values.byName(...) conversion at the one call site that reconstructs a session from this record.

Improvement note
No weakness beyond what's already flagged in AppSettings above — this file is a careful, well-reasoned example of "storage is best-effort, never load-bearing for whether the app runs at all."

state/active_game_binding.dart

frontend/lib/state/active_game_binding.dart
Purpose

A player killed by the OS mid-game (not a graceful app close — a real kill, task-switched away and never brought back) gets no chance to tell the server goodbye. Without a persisted record of "I was at this table, here's my resume token," the app has no way to even offer reclaiming that seat on next launch — it would just look like a fresh install to the player.

Decision

A standalone function that wires a RemoteSession (module 9) to AppSettings/IdentityStore from outside both, rather than RemoteSession persisting its own resume state internally. This keeps RemoteSession itself unaware that IdentityStore exists at all — the net layer doesn't import the state layer, mirroring the reverse boundary ActiveGame just kept in the other direction. The cost: this wiring only happens where something remembers to call it — module 6 showed the one real call site, wireActiveGamePersistence(settings, session) in home_screen.dart:881, right after constructing a RemoteSession.

Explanation
void wireActiveGamePersistence(AppSettings settings, RemoteSession session) {
  String? persistedToken;
  session.addListener(() {
    settings.guestToken = session.guestToken;

    final view = session.view;
    final terminal =
        session.status == SessionStatus.closed ||
        session.status == SessionStatus.error ||
        view?.phase == GamePhase.gameOver;
    if (terminal) {
      final stored = settings.identity.activeGame;
      if (stored != null &&
          stored.serverUrl == session.serverUrl &&
          stored.roomCode == session.roomCode) {
        unawaited(settings.identity.clearActiveGame());
      }
      return;
    }

    final token = session.resumeToken;
    if (token != null && token != persistedToken) {
      persistedToken = token;
      unawaited(settings.identity.saveActiveGame(ActiveGame(...)));
    }
  });
}

This is a listener attached once, at session creation, that watches every future change and does two things: keeps guestToken current (so the player's identity survives across future tables), and keeps the "table I could reclaim" record current — writing a fresh one whenever a new resumeToken is issued (join, or every reconnect), and clearing it the moment the session reaches a genuinely final state. The stored.serverUrl == session.serverUrl && stored.roomCode == session.roomCode check before clearing matters: it stops this session from erasing a record that belongs to some other table, in case more than one session has existed in the process's lifetime.

Improvement note
Because this is opt-in wiring rather than something RemoteSession does automatically in its own constructor, any future code path that builds a RemoteSession without also calling wireActiveGamePersistence would silently lose the "reclaim my seat after a kill" feature for that path — with nothing in the type system to catch the omission, since RemoteSession works perfectly well without it, just without persistence. A safer version would take this wiring inside RemoteSession's own constructor (accepting an optional IdentityStore), making it opt-out instead of opt-in.

Checkpoint

Why does AppSettings.guestToken's setter deliberately skip notifyListeners() while every other setter calls it?
Because a credential changing isn't something any widget needs to rebuild in response to — it's persisted state, not UI state. Calling notifyListeners() there would rebuild the whole SettingsScope subtree for no visible benefit, on every join.
Why does IdentityStore use Random.secure() instead of the default Random() for the device id, when the id doesn't need to be unguessable, only unique?
Because the default Random() is seeded from the system clock, and phones tend to launch an app for the first time at round numbers of milliseconds — a plain clock-seeded generator has a real, if narrow, chance of producing colliding ids across different devices, which would silently merge two players' games server-side. Random.secure() avoids that regardless of when the device happens to boot.
Why does ActiveGame store GameMode as a plain string instead of the enum value itself?
So identity_store.dart (the state layer) never has to import net/session.dart (the net layer) just to reference the enum type — keeping that dependency direction one-way. The cost is a GameMode.values.byName(...) conversion at the point the record is later reconstructed into a real session.
wireActiveGamePersistence lives outside RemoteSession entirely, as a function the caller must remember to invoke. What does that buy, and what's the real risk?
It buys a clean boundary: RemoteSession never needs to know IdentityStore exists. The real risk is that this wiring is opt-in — any future code path that constructs a RemoteSession without also calling this function will silently work fine except for losing seat-reclaim-after-a-kill, with no compiler error or test failure pointing at the gap.
