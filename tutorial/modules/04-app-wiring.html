App Wiring & Design Tokens

The engine (Part I) can run a full game in memory, but nothing shows it on screen yet. This module wires up the actual Flutter application — lib/main.dart — and the two files that keep every widget built after this point from hard-coding a colour or a pixel size: design/tokens.dart and design/metrics.dart.

Where this fits

lib/main.dart

frontend/lib/main.dart
Purpose

Every Flutter app needs exactly one entry point that starts the widget tree. This file is also where the small set of things that must exist before a single pixel is drawn get built once: on-disk settings, the device identity, and the queue of any offline games that still need uploading from a previous run.

Decision

Build AppSettings once in main() and hand it down through a hand-rolled InheritedWidget (SettingsScope, module 7), instead of a state-management package like Provider or Riverpod. The whole app has one real piece of app-wide mutable state (settings), so a stdlib InheritedWidget is enough — no extra package for the team to learn, no code generation. The cost: if this app grew several independent pieces of app-wide state, each would need its own hand-rolled scope, where a package gives you that pattern for free and composes multiple stores more easily.

Explanation
Future<void> main() async {
  WidgetsFlutterBinding.ensureInitialized();
  SystemChrome.setEnabledSystemUIMode(SystemUiMode.immersiveSticky);
  SystemChrome.setPreferredOrientations([...]);

  // Storage is read once, here, so every widget below can treat the device id
  // and the session token as plain synchronous values.
  final settings = AppSettings(identity: await IdentityStore.open());

  // Offline games queued by the last run go out now. Deliberately not awaited:
  // the home screen must not wait on a network call to appear.
  GameUploader.install(await GameUploader.open(client: ApiClient.forSettings(settings)));

  runApp(CallBreakApp(settings: settings));
}

WidgetsFlutterBinding.ensureInitialized() exists because the two calls right after it (SystemChrome...) talk to native platform code before runApp has set that channel up itself — a required one-liner any time you touch a platform API before the app is running.

The two comments in the code above are doing real explanatory work, verbatim from the file — read them closely: identity: await IdentityStore.open() is awaited deliberately, so every widget built afterward can assume the device id is already loaded and read it synchronously, with no "is it ready yet" check anywhere else in the app. GameUploader.install(...), by contrast, is not awaited — its own network upload must not delay the first frame the player sees. Same file, two adjacent lines, opposite async strategy, each for a stated reason.

SettingsScope wraps outside MaterialApp, so settings are reachable from absolutely anywhere in the tree, including code that runs before any screen (route transitions, error builders). It's built in module 7, alongside AppSettings itself.

Improvement note
main() (lines 12–29) has no top-level error handling around the two awaited calls — if IdentityStore.open() or building the ApiClient/GameUploader throws (a corrupt on-disk settings file, for instance), runApp is never reached and the user sees a blank screen with no crash report and no fallback UI. A runZonedGuarded wrapper with a minimal error screen, or a try/catch that falls back to fresh in-memory settings, would turn a silent blank-screen failure into a recoverable one.

design/tokens.dart

frontend/lib/design/tokens.dart
Purpose

A card table app has dozens of widgets that all need to agree on the same gold, the same felt green, the same type ramp. Without one shared source, colours drift widget-by-widget over time as different people (or different sessions with an AI) touch different screens. The file's own doc comment states the rule directly: "Nothing in the UI should hard-code a colour or a type ramp — it all comes from here."

Decision

Table appearance and card-face appearance are two independent enums (TableTheme and CardStyle), each resolved through its own static lookup class, rather than one combined "theme" enum (e.g. Theme.emeraldClassic). Two independent axes let a player pick "Sapphire table, Midnight cards" — 4 × 6 = 24 combinations from 10 declared values instead of needing 24 declared combinations. The cost is exactly what you'd guess: nothing enforces that a given CardStyle looks good against every TableTheme — that's left to whoever picks the literal colour values to get right by eye, which the code above (lines 170–174, 199–202) shows real thought went into, but the type system can't verify it.

Explanation
enum TableTheme { emerald, sapphire, amethyst, crimson }

class ThemePalette {
  const ThemePalette({required this.label, required this.background, ...});
  ...
  static const _palettes = <TableTheme, ThemePalette>{
    TableTheme.emerald: ThemePalette(
      label: 'Emerald',
      background: [Color(0xFF061A14), Color(0xFF0D3D2C), Color(0xFF145C42)],
      ...
    ),
    ...
  };

  static ThemePalette of(TableTheme theme) => _palettes[theme]!;
}

Every theme's actual colour values live in one const map, keyed by the enum. Any widget that needs "the felt colour for the current theme" calls ThemePalette.of(theme).felt — never a raw Color(0x...) literal. This is the mechanism, repeated for CardFacePalette, that makes the file's "nothing hard-codes a colour" rule actually enforceable in practice rather than just a comment nobody follows.

Read the two comments above the CardStyle.crimson and the four saturated-suit entries (lines 170–174, 199–202) verbatim — they explain a real design constraint, not decoration: a saturated red card face would make the normal red-suit ink (also red) disappear into it, so Crimson's ink colours are inverted specifically to stay legible. That's the kind of non-obvious reasoning a plain colour value can't carry on its own — which is the actual argument for keeping it in one commented file instead of scattered literals.

design/metrics.dart

Sitting next to tokens.dart: colour comes from tokens, size comes from Metrics. Same principle, different axis.

Decision

One scalar scale factor, derived from the device's shortest side and applied everywhere via Metrics.s(designPx), instead of per-breakpoint layouts (distinct phone/tablet layout code, or a package like flutter_screenutil). One number keeps every widget's proportions consistent relative to each other automatically — design at 390pt, multiply by scale, done. The cost, from the file's own comment: it's "a ceiling so a tablet does not end up with comically large cards," meaning the same scalar can't independently decide that, say, the bid panel should grow slower than the card fan — every design-pixel value scales by the exact same factor.

Explanation
static double _scaleFor(Size size) {
  final shortSide = size.shortestSide;
  return (shortSide / designShortSide).clamp(_minScale, _maxScale);
}

designShortSide is 390.0 — the design's own reference device width. Any real device's shortest side (portrait width, or landscape height) divided by that gives a ratio, clamped between 0.78 and 1.4 so an extreme phone or tablet doesn't blow layout proportions out. Every widget then calls Metrics.s(24) instead of a hard-coded 24, and gets a device-appropriate pixel value back.

The more subtle piece is where that size comes from — read the doc comment on MetricsScope verbatim, because the reasoning is a real, specific Flutter gotcha: 

/// Sized from the media query rather than from the incoming layout
/// constraints on purpose: a `Scaffold` shrinks its body on every frame of the
/// on-screen keyboard's open/close animation (`Scaffold.resizeToAvoidBottomInset`),
/// but `MediaQuery.sizeOf` ignores that inset and keeps reporting the settled
/// screen. Keying the scale and the portrait/landscape split off the stable
/// value means `Metrics.updateShouldNotify` returns false while the keyboard
/// animates, so the whole subtree does not rebuild — and re-lay out — at 60fps
/// just to adjust to a shrinking viewport.
class MetricsScope extends StatelessWidget { ... }

Without this, opening a text field's keyboard would trigger a full-tree relayout every animation frame while the keyboard slides up — a real, previously-hit performance bug this comment is documenting the fix for, not a hypothetical one.

Improvement note
No known weakness — both files are pure, static data plus one small pure function (_scaleFor), with the reasoning behind every non-obvious choice already captured in the file's own comments.

Checkpoint

Why is GameUploader.install(...) not awaited in main(), while IdentityStore.open() is?
The device identity must be ready before any widget builds, so every screen can read it synchronously — hence it's awaited. The upload queue's network call has no such requirement, and awaiting it would delay the very first frame the player sees for no benefit; the file's own comment says exactly this.
TableTheme and CardStyle are separate enums instead of one combined theme. What does that buy, and what does it not guarantee?
It buys every table-colour × card-colour combination (24 from 10 declared values) without declaring each combination by hand. It does not guarantee every combination looks good together — that's down to whoever picks the literal colours, verified by eye, not by the type system.
Why does Metrics compute its scale from MediaQuery.sizeOf instead of the widget's own incoming layout constraints?
Layout constraints shrink every frame while the on-screen keyboard animates open or closed (via resizeToAvoidBottomInset), which would trigger a full relayout of the metrics-dependent subtree at 60fps for no reason. MediaQuery.sizeOf reports the settled screen size and ignores that transient inset, so the scale — and anything depending on it — stays stable through the animation.
