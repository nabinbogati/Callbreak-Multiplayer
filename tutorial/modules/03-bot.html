Bot Opponent

The engine can now run a full game, but only if all four seats hand it valid bids and card plays. frontend/lib/bots/bot.dart is what stands in for the three seats a solo player doesn't fill — and, later, for any seat a networked table needs to cover.

Purpose

Without an opponent, "vs bots" isn't a mode — it's an empty table. This class is the entire opponent: it decides what to bid given a hand, and which legal card to play given the current trick. Nothing about it depends on Flutter, the UI, or the network; it's handed plain data (a hand, a trick, unseen cards) and returns a decision, which is what lets the exact same class run inside a purely offline solo game.

Decision

A hand-tuned heuristic (count controlled tricks, then play to hit that number) instead of a search algorithm like minimax or Monte Carlo tree search over the hidden information. A trick-taking game with hidden hands is a genuinely hard search problem — modelling what three unseen hands might contain gets expensive fast. The heuristic runs in microseconds with no real computational cost, at the price of playing suboptimally in situations a deeper search would handle correctly (e.g. inferring a specific opponent's void suit from their earlier discards, which this bot doesn't track at all — it only tracks which cards have been played, in _unseenCards, not who played them).

One class with a difficulty knob (noise + blunder rate) instead of three separate bot implementations. All three difficulties share the exact same decision logic; only _noise (how much random jitter is added to the bid estimate) and _blunderRate (chance of playing a uniformly random legal card instead of the computed one) differ. One code path is far less to maintain than three, but it puts a hard ceiling on "hard" mode — turning noise and blunders to zero just plays the heuristic perfectly, it can never play better than the heuristic's ceiling the way a genuinely different, stronger algorithm could.

Explanation

Bidding (lines 21–39):

double get _noise => switch (difficulty) {
  BotDifficulty.easy => 1.4,
  BotDifficulty.normal => 0.5,
  BotDifficulty.hard => 0.0,

int chooseBid(List<PlayingCard> hand) {
  final estimate = estimateTricks(hand);
  final jitter = _noise == 0 ? 0.0 : (_random.nextDouble() * 2 - 1) * _noise;
  return clampBid((estimate + jitter).round());
}

This reuses estimateTricks from module 1's rules.dart — the exact same function that powers the human's on-screen bid suggestion — then adds up to ±_noise tricks of random jitter before rounding and clamping. An easy bot's bids look human-ishly imperfect; a hard bot's bids are the heuristic's best estimate, unmodified.

If there's only one legal card, there's nothing to decide — return it and skip all the analysis below. Otherwise, roll the dice against _blunderRate first (0 on hard, 0.06 normal, 0.25 easy): a "blunder" means picking uniformly at random among the legal cards, deliberately bypassing the strategy entirely — this is what makes easy bots visibly make bad plays sometimes, not just weaker bids.

Leading a trick — the actual strategy (lines 67–93):

PlayingCard _chooseLead(...) {
  final sideMasters = legal.where((c) => !c.isTrump && _isMaster(c, unseen)).toList();
  if (sideMasters.isNotEmpty) return _bestMasterToLead(sideMasters, hand);

  final trumps = legal.where((c) => c.isTrump).toList();
  if (need > 0) {
    if (need >= tricksLeft && trumps.isNotEmpty) return trumps.highest;
    final trumpMasters = trumps.where((c) => _isMaster(c, unseen)).toList();
    if (trumpMasters.isNotEmpty) return trumpMasters.lowest;
    if (trumps.length >= 5) return trumps.highest;
  }
  return _safeDiscard(legal, hand);
}

Read this as priority order, top to bottom: (1) if you hold a side-suit master — a card no unseen card can beat, see _isMaster below — cash it, it's a free trick that costs nothing to take now. (2) Otherwise, if you still need tricks to hit your bid (need > 0) and you're so far behind that you need every remaining trick, throw your best trump. (3) If you have a trump master, play your lowest one — no need to spend the good one when the cheap one already wins. (4) With five or more trumps, lead one anyway, to drain opponents' trumps out so your remaining small ones become winners later. Fail every case and there's nothing useful to do — discard safely instead.

The card-counting primitive everything above depends on (lines 123–135):

List<PlayingCard> _unseenCards({
  required List<PlayingCard> hand,
  required List<PlayingCard> played,
}) {
  final known = {...hand, ...played};
  return fullDeck().where((c) => !known.contains(c)).toList();
}

bool _isMaster(PlayingCard card, List<PlayingCard> unseen) =>
    !unseen.any((c) => c.suit == card.suit && c.rank > card.rank);

"Unseen" means neither in your own hand nor already face-up this hand — i.e. every card that could plausibly still be in one of the other three hands. A card is a "master" exactly when no unseen card of the same suit outranks it — this is the bot's entire model of "what might the opponents have," and it's intentionally simple: it tracks which cards remain, never who is likely holding which.

Improvement note
BotBrain's constructor (bot.dart:15–16) defaults Random? random to Random() — the system's non-deterministic source — if nobody passes one in. Module 5's LocalSession is careful to pass its own seeded generator instead (BotBrain(difficulty: p.difficulty, random: _random), where _random is seeded from the same value the deal itself uses), so in practice a solo game is fully reproducible from its seed. The gap is narrower than it looks from this file alone: it's an implicit contract ("always pass a seeded Random") that this file's own type signature doesn't enforce — a future call site that constructs BotBrain() with no argument would silently break replay determinism with no compiler warning.

Checkpoint

Why does BotBrain use one heuristic with a difficulty knob instead of three separate strategies for easy/normal/hard?
One code path is far less to build and maintain, and it's enough to produce visibly different-feeling opponents by tuning noise and blunder rate. The cost is a hard ceiling: "hard" can only ever play as well as the underlying heuristic — it can't become a fundamentally stronger algorithm just by turning noise to zero.
What does _isMaster actually know about the other three players' hands, and what does it deliberately not know?
It knows exactly which cards have not yet appeared anywhere (not in its own hand, not played face-up) — that's the entire "unseen" set. It has no model of which of the other three seats is more likely to hold any particular unseen card; every unseen card is treated as equally possible to be in any opponent's hand.
Why does chooseCard check legal.length == 1 before running any strategy at all?
Because with exactly one legal card there is no decision to make — running the lead/follow strategy would just be wasted computation that returns the same answer skipping it does immediately.
