Part III — Go backend · Module 14 of 20

WebSocket Edge

Module 13's room actors never touch a raw socket — they only know room.Client, the small interface from module 13's room.go. This module builds the thing that actually implements it: ws/server.go (upgrading HTTP to a socket, routing a join to a table), ws/conn.go (one connection's two goroutines), ws/identity.go (resolving an account without ever blocking a join on the database), and ws/limit.go (the two rate limits that protect the server from a hostile or just-broken client).

Where this fits

ws/server.go

backend/internal/ws/server.go
Purpose

Something has to turn an HTTP request into a live socket, decide whether the first frame it sends is a private-table join or a quickplay request, and route it accordingly. The package comment states its scope precisely: "Nothing here knows the rules of Call Break. Its job is to make sure that by the time a message reaches a room actor it is well-formed, rate-limited, and attributable to a seat."

Decision

A Locator interface, satisfiable by nothing at all. 

type Locator interface {
	Owner(room string) (endpoint string, elsewhere bool)
}

Multi-node deployments need to know which node actually owns a given room code, so a client joining the wrong node can be redirected rather than failing to find their table. Rather than baking that lookup directly into Server, it's an interface — and Server.Locator is allowed to stay nil. A single-node deployment (the default covered in this course) simply never sets it, and every code path that checks it (if s.Locator != nil { ... }) skips straight past. The alternative — a concrete field always pointing at a real registry — would force even a single developer running go run ./cmd/server locally to stand up Redis (module 16) just to accept a connection.

The account lookup for a device id is started before the join finishes, and nothing downstream waits on it. 

lookup := s.resolveAccount(frame.DeviceID, protocol.SanitizeName(frame.Name), c.log)
...
req := room.JoinRequest{ ..., UserID: lookup.peek() }
...
res := table.Join(req)
...
lookup.attach(c, table, res.Seat)

This is the same principle module 11's config comment named for the database broadly — persistence is an enrichment, never a precondition — made concrete at the exact point a player joins. resolveAccount kicks off a goroutine immediately; the actual work of validating the room code, finding or creating the table, and round-tripping through the room actor's message inbox all happens in parallel with it. Whatever the lookup has produced by the time the JoinRequest is actually built (lookup.peek()) rides along; anything still pending is delivered later via lookup.attach, covered in identity.go below. A player never waits on Postgres to sit down at a table.

func (s *Server) checkOrigin(r *http.Request) bool {
	origin := r.Header.Get("Origin")
	if origin == "" { return true }
	for _, allowed := range s.cfg.AllowedOrigins {
		if allowed == "*" || strings.EqualFold(allowed, origin) {
			return true
		}
	}
	return false
}

The comment says it plainly: "The Flutter app sends no Origin header, so native clients always pass; a browser is only allowed when its origin has been configured explicitly." This is the concrete mechanism behind module 11's validate() requiring ALLOWED_ORIGINS in production — without it, any web page could open a socket to the server on a visitor's behalf, since a plain native client (this game's actual target) never triggers this check at all. 

func (s *Server) joinPrivate(c *Conn, frame protocol.ClientFrame, ...) {
	code := frame.Room
	if !room.ValidRoomCode(code) { c.Fail(protocol.ErrBadFrame, ...); return }
	if s.Locator != nil {
		if endpoint, elsewhere := s.Locator.Owner(code); elsewhere {
			c.sendThenClose(protocol.Encode(protocol.NewRedirect(endpoint)))
			return
		}
	}
	var table *room.Room
	var created bool
	if frame.Create {
		table, created, _ = s.hub.GetOrCreate(code, protocol.ModePrivate, ...)
	} else {
		table, ok := s.hub.Get(code)
		if !ok { c.Fail(protocol.ErrRoomNotFound, ...); return }
	}
	...
}

Only a join carrying Create: true (the room's actual creator, per module 11's protocol field) may bring a fresh table into existence — an ordinary join to an unknown code fails outright rather than silently minting an empty room. The comment explains why: "a mistyped or stale code [would otherwise become] a request to build a new empty room ... guests would silently create tables they can never seem to find again."

The room code the client never sees is embedded, signed, inside the resume token itself (auth.Seat, built next module) — the token the player was handed in the original joined frame (protocol.Joined.ResumeToken, module 11). A dropped quickplay player's client still holds that token from before it disconnected, so presenting it on reconnect names the exact table without the player ever having had to know or type a room code — matching module 11's own QuickplayRoom sentinel design, where the join frame's Room field is never a real address for this mode.

Improvement note
clientIP trusts client-supplied headers with no trusted-proxy allowlist. 
func clientIP(r *http.Request) string {
	if v := r.Header.Get("X-Real-IP"); v != "" { return v }
	if v := r.Header.Get("X-Forwarded-For"); v != "" {
		if first, _, ok := strings.Cut(v, ","); ok { return strings.TrimSpace(first) }
		return strings.TrimSpace(v)
	}
	...
}

This is what MaxConnsPerIP (module 11) and the ip limiter (limit.go below) key their entire per-address connection cap on — but the function trusts X-Real-IP and X-Forwarded-For unconditionally, with no check that the request actually arrived through a known, trusted load balancer that would be the one setting them honestly. A client connecting directly to the server's port (bypassing any load balancer entirely, which nothing here prevents) can set X-Forwarded-For to a different fake address on every single connection attempt, and ipLimiter.acquire would treat each one as a brand-new address with its own fresh allowance — the exact connection-exhaustion attack MaxConnsPerIP exists to stop, defeated by the header meant to make the limit more accurate behind a proxy. The identical pattern, with the identical gap, is repeated independently in httpapi/api.go (module 17) — this is a systemic issue affecting both the WebSocket and REST edges, not a one-off. The fix is standard: only trust these headers when the immediate peer address is itself a configured, trusted proxy/load-balancer IP; otherwise fall back to the raw socket address every time.

ws/conn.go

backend/internal/ws/conn.go
Purpose

One player, one Conn, implementing the exact room.Client interface a room actor was built against in module 13 — Send, Fail, Close, PlayerID. Everything about turning bytes on a socket into frames a room understands, and back, lives here.

Decision

Two goroutines per connection, with one strict rule: only the write pump ever calls ws.WriteMessage. The type's own comment: "a read pump that turns frames into room messages, and a write pump that is the only writer to the socket." A single gorilla/websocket connection is not safe for concurrent writes from multiple goroutines — so rather than a mutex around every write call site (several: incoming frames, pings, the close handshake), the design sidesteps the question entirely by having exactly one goroutine ever touch the write side. Everything that wants to send something posts to the buffered send channel instead; the write pump is the only consumer.

Send never blocks — a slow client is dropped, not waited on. 

func (c *Conn) Send(frame []byte) {
	select {
	case <-c.closed: return
	default:
	}
	select {
	case c.send <- frame:
	default:
		obs.SendDrops.Inc()
		c.Close("policy", "send queue overflow")
	}
}

This is the same "never stall the table" rule module 13's Client interface documents at the definition site, implemented here concretely: a full 64-frame queue means this specific socket has fallen far enough behind that catching it up isn't worth blocking a room actor's goroutine (module 13's actor never does anything except post to channels — a blocking Send here would stall the whole table, not just one player). The comment on the interface itself makes the trade-off explicit: the client "reconnects and gets a fresh authoritative view, so nothing is lost but the connection" — the alternative, buffering without limit, risks unbounded memory growth per stuck socket for a value (queued frames for someone who isn't reading them) that's worthless anyway.

finish() queues a nil sentinel through the same channel real frames travel, rather than closing the socket directly. 

func (c *Conn) finish() {
	select {
	case <-c.closed:
	case c.send <- nil:
	default:
		c.Close("policy", "closing")
	}
}

// in writePump:
case frame := <-c.send:
	if frame == nil {
		c.Close("normal", "closing after final frame")
		return
	}
	...

Because the write pump is a single consumer draining the channel in order, a nil sentinel behind a real error frame guarantees the error is actually written to the wire before the socket closes — closing directly from Fail would race the close against the write pump still having that frame queued, and the client could see a bare disconnect with no explanation at all. This is exactly the mechanism the Fail doc comment on Client (module 13) demands: "Implementations must never close before the frame is written."

Explanation
func (c *Conn) readPump() {
	defer c.teardown()
	c.ws.SetReadLimit(protocol.MaxFrameBytes)
	_ = c.ws.SetReadDeadline(time.Now().Add(pongWait))
	c.ws.SetPongHandler(func(string) error {
		return c.ws.SetReadDeadline(time.Now().Add(pongWait))
	})
	limiter := newBucket(c.srv.cfg.MsgRatePerSecond, c.srv.cfg.MsgBurst)
	for {
		_, data, err := c.ws.ReadMessage()
		if err != nil { return }
		_ = c.ws.SetReadDeadline(time.Now().Add(pongWait))
		if c.fatal.Load() { continue }
		if !limiter.allow() {
			c.Fail(protocol.ErrRateLimited, ...)
			continue
		}
		frame, err := protocol.DecodeClient(data)
		if err != nil {
			c.reject(protocol.ErrBadFrame, ...)
			continue
		}
		c.dispatch(frame)
	}
}

Notice the read deadline is refreshed by any traffic, not only pong control frames — the comment: "a client that is playing should never be timed out" — a player actively sending bid and play frames proves liveness just as well as a pong would, so there's no reason to require a separate heartbeat from someone who's obviously still there. DecodeClient (module 11) does the actual validation — this loop's only job is size (SetReadLimit), pace (the token bucket), and shape (decode), before dispatch routes a clean frame to either the join handler or the bound room's Action.

Try it yourself — after Fail sets c.fatal, the read pump keeps looping and reading frames (just discarding them) instead of returning immediately. Why not just exit the loop the moment a fatal error is queued?
Show solution 
// Once a fatal error is on its way out, nothing else this client says
// should reach a table.
if c.fatal.Load() {
	continue
}

Fail only queues the close (through finish's sentinel) — it doesn't synchronously close the socket, because that's the write pump's job, and it has to happen only after the error frame is actually written. Until the write pump gets to that sentinel and calls Close, the socket is still technically open and ReadMessage will keep returning data. Exiting the read loop immediately would either mean duplicating the close logic here or leaving the socket in a half-torn-down state; discarding further reads until the real close happens (which stops ReadMessage with an error, ending the loop naturally) keeps there being exactly one place that actually closes the connection.

Improvement note
No weakness found beyond the shared clientIP gap noted under server.go. The two-pump, single-writer design and the close-sentinel ordering are both textbook solutions to real, named concurrency hazards, and — notably for this package specifically, unlike most of module 13's room package — this behavior actually has test coverage: backend/internal/ws/ contains five test files totaling roughly 2,900 lines (autoplay_test.go, online_test.go, persistence_test.go, private_test.go, resilience_test.go) against 826 lines of source in this module's four files — more than three lines of test for every line of implementation, including scenarios named for exactly the kind of thing this module handles: reconnects, autoplay handoff, private and online table flows. This is worth noting because it demonstrates the gap flagged repeatedly in module 13 is not a project-wide habit — this package proves the team tests exactly this class of networking/concurrency code well elsewhere; the room package's near-total absence of tests is an inconsistency, not an inherent limitation of how this codebase is written.

ws/identity.go

backend/internal/ws/identity.go
Purpose

Turns a client-supplied device id into a stored account id, in the background, without a slow or unreachable database ever adding latency to the moment a player sits down at a table — the concrete mechanism behind the "identity is an enrichment, never a precondition" rule this module's server.go section already named.

Decision

A channel-close happens-before edge, not a mutex, guards the shared result. 

type accountLookup struct {
	id   string
	done chan struct{}
	delivered bool
}

The comment states the safety argument directly: "id is written before done is closed and read only after done is observed closed, which is the happens-before edge that makes it safe without a lock." This leans on a specific, named Go memory-model guarantee (a channel close happens-before any receive that observes it) rather than a sync.Mutex — a smaller, allocation-cheaper primitive doing exactly the one job needed here: one writer, potentially several readers, one irreversible transition from "pending" to "done."

Two separate access methods — peek (never blocks) and attach (waits, but off on its own goroutine) — instead of one function that always blocks with a timeout. A single blocking "get the result, waiting up to N seconds" function would be simpler to write, but would reintroduce exactly the coupling this design exists to avoid: whoever calls it would have to decide how long they're willing to wait, and any nonzero wait re-couples the join to the database's latency. Splitting the two calls lets the fast path (database answered already) cost nothing, and the slow path (still pending) cost one extra goroutine that attaches the answer whenever it eventually arrives — with the seat already allocated and the player already playing either way.

Explanation
func (l *accountLookup) peek() string {
	if l == nil { return "" }
	select {
	case <-l.done:
		l.delivered = true
		return l.id
	default:
		return ""
	}
}

func (l *accountLookup) attach(c *Conn, table *room.Room, seat int) {
	if l == nil || table == nil || l.delivered { return }
	go func() {
		<-l.done
		table.AttachUser(c, seat, l.id)
	}()
}

peek's select with a default case is the non-blocking read: if done is already closed, take the answer; otherwise return empty immediately, no waiting. It also records l.delivered = true the moment it succeeds — which is exactly what lets attach skip spawning a goroutine at all in the common case where the database answered quickly: "the test is peek's own record rather than the channel: the lookup may well have finished in between, and that answer still has to reach a seat that was allocated without it" — so even a lookup that finishes a few milliseconds too late to make peek's window is guaranteed to eventually reach the seat via room.AttachUser (module 13), just later.

Improvement note
No weakness found. This is a small, carefully reasoned piece of concurrent code whose safety argument is documented inline rather than left implicit, and the pending-database-answer scenario is exactly the kind of edge case a rushed implementation would get wrong (either by blocking the join, or by dropping a late answer on the floor) — neither happens here.

ws/limit.go

backend/internal/ws/limit.go
Purpose

Two independent defenses against abuse, at two different scopes: a per-connection message-rate limiter (a single misbehaving or buggy client flooding frames), and a per-IP-address connection-count cap (many sockets from one source trying to exhaust the server).

Decision

The token bucket is deliberately lock-free, because it's structurally impossible for it to need one. The comment: "it is deliberately tiny and allocation-free: there is one per connection, and it is consulted on every frame. Not safe for concurrent use — each bucket is touched only by its own read pump." Because exactly one goroutine (that connection's own read pump, per conn.go's two-pump design) ever calls allow() on a given bucket, adding a mutex here would be pure overhead paid on every single incoming frame for a race that can never occur — the same "no lock needed because only one goroutine ever touches this" reasoning module 13's room actors use for game state, applied at connection scope instead of table scope.

The IP limiter, by contrast, needs its lock — because it's shared across every connection on the server. Unlike the bucket, many connections' goroutines call acquire/release concurrently on the same ipLimiter instance (there's exactly one, owned by Server), so its map genuinely is shared mutable state — and it gets the sync.Mutex the bucket correctly omits. Two structurally similar-looking rate limiters, two different concurrency answers, each correct for its actual scope.

Explanation
func (b *bucket) allow() bool {
	now := time.Now()
	b.tokens += now.Sub(b.last).Seconds() * b.rate
	if b.tokens > b.burst { b.tokens = b.burst }
	b.last = now
	if b.tokens < 1 { return false }
	b.tokens--
	return true
}

Classic token bucket: tokens accumulate continuously at rate per second, capped at burst so a client that's been idle for a while can't bank unlimited tokens and then unleash a huge burst — it can only ever have up to burst saved up. Every allowed frame costs exactly one token. Module 11's MsgRatePerSecond (default 20) and MsgBurst (default 40) are what parameterize this per connection.

Improvement note
The IP limiter's fairness is only as good as clientIP's accuracy, which this module's server.go section already flagged as trusting unauthenticated headers. That gap surfaces here concretely: an attacker who can vary their apparent address defeats MaxConnsPerIP entirely, since ipLimiter itself has no way to know the address it was given is fabricated — it does exactly what it's supposed to with the input it's handed. No further independent weakness in this file itself.

Checkpoint

Why can Server.Locator safely be nil, and what does that buy a single-node deployment?
Every call site checks if s.Locator != nil before using it, so a nil Locator simply means every table this server knows about is considered its own — no redirect logic ever runs. A single developer running the server locally never has to stand up Redis or any cross-node registry just to accept a connection.
Why does Conn use two goroutines with a strict "only the write pump writes" rule, instead of a mutex around every WriteMessage call?
gorilla/websocket connections are not safe for concurrent writes from multiple goroutines. Rather than guard every one of several write call sites with a lock, the design sidesteps the question by making exactly one goroutine the only writer — everything else posts to a channel instead.
Why does accountLookup use a closed channel as its synchronization primitive instead of a mutex protecting the result field?
A channel close is a one-way, irreversible "done" signal with a documented happens-before guarantee in Go's memory model — exactly what's needed for a single writer and potentially multiple readers of a value that's written once and never changes again. It's a smaller, cheaper primitive than a mutex for a job that never needs to be reversed or re-locked.
Why does the per-connection token bucket need no lock, while the per-IP connection limiter does?
Exactly one goroutine — that connection's own read pump — ever touches its bucket, so there is structurally nothing to race. The IP limiter is a single shared instance that many different connections' goroutines call into concurrently, so its map is genuinely shared mutable state that does need a lock.
