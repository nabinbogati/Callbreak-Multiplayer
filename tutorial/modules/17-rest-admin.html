Part III — Go backend · Module 17 of 20

REST API & Admin Dashboard

The socket carries play; everything request/response-shaped — signing in, reading a profile, listing history, uploading a solo game, and an operator's live dashboard — lives in httpapi. This module covers the wire contract (wire.go), the error vocabulary (errors.go), the middleware chain that every route runs through (api.go), REST's own rate limiter (limit.go), the one endpoint a client fully controls (games.go's upload handler), and the admin token gate (admin.go).

Where this fits

httpapi/wire.go

backend/internal/httpapi/wire.go
Purpose

The REST equivalent of module 11's protocol.go: every JSON shape that crosses this boundary, collected in one file, mirroring docs/API.md block for block, so no handler ever writes a response body by hand.

Decision

Timestamps are formatted explicitly, never left to time.Time's default marshaller. 

func rfc3339(t time.Time) string { return t.UTC().Format(time.RFC3339) }

The file comment names why: "time.Time's own marshaller emits nanoseconds and a numeric offset, neither of which the document promises." Go's default JSON encoding of a time.Time is technically valid RFC 3339 but includes sub-second precision and whatever offset the value happens to carry — accurate, but not what the documented contract commits to. Formatting explicitly here is what keeps every timestamp the client receives shaped exactly as promised, regardless of what precision or timezone happened to be attached to the underlying Go value.

statsJSON deliberately omits every derived figure — win rate, average score, bid accuracy — exactly as db.Stats (module 16) does. The comment: "the client derives them, so the two can never disagree." The same "never store what can be computed" principle from module 16 crosses the wire boundary unchanged — this file could have computed and included a winRate field for convenience, but doing so would create a second place that number could go stale relative to its own inputs.

uploadSeatJSON.UserID is decoded, on purpose, even though the documented contract says it must never be sent. This is the one deliberate exception to decodeBody's general "unknown fields are always safe to ignore" policy (covered under api.go below): a client that includes a userId in an upload isn't committing an unknown-field mistake Go should silently swallow — it's attempting something the server needs to actively refuse and explain, which games.go's validation does. Decoding the field is what makes that refusal possible at all.

Explanation
func nullableID(id string) *string {
	if id == "" { return nil }
	return &id
}

func score(f float64) float64 { return math.Round(f*100) / 100 }

Two small, consistently-applied conventions run through every constructor in this file: an empty id (a bot seat, or a human the server couldn't attribute — module 13's redaction-adjacent concept, applied here to identity rather than cards) becomes JSON null rather than an empty string, and every float that reaches a client is rounded to two decimals — matching the numeric(6,2) column module 16's schema actually stores it in, so a client never has to look at 13.199999999999999, a float-representation artifact that was never really part of the data.

Improvement note
No weakness found. This package is, like ws (module 14) and db (module 16), genuinely well tested — api_test.go runs to 1,560 lines, the single largest test file anywhere in this backend. The pattern holds again: code at an external-facing edge gets careful test coverage in this codebase; the purely internal orchestration layer (module 13's room package) remains the outlier.

httpapi/errors.go

backend/internal/httpapi/errors.go
Purpose

Every non-2xx response this package ever sends needs the same shape, and every one of the handful of ways a db.Store call can fail (module 16's sentinel errors) needs to become the exact same wire error every time, regardless of which of dozens of call sites hit it.

Decision

The error body is an object, not a bare string, specifically so it can grow without becoming a breaking change. 

type errorBody struct {
	Code    string `json:"code"`
	Message string `json:"message"`
	ExistingUserID string `json:"existingUserId,omitempty"`
}

The comment: "the reserved conflict response for POST /v1/auth/link adds existingUserId beside the code, and a client that ignores unknown keys keeps working either way." This is the identical additive-fields-are-safe philosophy module 11's protocol package states for the WebSocket wire format, applied to REST error responses — a field can be added to this envelope in the future without every existing client breaking, because nothing about the shape itself changed, only what's present in one specific error case.

db.ErrDisabled maps to 503, not 500. The comment: "persistence being off is a supported deployment (PERSISTENCE.md §5), not a fault." This distinction — between "the operator chose not to configure a database" and "something genuinely broke" — is the REST-facing expression of the exact same Nop-store philosophy module 16 builds the whole persistence layer around: a 503 tells a client (and an on-call engineer reading a status-code dashboard) "this is an expected, configured state," where a 500 would wrongly suggest a bug.

Explanation
func storeError(w http.ResponseWriter, log *slog.Logger, op string, err error) {
	switch {
	case errors.Is(err, db.ErrDisabled):
		writeError(w, http.StatusServiceUnavailable, codePersistenceDisabled, msgDisabled)
	case errors.Is(err, db.ErrNotFound):
		writeError(w, http.StatusNotFound, codeNotFound, msgNotFound)
	case errors.Is(err, db.ErrConflict):
		writeError(w, http.StatusConflict, codeConflict, ...)
	default:
		log.Error("store call failed", "op", op, "err", err)
		writeError(w, http.StatusInternalServerError, codeInternal, msgInternal)
	}
}

Every handler in this package that touches the store funnels its error through this one function rather than writing its own status code — the comment notes only the unexpected, default branch is worth an error-level log line, since the three named cases above it are "ordinary outcomes," not bugs. This is the REST-layer counterpart to module 16's Postgres.fail: two different translation functions, at two different boundaries, both converting a small internal error vocabulary into whatever the layer above actually needs — Go sentinel errors here becoming wire error codes, driver errors there becoming Go sentinel errors.

Improvement note
No weakness found — a small, single-purpose file doing exactly one job (translate errors to responses) consistently across the whole package.

httpapi/api.go

backend/internal/httpapi/api.go
Purpose

Everything that has to happen to every request before a handler's actual logic runs — panic isolation, logging, the database-not-configured short-circuit, authentication, rate limiting — plus the route table that decides which handler a request even reaches.

Decision

Authentication runs before rate limiting on private routes, specifically so the limiter keys on an account, not an address. 

func (s *Server) private(h http.HandlerFunc) http.Handler {
	return s.recoverPanics(s.logRequest(s.requireStore(s.authenticate(s.limitByUser(h)))))
}

The comment: "four players behind one café router must not share an allowance." Reversing the order — rate-limiting by IP before authenticating — would mean every phone on the same Wi-Fi network (a household, an office, a café) drained from one shared bucket regardless of how many distinct, legitimate accounts were behind it. Authenticating first means the limiter sees "u:" + userID — one bucket per real account — for every route that requires a session, and only the single unauthenticated route (POST /v1/auth/device, via public) has to fall back to limiting by address, because there's no account yet to key on.

recoverPanics re-panics on one specific, named sentinel instead of swallowing every panic uniformly. 

if err, ok := rec.(error); ok && errors.Is(err, http.ErrAbortHandler) {
	panic(rec)
}

The comment: "http.ErrAbortHandler is the documented way to abandon a response; it is not a bug and must be re-panicked for the server to see it." This is a specific piece of standard-library knowledge encoded directly into the recovery logic: Go's own net/http package uses a panic with this exact sentinel value as its blessed mechanism for a handler to deliberately abandon a response mid-flight, and the HTTP server itself is listening for that specific panic to handle the abandonment correctly. A recovery handler that caught every panic uniformly — the naive, seemingly-safer choice — would actually break that mechanism by intercepting it before the standard library ever saw it.

Unknown JSON fields are accepted, not rejected, on every decode. decodeBody uses a plain json.NewDecoder, never calling DisallowUnknownFields. The comment: "docs/API.md promises that adding a field is safe, and that promise has to hold in both directions or a newer client cannot talk to an older server." A stricter decoder that rejected any JSON key it didn't recognize would be a real, defensible hardening choice in a different system — it can catch a client sending garbage it thinks means something. Here, it would break exactly the forward-compatibility guarantee the whole wire contract is built around: an app update that adds a field to a request would fail against any server that hasn't been redeployed yet.

Explanation
func (s *Server) authenticate(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		token, ok := bearerToken(r)
		if !ok { writeError(w, http.StatusUnauthorized, codeUnauthorized, msgUnauthorized); return }
		userID, err := s.signer.VerifySession(token)
		if err != nil || userID == "" {
			s.log.Debug("rejected session token", "path", r.URL.Path, "err", err)
			writeError(w, http.StatusUnauthorized, codeUnauthorized, msgUnauthorized)
			return
		}
		next.ServeHTTP(w, r.WithContext(withUserID(r.Context(), userID)))
	})
}

The comment: "Every failure looks the same from outside — a client cannot learn whether a token was forged, expired or simply of the wrong kind." Every failure path returns the identical 401 unauthorized with the identical message, and the actual reason is only ever logged at debug level server-side — the same principle as module 15's uniform ErrWrongKind/ErrExpired/ErrSignature treatment, applied at the HTTP layer: a distinguishable error response would hand an attacker a free oracle for probing which kind of forgery attempt came closest to working. 

func (s *Server) requireStore(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		if !s.store.Enabled() {
			writeError(w, http.StatusServiceUnavailable, codePersistenceDisabled, msgDisabled)
			return
		}
		next.ServeHTTP(w, r)
	})
}

Notice this runs before authenticate in both chains — a deployment with no database answers 503 to every /v1 route before it ever tries to verify a token, which is the correct order: there's no point checking a credential against a service that has nothing to serve regardless of whether it's valid.

Try it yourself — Handler() registers routes like "POST /v1/auth/device" with the method baked into the pattern string. What does that buy over registering just "/v1/auth/device" and checking r.Method inside the handler?
Show solution 
// Method-qualified patterns mean a GET to a POST-only route is a 405 from
// the mux rather than something a handler has to check.
mux.Handle("POST /v1/auth/device", s.public(s.handleDeviceAuth))

Go 1.22's net/http.ServeMux understands method-qualified patterns natively — a GET to a route registered only for POST gets an automatic 405 Method Not Allowed straight from the standard library's router, before any of this package's own middleware or handler code runs at all. The alternative (registering a bare path and checking r.Method == http.MethodPost inside every handler) would mean writing that same check, and remembering to write it correctly, in every single handler in the package — one more thing that could be forgotten or gotten subtly wrong per route.

Improvement note
clientIP in this file is a byte-for-byte duplicate of ws/server.go's function of the same name (module 14): same header-trust order (X-Real-IP, then the first hop of X-Forwarded-For, then the raw socket address), same lack of any trusted-proxy allowlist. Module 14 already covers the concrete risk in depth — an attacker connecting directly, bypassing any real load balancer, can spoof either header to make every request look like it's coming from a fresh address, defeating limitByIP (this file) and ipLimiter (module 14) alike. What's worth adding here is scope: this is now confirmed as a systemic pattern across both of this server's edges, WebSocket and REST, with the identical logic independently duplicated rather than shared from one place — meaning a fix also has to happen twice, in two files, unless the function is extracted into a shared package first.

httpapi/limit.go

backend/internal/httpapi/limit.go
Purpose

The REST-side rate limiter — the same job module 14's ws/limit.go token bucket does for the socket, adapted to a protocol with no persistent connection to hang per-caller state off.

Decision

Keyed by string in a map, with inline sweeping — not one bucket per connection, because REST has no connection. The comment states the contrast directly: "Same shape as the socket's per-connection bucket ... but keyed by a string, because REST has no connection to hang state off." Module 14's bucket got to be lock-free because exactly one goroutine (a connection's read pump) ever touched it; here, many concurrent requests for the same account or address all share one bucket, so keyLimiter needs both a map and a mutex module 14's version didn't.

Sweeping stale buckets happens inline, on the request path, rather than on a background goroutine. 

// Sweeping happens inline rather than on a background goroutine: a limiter
// with no goroutine cannot outlive the server that made it, which matters
// most in tests, where one is built per case.

A background goroutine ticking on its own schedule is the more obvious design, but it introduces a lifecycle problem: something has to stop that goroutine when the limiter is no longer needed, or it leaks — a real annoyance in a test suite that constructs a fresh Server (and therefore a fresh limiter) for every test case. Folding the sweep into allow() itself, gated by "has it been at least a minute since the last sweep," removes the lifecycle question entirely: the limiter is just a plain struct with no goroutine of its own, so it's collected exactly like any other value the moment nothing references it anymore.

A full minute's worth of requests as the burst allowance, matching how REST traffic actually shapes up. The comment: "the client's real traffic is bursty (opening the profile fires three GETs at once) and then idle, which is exactly the shape a token bucket forgives." Module 14's socket-side bucket defaults to a much tighter 20-per-second rate with a 40-message burst, appropriate to a steady stream of small game frames; this one is sized for a completely different traffic pattern — a screen opening that fires a handful of concurrent requests, then nothing for a while.

Explanation
func (l *keyLimiter) sweep(now time.Time) {
	if now.Sub(l.lastSweep) < sweepEvery { return }
	l.lastSweep = now
	for key, b := range l.buckets {
		if now.Sub(b.last) > idleEviction {
			delete(l.buckets, key)
		}
	}
}

Called from inside allow(), under the same lock, at most once per minute regardless of request volume — the comment on eviction is worth noting too: "Anything evicted comes back full, which is correct: a caller idle for that long has earned a full bucket anyway." A bucket that's disappeared from the map because nobody used it in five minutes is indistinguishable, on the next request, from a caller who's never been seen before — exactly the right behavior, since both cases deserve a fresh full allowance.

Improvement note
No weakness found. This is a small, well-adapted variant of the same rate- limiting pattern used elsewhere in the codebase, with each difference from the socket-side version (the map, the lock, the inline sweep, the burst size) traceable to a real, stated constraint specific to REST rather than an arbitrary divergence.

httpapi/games.go — the upload handler

backend/internal/httpapi/games.go
Purpose

Bots and LAN games are played entirely on a device and never touch the server live (modules 5 and 10) — the only way one reaches a player's history is for the device to upload it after the fact. That makes this endpoint unique in the whole package: it's the one place a client supplies an entire finished game record, not just a request for something the server already knows.

Decision

Seat ownership is rewritten from the session, never trusted from the payload — and a payload that tries to set it is refused outright, not silently corrected. 

if seat.UserID != nil && *seat.UserID != "" {
	return zero, fmt.Errorf("seats must not carry a userId; your own seat is taken from your session")
}
...
for i := range seats {
	if seats[i].Seat == yours {
		seats[i].UserID = userID
		break
	}
}

The comment on uploadSeatJSON.UserID (this module's wire.go section) already named the reasoning: a client attempting to set this field is "told plainly that seat ownership comes from the session, rather than having the field silently dropped and quietly believing it worked." This is the one field in the whole upload where silently ignoring an unexpected value (the package's normal, generous policy) would be actively dangerous — a client bug that thinks it's attributing a seat to some other account would otherwise fail invisibly, with the developer never finding out their attempt did nothing.

Only bots and lan modes may be uploaded — online and private are refused outright. Both of those modes are played on the server, which records them itself (module 13's Recorder) — accepting an uploaded "online" result here would let any client simply assert it won a match no server ever adjudicated, exactly the kind of client-authoritative result module 16's Source field (SourceServer vs SourceClient) exists to keep separate. Rejecting the mode outright, rather than accepting it and marking it client-sourced anyway, closes the door entirely rather than relying on every downstream consumer remembering never to trust a client-sourced online game.

Validation and record construction happen in one pass, in one function, rather than a validate-then-build split. The comment: "the seat that gets the caller's user id is decided in the same pass that proves there is exactly one isYou seat, so the two cannot drift apart." Splitting this into a separate validation function followed by a separate construction function is the more conventional shape — but it opens a real, if subtle, risk: two passes over the same data that are supposed to agree (which seat is "yours") could theoretically disagree if one were ever edited without the other. One function, one loop, closes that gap structurally rather than by convention.

Explanation
const (
	maxSeats           = 4
	maxHandsTotal      = 100
	maxClientGameIDLen = 128
	maxDifficultyLen   = 32
)

Every one of these bounds exists because a client controls this payload completely — the comment on maxHandsTotal makes the reasoning for that one explicit: "it is multiplied by four to bound the hands array, and a client that sends a billion would make that check vacuous. A hundred is two decades of the longest format anyone plays." Every numeric or string-length limit in this file traces back to the same instinct: bound everything a client fully controls, generously enough that no real game ever brushes against the limit, tightly enough that a malicious or buggy payload can't turn a validation check into a multi-gigabyte allocation. 

func parseUploadTime(field, raw string) (time.Time, error) {
	if raw == "" { return time.Time{}, nil }
	t, err := time.Parse(time.RFC3339, raw)
	if err != nil {
		return time.Time{}, fmt.Errorf("%s must be an RFC 3339 timestamp", field)
	}
	return t.UTC(), nil
}

A malformed timestamp is refused outright rather than defaulted to now() or silently zeroed — the comment: "a game with a garbled clock would sort wrongly in a history list forever, and the client cannot fix it afterwards." Once a bad timestamp is committed to the database, the player has no way to correct it themselves; rejecting the whole upload at the boundary, where the client can actually retry with a fixed value, is the only point where this is still fixable.

Improvement note
No weakness found — and worth calling back explicitly to module 16's own improvement note on db.RecordGame: the maxClientGameIDLen check here (128 characters) is exactly the defense-in-depth validation this file performs correctly for the one caller that goes through it. The gap module 16 identified is specifically that this same discipline doesn't also exist independently inside the db package itself — this handler is doing its job properly; the concern is what protects RecordGame from any caller that isn't this handler.

httpapi/admin.go — the token gate

backend/internal/httpapi/admin.go
Purpose

A live, human-facing view of every table on this node plus the runtime- tunable pacing defaults, for an operator debugging a production issue — deliberately independent of the database (module 13's Room.Snapshot reads live in-memory state), because, per the file's own comment, "an operator needs the dashboard most exactly when something else has gone wrong."

Decision

The admin token comparison is constant-time, the same defense module 15's auth.Signer uses for HMAC signatures. 

func (s *Server) admin(next http.HandlerFunc) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		token, ok := bearerToken(r)
		if !ok || subtle.ConstantTimeCompare([]byte(token), []byte(s.adminToken)) != 1 {
			writeError(w, http.StatusUnauthorized, codeUnauthorized, "That admin token is not valid.")
			return
		}
		next(w, r)
	})
}

The comment: "the token is a credential an operator typed somewhere; timing it must not leak it." Exactly module 15's timing-oracle argument, applied to a completely different credential — an admin token is a single static secret rather than a signed, structured token, but it's just as vulnerable to the same byte-by-byte timing attack a naive comparison would permit.

The dashboard's HTML shell is served without checking the token at all — only the data it fetches is gated. 

mux.Handle("GET /admin", s.adminPage())                       // no s.admin(...) wrapper
mux.Handle("GET /v1/admin/rooms", s.admin(s.handleAdminRooms)) // gated

This looks, at a glance, like an oversight — but it follows directly from how bearer tokens work: a plain browser navigation to a URL cannot attach an Authorization header, so if the shell itself required the token to load, there would be no way for an operator's browser to ever present it in the first place except through some other mechanism (a cookie, a token embedded in the URL) each carrying its own, arguably worse, set of risks. The comment states the actual security argument: "The page is a shell; every piece of data it shows comes from the API routes above it, so the token protects the whole thing rather than just this file." The HTML and JavaScript alone contain no player data, no game data, nothing from db.Store or room.Hub — real data only starts flowing once the page's own JavaScript makes its first authenticated fetch() call, at which point it can attach the token exactly like any other API client.

Explanation
func (s *Server) adminPage() http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		w.Header().Set("Content-Type", "text/html; charset=utf-8")
		w.Header().Set("X-Frame-Options", "DENY")
		_, _ = w.Write(adminUI)
	})
}

X-Frame-Options: DENY is a small, specific defense worth noticing: it stops this one page from ever being loaded inside an <iframe> on another site, which closes off clickjacking — tricking an already-logged-in operator into clicking something on the real dashboard while believing they're interacting with a different page overlaid on top of it. The header is set here, on this one route, rather than globally — the rest of the REST API returns JSON, not a renderable page, so the same attack doesn't apply to it.

Improvement note
Serving the dashboard shell without a token is a deliberate, well-reasoned choice (see Decision above), not an oversight — but it does still leak the existence and internal structure of an admin surface (route names, page layout, whatever the embedded JavaScript reveals about the API shape) to any unauthenticated request, which a determined attacker could use for reconnaissance even though the page carries no real data on its own. This is a genuinely low-severity concern given the actual data stays behind the constant-time-checked token regardless — worth naming as a real, if minor, residual information disclosure rather than a gap that needs fixing.

Checkpoint

Why does authentication run before rate limiting on every private route?
So the limiter can key its bucket on the authenticated account rather than the caller's IP address — otherwise every device sharing one network address (a household, a café) would drain from one shared allowance regardless of how many distinct accounts were actually behind it.
Why does decodeBody accept unrecognized JSON fields instead of rejecting them as a hardening measure?
Because docs/API.md promises that adding a field to either side of the wire contract is always safe, and that promise has to hold in both directions — rejecting unknown fields would break a newer client talking to a server that hasn't been redeployed with the field it now sends.
Why does the game-upload handler refuse a payload that includes a userId on any seat, rather than silently ignoring it the way an unrecognized field elsewhere would be ignored?
Because silently dropping it would let a client believe an attempt to attribute a seat to some account had succeeded when it actually did nothing — a client bug or malicious attempt would fail invisibly. Refusing the whole request loudly is the only way the client author finds out immediately that seat ownership always comes from the session, never the payload.
Why is the admin dashboard's HTML shell served without checking the admin token, while every API route it calls is gated?
A plain browser navigation cannot attach an Authorization header, so requiring the token to load the shell itself would leave no way for a browser to ever present it. The shell alone contains no real data — actual game and room data only flows once the page's own JavaScript makes its first authenticated request, at which point the token gate applies exactly like any other API caller.
