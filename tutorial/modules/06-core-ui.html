Core Table UI

This is the milestone module: by the end of it, flutter run shows a real, playable game against bots on your screen. It wires home_screen.dart's mode picker to a LocalSession (module 5), and renders it with table_screen.dart and its two foundational card widgets.

Scope note: table_screen.dart is 3,209 lines — by far the largest file in the project (flagged in the Roadmap, module 20, as a maintainability concern in its own right). This module covers its orchestration pattern in depth with real excerpts and exact line numbers, not every widget inside it line-by-line. playing_card_view.dart and hand_fan.dart, the two files under it that do the most interesting work, are covered in full.

Where this fits

Wiring a mode to a session

frontend/lib/ui/screens/home_screen.dart:839–889
Purpose

Something has to translate "the player tapped vs Bots" into an actual running game. This function is that single translation point — the one place in the codebase where a GameMode becomes a concrete GameSession implementation and gets handed to the screen that renders it.

Decision

One function, branching on mode, that constructs the concrete session and pushes TableScreen with it — rather than, say, TableScreen itself deciding what kind of session to build from a mode parameter. Keeping session construction in the caller (here) and letting TableScreen only ever accept an already-built GameSession (module 5's contract) is what keeps the screen honestly ignorant of which mode it's rendering — it's the same decision as module 5's session abstraction, paid off at the call site.

Explanation
Future<void> startTable(BuildContext context, GameMode mode) async {
  final settings = SettingsScope.of(context);

  if (mode.isOffline) {
    final details = await showJoinSheet(context, mode: mode);
    if (details == null || !context.mounted) return;
    _push(context, LocalSession(
      playerName: settings.playerName,
      difficulty: settings.difficulty,
      mode: mode,
      animationSpeed: settings.animationSpeed,
      handsPerGame: details.handsPerGame ?? handsPerGame,
    ));
    return;
  }
  ...
}

void _push(BuildContext context, GameSession session) {
  Navigator.of(context).push(
    MaterialPageRoute<void>(builder: (_) => TableScreen(session: session)),
  );
}

mode.isOffline (defined in module 5's session.dart as this == GameMode.bots) is the entire branch that decides "build a LocalSession, no server talk at all." Every setting the offline game needs — player name, bot difficulty, animation speed, match length — comes straight from AppSettings (module 7) and the just-collected details from a join sheet, then flows into LocalSession's constructor exactly as built in module 5. Notice _push — the function every branch eventually calls — takes the abstract GameSession type, not a specific subclass: that's what makes this the one place in the whole app that ever needs to know which concrete session type exists for which mode.

Improvement note
No weakness in this exact function — it's a thin, honest dispatcher. (The online/LAN branches it also contains are covered in modules 9 and 10.)

ui/widgets/playing_card_view.dart

frontend/lib/ui/widgets/playing_card_view.dart:9–80
Purpose

Every screen that shows a card — the hand fan, the felt, the scoreboard replay — needs the same visual card, just at different sizes (a 54pt hand card, a 44pt table card). Without one shared widget, each of those would drift visually out of sync over time exactly the way tokens.dart (module 4) exists to stop colours from drifting.

Decision

Every internal measurement is a ratio of the widget's own width parameter (e.g. width * (14 / 54)) rather than going through Metrics.s() (module 4) directly inside this widget. This keeps PlayingCardView genuinely size-agnostic — hand this same widget class a width of 54 or 44 and every padding, border, and font size scales proportionally with it, with zero special-casing. The trade-off: the ratios themselves (7/54, 6/54, 14/54...) are "magic numbers" baked from the original 54pt design reference with no named constant explaining what each one represents — you have to trust the comment ("Every internal measurement is derived from width") and infer the rest from the numbers themselves.

Explanation
final radius = width * (7 / 54);
final pad = width * (6 / 54);
...
Text(card.label, style: AppText.bold(width * (14 / 54), inkColor)),
SizedBox(height: width * (2 / 54)),
Text(card.suit.symbol, style: AppText.bold(width * (16 / 54), inkColor)),

Whatever width is passed in, the corner radius is always 7/54ths of it, the padding 6/54ths, and so on — so a card drawn at any size looks like a uniformly scaled photograph of the same card, never a differently-proportioned redraw. The caller (HandFan, next) is what actually decides which width to pass, using Metrics.s() upstream — this widget itself only knows about its own local proportions.

Try it yourself — why is dimmed implemented as an Opacity wrapper around the whole card, rather than, say, changing the card's own colours to greyed-out versions?
Show solution 
return Opacity(
  opacity: dimmed ? 0.45 : 1,
  child: Container(...),
);

One Opacity wrapper dims everything inside uniformly — face colour, ink, border, shadow — with a single value, regardless of which CardStyle (module 4) is active. Hand-picking a "dimmed" variant of every one of the six card-face palettes would be six times the work for a purely cosmetic state, with no functional benefit.

Improvement note
No functional weakness — the trade-off flagged above (unexplained scaling ratios) is a minor readability cost, not a correctness or robustness one.

ui/widgets/hand_fan.dart

frontend/lib/ui/widgets/hand_fan.dart
Purpose

The player's hand isn't just a static row of cards — it has to lay out 13 overlapping cards that reflow as cards are played, show which ones are legal to play right now, and accept either a tap or a drag-upward gesture to throw one. This file is all of that in one place, so table_screen.dart only has to hand it a hand and a set of legal ids and get playable cards back.

Decision

A card's pressed/dragged state is tracked by card id (_pressedCardId), not by list index. A card's index in the hand shifts every time another card is played and removed — tracking by id means the fan stays visually correct across a rebuild even if the pressed card's position in the list changed. The cost is one extra lookup (widget.cards.indexWhere(...), line 151) every build to resolve the id back to a current index.

Both tap-to-play and drag-to-play are supported simultaneously, with drag release triggered the instant the threshold is crossed rather than on finger-lift. The alternative — commit only when the finger actually lifts — reads as laggy for a fast, decisive flick. The cost is real gesture complexity: _FanCard tracks tap-down, tap-up, tap-cancel, drag-start, drag-update and drag-end as six separate callbacks, each with its own guard against double-firing (the _thrown flag), because a real touch gesture can transition between "might be a tap" and "is now a drag" mid-stream.

Explanation

Fan layout — spacing differs by orientation on purpose (lines 108–139):

final spacing = n <= 1
    ? 0.0
    : m.isPortrait
    ? (widget.cardWidth * 0.55).clamp(0.0, fillSpacing)
    : fillSpacing.clamp(0.0, widget.cardWidth * 0.7);

Per the comment above this line: portrait rarely has enough width for 13 cards laid edge-to-edge, so it keeps the traditional overlapping fan at a fixed 55%-of-card-width spacing. Landscape has width to spare, so spacing grows toward filling the available space — but capped at 70% of a card's width, so at least 30% always stays overlapped, which is what keeps the fan reading as one hand instead of a loose row of individual cards.

Throwing a card — commit on threshold, not on release (lines 378–389):

void _onVerticalDragUpdate(DragUpdateDetails details) {
  if (!_canDrag || !_dragging || _thrown) return;
  setState(() { _dragOffset += details.delta; });
  // Release as soon as the card has moved far enough, without waiting for
  // the finger to actually lift — a decisive enough flick should commit
  // right away rather than requiring the user to also let go.
  if (-_dragOffset.dy >= widget.dragThreshold) {
    _throwCard();
  }
}

dragThreshold itself (set by the parent HandFan.build, module 5's sibling file) is cardHeight * 0.3 — relative to the card's own rendered size, not a fixed pixel count, so "far enough to throw" feels the same whether the card is rendered small (portrait, many cards) or large (landscape). Once _throwCard() sets _thrown = true, every subsequent drag callback's guard clause (if (... || _thrown) return;) becomes a no-op — the card is already on its way out and nothing here should touch its state again.

Try it yourself — the comment on _throwCard() explains a real, previously-fixed visual bug. Read it, then guess what the bug looked like before the fix.
Show solution 
void _throwCard() {
  _thrown = true;
  _dragging = false;
  // Deliberately not touching _pressed or _dragOffset here: the parent's
  // state update (from onPlay, below) removes this card from the hand in
  // the very same frame, so this widget is about to be unmounted outright.
  // Resetting the zoom/lift/drag transforms first — as this used to do —
  // meant they'd animate back toward the resting slot for a frame or two
  // before disappearing, reading as the card snapping back into place
  // before vanishing. ...
  widget.onPlay?.call(widget.card, _releasePosition);
}

Before this fix, resetting the drag offset/zoom state before notifying the parent meant the widget briefly re-rendered at its resting position — snapping back — for a frame or two before the parent's rebuild actually removed it from the hand. The fix is to change nothing about this widget's own visual state and let it simply vanish mid-throw, which reads as one continuous motion instead of a snap-then-disappear.

Improvement note
No functional weakness found — the gesture-state machine here is unusually well-commented for exactly the subtle interaction bugs (tap-vs-drag race, snap-back-then-vanish) that this class of UI code tends to hide. Worth studying as an example of documenting why, not what.

ui/screens/table_screen.dart — orchestration

frontend/lib/ui/screens/table_screen.dart
Purpose

Everything built so far in Part II needs one place to actually come together on screen: subscribe to the session's view and events, render the felt, the seats, the hand, the bid panel, the scoreboard, and react to the session telling it something happened (a card played, a reconnect, a hand dealt). TableScreen is that place — the single widget every mode's table renders through.

Decision

One TableScreen, driven purely by the GameSession abstraction, instead of a separate screen per mode (an OfflineTableScreen, OnlineTableScreen, etc). This is where module 5's whole session-abstraction decision cashes out: because every mode implements the same GameSession contract, one screen renders all of them, and any bug fix or visual change here benefits every mode at once. The one place mode-specific behaviour leaks back in is explicit type checks like widget.session is RemoteSession (line 196) and the _isRealSession getter (lines 216–219) — a deliberate, narrow exception, not a general pattern used throughout the file.

Explanation

Subscribing to the session (lines 193–231):

void initState() {
  super.initState();
  final session = widget.session;
  _rejoined = session is RemoteSession && session.resumeToken != null;
  session.addListener(_onSessionChanged);
  _eventsSub = session.events.listen(_onGameEvent);
  if (_isRealSession) {
    _maybeStartDeal();
  }
}

@override
void dispose() {
  _autoPlayTimer?.cancel();
  _presenceTimer?.cancel();
  _eventsSub?.cancel();
  AudioController.instance?.stopDeal();
  widget.session.removeListener(_onSessionChanged);
  widget.session.dispose();
  super.dispose();
}

This is the ChangeNotifier + Stream pattern from module 5, consumed exactly as that module predicted: addListener(_onSessionChanged) for "the view changed, rebuild," and a separate StreamSubscription on events for one-shot happenings (this is where sound effects are triggered, per the comment on _eventsSub: "Fired from the session's event stream so it covers local throws, bots and remote plays alike" — one listener, working identically no matter which GameSession implementation is behind it). dispose() tears down in the mirrored order: cancel timers and the event subscription first, then unsubscribe from the notifier, and — notably — widget.session.dispose() is called from here, the screen, not by whoever constructed the session. TableScreen takes ownership of the session's lifecycle the moment it's handed one.

The _isRealSession check (lines 216–219) exists specifically so widget tests can hand TableScreen a plain, hand-built GameSession stub with an already-dealt view and skip the dealing flourish animation entirely — a real accommodation for testability, called out directly in the doc comment above it.

The build skeleton (lines 595–650, abbreviated):

Read the showTable line closely — it's the exact place module 5's NetworkSession.isResuming earns its existence: a session that's mid-reconnect (resuming) with a view still in hand keeps showing the last-known table instead of blanking to a loading spinner, "so the table is never swapped for a blank page," per the comment right above it. The outer Listener wrapping literally everything exists so any touch on the table — not just a card tap — counts as "the player is still here" and can cancel autoplay (module 5's wakeUp()), which is why it's HitTestBehavior.translucent: it must see every touch without stealing any of them from the widgets underneath.

Improvement note
The file's size itself is the improvement note: at 3,209 lines, table_screen.dart mixes screen-level orchestration (session lifecycle, build skeleton) with a large number of private presentation widgets that don't need to live in the same file (_AutoplayBanner, _ThrowFlight, _DealOverlay, _ConnectionState, LobbyPanel and its sub-widgets, and more — all defined in this one file per the class listing surveyed for this module). Splitting the self-contained overlay/animation widgets into their own files under ui/widgets/ (as felt_table.dart, seat_view.dart etc. already are) would make each piece independently testable and reviewable without touching a 3,000+ line file, at the cost of a one-time, mechanically risky refactor across a file this central. See the Roadmap (module 20) for this listed as a maintainability item.

Checkpoint

Why does startTable construct the concrete GameSession subtype (LocalSession, RemoteSession...) in home_screen.dart rather than inside TableScreen itself?
So TableScreen never needs to know which mode it's rendering — it only ever depends on the abstract GameSession contract from module 5. Keeping construction at the call site is what makes one screen able to render every mode identically.
PlayingCardView computes its proportions from its own width parameter rather than calling Metrics.s() internally. Why does that make it more reusable, not less?
It decouples the widget from any particular scale — hand it width 54 for a hand card or 44 for a table card and every internal measurement follows proportionally, with the caller (not this widget) deciding the actual size via Metrics. If it called Metrics.s() internally, it would be baking in one specific design-pixel reference rather than staying a size-agnostic ratio.
Why does dragging a card in HandFan commit the throw the instant the drag crosses a distance threshold, instead of waiting for the finger to lift?
Because a decisive, fast flick crosses the threshold well before the finger actually lifts, and waiting for the lift anyway would make a confident gesture feel laggy. Committing at the threshold is what makes a quick flick feel instantly responsive, at the cost of needing an explicit _thrown guard so no later drag callback can act on a card already on its way out.
TableScreen is one shared screen for every game mode, but it still contains a few explicit is RemoteSession/is NetworkSession checks. Does that contradict the session-abstraction decision from module 5?
Not quite — it's the same narrow exception module 5's NetworkSession subclass already anticipated: capability that only networked sessions have (reconnect state, resume tokens) genuinely doesn't exist on LocalSession, so a type check to reach it is the honest cost of that design, used sparingly and only where that capability is actually needed — not scattered as a general per-mode branching pattern through the rest of the screen.
