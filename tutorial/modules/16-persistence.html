Persistence (Postgres & Redis)

Two optional, independently-degradable stores: Postgres for game history and accounts, Redis for telling a multi-node deployment which node owns which table. "Optional" and "independently" are the load-bearing words — this module is about how the codebase makes a database an enrichment rather than a dependency, all the way down to the interface shape.

Where this fits

db/store.go

backend/internal/db/store.go
Purpose

Every other package that needs to persist something — the room actors, the REST handlers — has to talk to something called a store, without knowing or caring whether it's really Postgres. This file is the entire contract: the Store interface, every type that crosses it, and a working implementation of the interface that persists nothing at all.

Decision

A "Nop" store that implements the whole interface by doing nothing, rather than a nilable *Store every caller has to check. 

type Nop struct{}
var _ Store = Nop{}
func (Nop) Enabled() bool { return false }
func (Nop) RecordGame(context.Context, GameRecord) (string, bool, error) {
	return "", false, ErrDisabled
}
...

The package comment: "Persistence is optional. Nop satisfies the whole interface by doing nothing and reporting ErrDisabled, which is a supported deployment rather than a failure." The alternative — a Store that's nil when no DATABASE_URL is set — would push a nil-check onto every single call site in room and httpapi that might touch persistence. Instead, every caller can call store.RecordGame(...) unconditionally, get back ErrDisabled, and treat that specific, named error as "nothing to do here" — the classic Null Object pattern, applied at the package boundary so the rest of the server never has to know persistence might not exist.

Every error the store can return is one of four named sentinels — never a raw driver error. ErrDisabled, ErrNotFound, ErrConflict, ErrNotGuest. A caller in room or httpapi can errors.Is against these without knowing or caring that the real implementation is pgx — the same "nothing outside this package knows the backing store is Postgres" isolation the package comment states directly, mirroring module 11's protocol package staying free of an engine import: a narrow, deliberately poor interface between two things that should be free to change independently.

Explanation

The interface itself groups into exactly three concerns the package comment names: accounts (ResolveIdentity, LinkIdentity, RestoreAccount, MergeGuest/MergeUsers — the guest-to-signed-in-account lifecycle docs/PERSISTENCE.md describes), recording (RecordGame, covered in depth below), and reading (History, Game, Stats, plus an admin-scoped AdminGames/AdminGame pair with no per-user filter — "that is what makes it admin-only," per its own comment, foreshadowing module 17's separate authorization check on top). Notice Stats is deliberately counters only — GamesPlayed, TotalScore, and so on — with the comment on the Stats struct explaining why: "Derived figures — win rate, average score, bid accuracy — are computed on read rather than stored, so the two numbers can never drift apart." Storing a computed average alongside its inputs is a classic way to end up with numbers that silently disagree after enough updates; computing it fresh from the stored counters every time a profile screen asks removes the possibility entirely.

Try it yourself — AbandonedAccount and RestoreResult exist for a specific, real product scenario. Given RestoreAccount's doc comment describes "bring my saved account to a new phone," what happens to the account that new phone already had?
Show solution 
// RestoreAccount moves the caller's device identity onto targetID ...
// The replaced install is deleted outright when it has no games; when it
// has games they are kept and named in the result so the caller can offer a
// merge-or-discard decision.
RestoreAccount(ctx context.Context, currentID, targetID string) (RestoreResult, error)

A fresh install already has its own guest account (created the first time it ever connected) the moment someone chooses "restore my old account" on it. If that fresh-install guest account never actually played anything, it's simply deleted outright — there's nothing worth keeping. But if the player had already played a few solo games on the new phone before restoring, those games are real and belong to somebody (per module 13's recording logic, they're attributed to that guest account's userID) — deleting them would silently erase games that were actually played. Instead, that account is kept, orphaned (all its sign-in methods just moved to the restored account), and handed back as an AbandonedAccount so the client can ask "you also have 3 games on this phone from before — keep them or discard them?" — the MergeGuest / DeleteAbandoned methods are that decision, made concrete.

Improvement note
No weakness found in this file. Worth noting explicitly: unlike most of module 13's room package, this package is genuinely well tested — db/postgres_test.go runs to 1,223 lines, more than the combined implementation files it exercises. Between this and module 14's ws package, the pattern across this codebase is that the edges dealing with an external system (a socket, a database) tend to be tested carefully, while the pure in-process orchestration layer (the room actor) is the outlier that isn't.

db/postgres.go

backend/internal/db/postgres.go
Purpose

The real Store — connects a pgx pool, turns driver-specific errors into the sentinel vocabulary store.go defines, and provides the two small utilities (transaction helper, opaque pagination cursor) every read/write method in this package builds on.

Decision

Startup does a real round trip and runs migrations synchronously, rather than opening a lazy pool. The comment on OpenPostgres: "a caller running with DATABASE_REQUIRED=true wants to know at boot that the credentials work, not on the first game that finishes." This directly implements module 11's DatabaseRequired config flag: failing fast at startup, with a clear error, beats a server that appears healthy for hours and only reveals a bad connection string the moment the first game tries to save. Running migrations in the same call, rather than a separate migration binary or step in the deploy pipeline, is the same reasoning applied to schema drift: "one code path, no separate migration binary to keep in step with the deploy, and by the time this returns the schema matches the binary."

Driver errors are translated to sentinels and never leaked past this file — the raw error is only ever logged, never returned. 

func (p *Postgres) fail(op string, err error) error {
	...
	var pgErr *pgconn.PgError
	if errors.As(err, &pgErr) {
		p.log.Error("database error", "op", op, "code", pgErr.Code,
			"constraint", pgErr.ConstraintName, "msg", pgErr.Message)
		switch pgErr.Code {
		case pgerrUniqueViolation, pgerrExclusionViolation:
			return ErrConflict
		...
		}
		return fmt.Errorf("db: %s failed", op)
	}
	...
}

The comment names the two reasons at once: "a constraint name or a column list leaking into a client response is both a bad API and a small information disclosure." A Postgres constraint name can reveal schema internals (table and column names, business rules encoded as constraints) to whatever's on the other end of an HTTP response — this function is the one seam where that detail gets logged, with full context, and then deliberately thrown away before it can travel any further outward.

Pagination is keyset (cursor-based), not offset-based. 

type cursor struct {
	FinishedAt time.Time `json:"t"`
	GameID     string    `json:"g"`
}

The comment: "Offsets are not used anywhere, because a game finishing while somebody scrolls would shift every subsequent page by one and silently hide a row." OFFSET 20 LIMIT 20 is simpler to implement, but its correctness silently depends on the underlying result set not changing between page requests — exactly the assumption a live, constantly-growing game history violates. A cursor built from the last row actually seen ((finished_at, id), encoded opaquely so "a client cannot construct one by hand and come to depend on its shape") keeps every page consistent regardless of what's inserted in between requests.

Explanation
func (p *Postgres) inTx(ctx context.Context, op string, fn func(tx pgx.Tx) error) error {
	tx, err := p.pool.Begin(ctx)
	...
	defer func() {
		_ = tx.Rollback(context.WithoutCancel(ctx))
	}()
	if err := fn(tx); err != nil { return err }
	if err := tx.Commit(ctx); err != nil { return p.fail(op, err) }
	return nil
}

"Rollback after a successful commit is a documented no-op" — this comment is what makes the unconditional deferred rollback safe: there's no need for a "did this already commit" flag, because calling Rollback on an already-committed transaction is simply a harmless no-op by pgx's own contract. context.WithoutCancel(ctx) on the rollback is a small but real detail: if the caller's context was cancelled (a client disconnected mid-request), the rollback still has to actually run to release the connection back to the pool — using the (now-cancelled) original context here would make the rollback itself fail to execute, leaking the connection until the pool eventually reaps it.

Improvement note
cfg.MaxConnIdleTime (30 minutes) and cfg.MaxConnLifetime (1 hour) are hardcoded constants in this file, while DBMaxConns — the pool's size — is exposed as an environment variable in module 11's config. That's an inconsistent surface: an operator tuning this server for a specific cloud provider's connection-recycling behavior (many managed Postgres offerings silently drop idle connections on their own schedule, which is exactly what the comment on MaxConnIdleTime is defending against) can adjust how many connections the pool holds, but not how long it holds them idle or alive, without a code change and a rebuild. Given the values already exist as named constants in one place, exposing them as two more envDuration-backed config fields (module 11) would be a small, low-risk change.

db/migrate.go

backend/internal/db/migrate.go
Purpose

The schema embedded in the server binary and the schema actually sitting in Postgres have to match before any query runs — this file is what brings the database up to date, automatically, every time the server starts.

Decision

Forward-only migrations. No down migrations, ever, by design. The comment states the reasoning about as plainly as a comment in this codebase gets: "There are no down migrations, because a down migration is a script nobody has ever run against production data and it is reached only in the moment you can least afford to find that out. A mistake is fixed by a new numbered file." This is a real, opinionated position with a real cost — a bad migration can't be automatically reverted, only corrected forward — traded deliberately against the alternative's own real cost: an untested rollback script, written once and never exercised until the exact moment of an incident, is arguably more likely to make things worse than better.

A session-scoped Postgres advisory lock serializes migrations across every replica that starts at once. The comment: "Two pods starting together would otherwise both see an empty schema_migrations and both try to CREATE TABLE users." Rather than requiring an external coordination mechanism (a leader-election step in the deploy pipeline, a separate migration job that must complete before any server pod starts), Postgres's own pg_advisory_lock — a lock that lives entirely inside the database, held for the duration of one connection — is used as the coordination point: whichever replica gets there first runs the migrations; every other replica blocks on the same lock, then finds nothing left to do and moves on.

Explanation
func migrate(ctx context.Context, pool *pgxpool.Pool, log *slog.Logger) error {
	all, err := loadMigrations()
	...
	conn, err := pool.Acquire(ctx)
	...
	defer conn.Release()
	conn.Exec(ctx, `SELECT pg_advisory_lock($1)`, migrateLockKey)
	defer conn.Exec(context.WithoutCancel(ctx), `SELECT pg_advisory_unlock($1)`, migrateLockKey)
	...
	applied, err := appliedVersions(ctx, conn.Conn())
	for _, m := range all {
		if _, done := applied[m.version]; done { continue }
		if err := applyOne(ctx, conn.Conn(), m); err != nil { return err }
	}
	return nil
}

The lock is taken on one pinned connection (session-scoped locks live on a specific connection, not the pool as a whole) and explicitly released via a deferred call, rather than just letting the connection close and the lock drop implicitly — the comment explains why: "keeps the lock out of pg_locks for the life of the pool, which makes a genuinely stuck migration easy to spot" for an operator inspecting the database live during an incident. 

func applyOne(ctx context.Context, conn *pgx.Conn, m migration) error {
	tx, err := conn.Begin(ctx)
	...
	if _, err := tx.Exec(ctx, m.sql); err != nil { return ... }
	if _, err := tx.Exec(ctx,
		`INSERT INTO schema_migrations (version, name) VALUES ($1, $2)`,
		m.version, m.name); err != nil { return ... }
	return tx.Commit(ctx)
}

Each numbered .sql file's DDL and its ledger entry commit together, in the same transaction — "recording the version in the same transaction as the DDL is what makes a crash mid-run safe: either both happened or neither did." A crash between running the SQL and recording it would otherwise leave the database schema changed but the ledger unaware of it, and the next startup would try to re-apply an already-applied migration.

Improvement note
No weakness found. The forward-only design is a deliberate, well-justified trade-off rather than a gap (see Decision above), and the transactional apply-plus-record pattern closes the obvious crash-consistency hole a naive implementation would have.

Idempotent writes: db/postgres_games.go

backend/internal/db/postgres_games.go
Purpose

This is where module 9's GameUploader (a Dart client retrying a failed upload with the same clientGameId) and module 13's Recorder (a Go room actor submitting a server-played game) both eventually land: the single function that writes a finished game, its seats, its per-hand scoreboard, and every statistic row it affects, and guarantees a retried upload never creates a second copy of the same game.

Decision

ON CONFLICT ... DO NOTHING, not DO UPDATE — the opposite choice from the one this same package's identity-resolution code makes for a structurally similar race. The comment draws the contrast explicitly: "There, the point was to learn who won a race. Here the point is that a retry must write nothing at all." A repeat upload of the same client_game_id isn't a race to be resolved — it's the exact same game, already fully written, being described a second time by a client that never saw the first response. DO NOTHING combined with a partial unique index (WHERE client_game_id IS NOT NULL, so the huge majority of server-played games with no client id never compete for this index at all) is what makes the whole operation a genuine no-op on a retry: no updated finished_at, no re-run statistics, nothing.

Statistics are recomputed for a scope only on the branch that actually inserted a new game — never on the duplicate branch. 

if errors.Is(err, pgx.ErrNoRows) {
	duplicate = true
	// ... fetch the existing gameID, return early
	return nil
}
...
for _, seat := range rec.Seats {
	...
	if err := p.applyStats(ctx, tx, d); err != nil { return err }
}

The comment is precise about why no separate idempotency key is needed for the counters themselves: "the games table already carries one, and this transaction is the only thing that can reach past it." Because the statistics update only ever runs in the same transaction as a successful INSERT, and that insert can only succeed once per client_game_id, the counters inherit exactly-once semantics from the games table's own unique index — there's nothing to duplicate-check separately.

Explanation
err := p.inTx(ctx, "record game", func(tx pgx.Tx) error {
	err := tx.QueryRow(ctx, insertGameSQL, ...).Scan(&gameID)
	if errors.Is(err, pgx.ErrNoRows) {
		duplicate = true
		tx.QueryRow(ctx, `SELECT id FROM games WHERE client_game_id = $1`, ...).Scan(&gameID)
		return nil
	}
	if err != nil { return p.fail("record game", err) }
	if err := p.insertChildren(ctx, tx, gameID, rec); err != nil { return err }
	for _, seat := range rec.Seats { ... applyStats ... }
	return nil
})

One call, one transaction, covering the game row, every seat, every hand, optionally every trick, and every affected statistics row (both the mode-specific scope and the across-everything ScopeAll scope, per seat). The comment on the function itself makes the actual correctness argument: "'One transaction' is the entire correctness argument. A game whose seats committed but whose statistics did not would be permanently wrong, and no amount of retrying at a higher level could tell that from a game that was never written." Either everything lands, or the whole transaction rolls back and the caller (module 13's Recorder, which itself retries once — module 13) is free to try again from a clean slate.

Try it yourself — insertChildren uses tx.SendBatch for the seats, hands and tricks instead of one INSERT statement per row in a loop. What does that actually save?
Show solution 
// One batch, so a game costs one network round trip below the game row
// rather than one per hand.
batch := &pgx.Batch{}
for _, s := range rec.Seats { batch.Queue(`INSERT INTO game_seats ...`, ...) }
for _, h := range rec.Hands { batch.Queue(`INSERT INTO game_hands ...`, ...) }
...
results := tx.SendBatch(ctx, batch)

A five-hand game writes 4 seat rows plus 20 hand rows (4 seats × 5 hands) — 24 separate INSERT statements. Issued one at a time, each pays a full network round trip to the database before the next can be sent. pgx.Batch pipelines all of them onto the wire together and reads back all the results together — the database still executes 24 inserts, but the client only pays the network latency once instead of 24 times, which matters far more than it sounds for a server recording hundreds of games under load.

Improvement note
rec.ClientGameID is never validated for shape or length at this layer — validateRecord in this same file checks Mode, Source, and that seats are well-formed, but never touches ClientGameID. Module 17's REST upload handler (httpapi/games.go's buildGameRecord) does enforce a 128-character cap before a client-uploaded game ever reaches this function — so the everyday path is covered. But that check lives entirely one layer up, in a different package, and is specific to the one HTTP handler that happens to call it; RecordGame itself, and this file's validateRecord, have no independent defense of their own. The schema column itself (migrations/0001_init.sql: client_game_id text) has no length constraint either, so this is entirely one caller's discipline away from being unenforced — any future or internal caller of db.Store.RecordGame that isn't httpapi's upload handler (module 13's Recorder never sets this field at all, so it's unaffected in practice) would insert an arbitrarily large or malformed value with nothing in this package stopping it. A defense-in-depth check here — the same length cap, enforced at the boundary that actually owns the uniqueness guarantee — would remove the reliance on every future caller remembering to validate upstream.

store/registry.go

backend/internal/store/registry.go
Purpose

When more than one server node is running, a private table's room code has to resolve to exactly one of them — otherwise two players typing the same code could land on two different nodes and each silently start their own empty table. This file is the shared directory that answers "which node owns this room," backed by Redis, with a single-node fallback that needs it not to exist at all.

Decision

Two implementations behind one Registry interface — a real Redis-backed one and Memory, which does nothing — mirroring exactly the Store/Nop split in db/store.go. Memory.Owner always returns "not elsewhere," so a single-node deployment behaves as if every room it knows about is unquestionably its own — because it is. The same pattern applied twice in one codebase (persistence, and now cross-node coordination) for the identical reason: let the rest of the server depend on an interface unconditionally, with the "nothing configured" case costing nothing extra to call into.

The registry is explicitly advisory, never authoritative — a Redis outage degrades to single-node behavior rather than blocking play. The type's own comment: "a lookup failure or a Redis outage degrades the server to single-node behaviour instead of taking it down. Players might end up on the wrong node during an outage, which costs them a rejoin — far better than a server that refuses to seat anybody." This is the same "database problems must never stop a game" philosophy from module 11's config and module 13's Recorder, applied to a completely different subsystem: Redis being unreachable is treated as "assume this room is local" rather than as a reason to fail the join outright.

Claiming uses SETNX (first writer wins); releasing uses a Lua script that only deletes a key if it still holds this node's own value. 

var releaseScript = redis.NewScript(`
if redis.call("GET", KEYS[1]) == ARGV[1] then
	return redis.call("DEL", KEYS[1])
end
return 0
`)

The comment: "so a node that paused long enough to lose its claim cannot delete its successor's." This defends against a specific, real distributed- systems failure mode: if node A pauses (a long garbage-collection stop, a frozen container) past ownerTTL, the key expires and a different node B might legitimately claim the same room in the meantime. If node A later wakes up and blindly runs DEL on that key, it would delete node B's now-legitimate claim — the compare-and-delete script prevents exactly that by checking the stored value still matches node A's own endpoint before deleting anything.

Explanation
func (r *Redis) heartbeat() {
	ticker := time.NewTicker(heartbeatPeriod) // 20s
	for {
		select {
		case <-r.stop: return
		case <-ticker.C:
			... pipe := r.client.Pipeline()
			for _, room := range rooms { pipe.Expire(ctx, keyPrefix+room, ownerTTL) } // 60s
			pipe.Exec(ctx)
		}
	}
}

Every claimed room's TTL is refreshed every 20 seconds against a 60-second expiry — comfortably inside it, per the comment: "It has to outlast a stop-the-world pause comfortably, or a healthy node would lose its rooms." A three-times safety margin means a single missed heartbeat cycle (a transient network blip) doesn't cost a claim; only a sustained outage does. Refreshing every currently-owned room in one pipelined batch, rather than one round trip per room, is the same batching principle postgres_games.go's SendBatch uses, applied to Redis instead of Postgres.

Improvement note
Two related, real risks from the timing itself, both narrow but worth naming. First: Owner() is called synchronously on the private and quickplay-resume join paths (module 14's server.go), each call bounded by a 500ms timeout — under a degraded but still responding Redis (not a clean outage, which fails fast and is handled gracefully per the Decision above), every single private join could pay up to half a second of added latency before falling through. Second, and narrower still: if Redis is unreachable for longer than ownerTTL (60 seconds) while a node is still up and still genuinely hosting a table, that table's claim silently expires from Redis's point of view even though nothing is actually wrong with the node holding it — a second node could then successfully claim the same room code during that window if a player happened to open a private table under the identical 4-character code elsewhere, briefly recreating the exact double-table problem this registry exists to prevent, for the remainder of the outage. Both are edge cases requiring a genuinely unhealthy-but-not-fully-down Redis, but neither is purely theoretical for a system explicitly designed to keep running through exactly that condition.

Checkpoint

Why does db.Nop implement the whole Store interface instead of the rest of the server checking for a nil store?
It lets every caller invoke store methods unconditionally and branch on the named ErrDisabled sentinel, instead of scattering nil-checks across every call site in the room and httpapi packages. It's the same Null Object pattern applied wherever this codebase makes a dependency optional.
Why does RecordGame use ON CONFLICT DO NOTHING for a duplicate game upload, while identity resolution elsewhere in the same package reportedly uses DO UPDATE for a similar race?
The two situations aren't actually the same kind of race. A duplicate game upload is the identical game being described twice — the correct answer is to write nothing at all a second time. Resolving an identity race is about figuring out which of two concurrent attempts actually won, which needs to read back a value, not silently ignore the conflict.
Why does the room-ownership registry treat a Redis outage as "assume this room is local" instead of refusing the join?
Because the whole codebase treats persistence and coordination as enrichments, never preconditions — a database or registry problem should cost accuracy (a player possibly landing on the wrong node, needing a rejoin) rather than availability (refusing to seat anyone at all). The same principle governs module 11's config, module 13's Recorder, and this file.
Why does the release operation use a compare-and-delete Lua script instead of a plain DEL?
A node that paused long enough for its claim to expire, and only woke up later, could otherwise delete a different node's legitimate, newer claim on the same room with a plain DEL. The script only deletes the key if it still holds this specific node's own value, so a stale node can never clobber whoever claimed the room after it.
