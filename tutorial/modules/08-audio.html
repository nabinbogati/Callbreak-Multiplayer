Audio

A card game with no sound reads as broken the moment you play it. This module builds audio/audio_controller.dart — background music plus one-shot sound effects (card thrown, trick collected, trump played, the turn clock's tick), triggered from the table screen you built in module 6.

audio/audio_controller.dart

frontend/lib/audio/audio_controller.dart
Purpose

Without this file, every place that wants to make a sound (a card landing, a trick won) would have to manage its own audio player and its own error handling for "what if the audio plugin isn't available on this platform." This file centralises both: one process-wide controller, and one guarantee, stated in its own doc comment — "Every underlying player call is guarded so a missing or failing audio plugin can never crash the game."

Decision

A process-wide singleton (static AudioController? instance), initialised once from main.dart, instead of an InheritedWidget-scoped instance like AppSettings. Sound has no meaningful "scope" the way settings do — there is exactly one soundtrack for the whole app, so a global reachable from anywhere (AudioController.instance?.playShot()) is simpler than threading it through the widget tree. The cost is the usual one for a singleton: nothing in the type system stops code from calling AudioController.instance before init() has run — every call site has to null-check it, which you can see it already does (AudioController.instance?.stopDeal() in module 6's table_screen.dart).

Sound is triggered imperatively by whoever has the relevant context (table_screen.dart's event listener, module 6), not by AudioController itself subscribing to the game's event stream. Some of that context isn't available to AudioController at all — deciding whether a play deserves the "trump" sound needs to know the trick's led suit, which lives in UI-adjacent state, not in a bare GameEvent. Exposing a small imperative API (playShot(), playTrump(), startTick()...) keeps this file from needing to understand game rules at all — the cost is that every place sound should play has to remember to call it; nothing enforces that a new event type gets a matching sound.

Separate, dedicated AudioPlayer instances for looping sounds (_musicPlayer, _tickPlayer, _dealPlayer), but a brand-new, disposable one per call for one-shot sounds (_oneShot). A loop needs a persistent player to start, stop, and resume; a one-shot card sound needs to be able to overlap itself — two cards played in quick succession should both make a sound, which a single shared, reused player couldn't do without cutting the first one off. The cost is real object churn: every single card play constructs and disposes a whole new AudioPlayer.

Explanation

The graceful-degradation pattern, everywhere in this file:

Future<void> _syncMusic() async {
  try {
    if (_settings.musicEnabled) {
      final player = _musicPlayer ??= AudioPlayer()..setReleaseMode(ReleaseMode.loop);
      await player.play(_bgMusic, volume: _musicVolume);
    } else {
      await _musicPlayer?.stop();
    }
  } catch (_) {
    // Audio unavailable (tests, headless platforms) — stay silent.
  }
}

This exact shape — try the real audio call, catch anything, do nothing — repeats in nearly every method in this file (_pauseMusic, _startDeal, _startTick, _oneShot). It's the same principle module 7's IdentityStore applied to storage, now applied to audio: a feature that enhances the experience must never be allowed to break the experience it's enhancing. A test running headless, or a platform with no audio output, plays the whole game in total, correct silence instead of crashing.

App lifecycle: pausing music when the app leaves the screen (lines 82–101):

void didChangeAppLifecycleState(AppLifecycleState state) {
  switch (state) {
    case AppLifecycleState.hidden:
    case AppLifecycleState.paused:
    case AppLifecycleState.detached:
      if (_musicPausedForLifecycle) return;
      _musicPausedForLifecycle = true;
      unawaited(_pauseMusic());
    case AppLifecycleState.resumed:
      if (!_musicPausedForLifecycle) return;
      _musicPausedForLifecycle = false;
      unawaited(_resumeMusic());
    case AppLifecycleState.inactive:
      break;
  }
}

_musicPausedForLifecycle is doing real work here — it distinguishes "paused because the app went to the background" from "paused because the player turned music off in settings." Without that flag, coming back to the foreground would blindly try to resume music even for a player who had it turned off, per the comment: "Music the player never enabled is never touched."

/// The deal card sound is a short single swish; looped at its natural speed
/// it lags a 55ms-per-card deal, so it is played faster to keep time.
static const _dealRate = 3.0;

Future<void> _startDeal() async {
  if (!_settings.sfxEnabled) return;
  try {
    final player = _dealPlayer ??= AudioPlayer()..setReleaseMode(ReleaseMode.loop);
    await player.setPlaybackRate(_dealRate);
    await player.play(_deal, volume: _dealVolume, mode: PlayerMode.lowLatency);
  } catch (_) { ... }
}

Thirteen cards land roughly every 55ms during the dealing flourish (module 6's _DealOverlay) — much faster than one playback of the swish sample takes to finish. Looping it at normal speed would visibly lag behind the cards actually landing on screen; playing it 3× faster keeps the sound in rhythm with what the eye is watching, a small but real audio/visual sync detail.

Improvement note
Every catch (_) in this file (e.g. lines 77–79, 106–108, 141–144, 186–189, 207–213) swallows any exception identically — a genuinely unavailable audio plugin looks exactly the same as a typo'd asset path or a real bug in this code, with zero logging even in debug builds. A developer who breaks something here (renames an asset, say) gets total silence with no signal that anything is wrong, rather than a caught-but-visible warning. A minimal fix: log via debugPrint inside the catch blocks (a no-op in release builds) so a real bug is at least visible during development without changing the "never crash" guarantee for production.

Checkpoint

Why is AudioController a process-wide singleton instead of scoped through the widget tree the way AppSettings is?
There's exactly one soundtrack for the whole app — no widget needs a differently-scoped audio controller the way different screens might want different settings. A reachable-from-anywhere global is simpler for something with genuinely global scope, at the cost of every call site needing a null-check for the window before init() has run.
Why does _oneShot create a brand-new AudioPlayer for every single sound, disposing it right after, instead of reusing one player for all one-shot sounds?
So overlapping sounds (two cards played in quick succession, a trump sound alongside a card shot) can each play fully without one cutting the other off. A single reused player could only ever play one sound at a time.
What real failure does the every-call-site try/catch-and-silently-continue pattern in this file protect against, and what does it cost when something actually goes wrong here that isn't "audio unavailable"?
It protects the whole game from crashing over a missing plugin, a headless test environment, or unsupported platform audio — sound is treated as enhancement, never a dependency. The cost is that a real bug in this file (bad asset path, wrong parameters) fails identically to "no audio hardware" — silently, with no log to tell the two apart during development.
