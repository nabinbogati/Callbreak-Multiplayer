Build It Yourself

Eighteen modules read the real source and explained why every file exists the way it does. This one asks you to close the tab and rebuild it — or a scoped, honest slice of it — from memory and first principles. No code is given here. What follows is a checklist in build order, and a collapsible hint for each item that nudges you toward the decision, not the implementation.

How to use this module

Pick one track below, not all three. Rebuilding the entire project solo is a multi-week undertaking even having just read how it works — that's not a failure of this course, it's an honest reflection of how much real software this actually is. A track that gets you a working, playable slice end-to-end teaches you more than an abandoned attempt at everything.

  • Track A — Solo engine, no network (modules 1–3). A pure Dart (or any language) card engine, playable against three bots in a terminal or the simplest UI you can manage. No Flutter widgets required if you'd rather prove the engine works first.
  • Track B — Full offline Flutter app (modules 1–8). A real, playable app: engine, bot, UI, settings, audio. No networking at all — this is exactly what LocalSession already proves is a complete, standalone product.
  • Track C — Minimal Go server (modules 11–15). Skip the Flutter client entirely. Build a Go server that accepts a WebSocket connection, lets a client join a room, deals a hand, and enforces turns — proven with a hand-written test client or even websocat, not a real app.

Whichever track, hold yourself to the same standard this course modeled: before you write a non-trivial function, ask why this approach and not an obvious alternative — that question, asked honestly, is most of what separates code that works from code you actually understand.

Track A checklist — the engine (modules 1–3)

  • HintModule 1 covers two real design decisions here: how equality/identity works for a card (does your language give you this for free, or do you need to define it?), and why the id format matters even before you have any networking at all — think about debuggability and logging, not just wire format.
  • HintThere are exactly three cases in Call Break's follow-suit rule, and the trickiest one isn't "must follow suit" — it's what happens when a player already-trumped a trick and a later player is void in the led suit too. Get the "heading" rule (must beat the best card of the led suit if you can) right before worrying about trump.
  • HintModule 1's real answer to the second part is a specific, reusable trick: construct a hypothetical trick with the candidate card appended, using a sentinel value for "seat," and ask your real trick-winner function who it thinks won.
  • HintResist the urge to make this perfect. The real one weighs top trumps heavily, discounts an unprotected high card in a short suit, and separately estimates "ruffing value" from voids and singletons — but any consistent heuristic that a bot can use to bid reasonably is enough for this checklist item.
  • HintThe single most important design question here: what does your mutation method do when the move is illegal or out of turn? Module 2's answer — return a signal, change nothing — is deliberately boring. Resist building rollback logic; make illegal moves impossible to have partially applied in the first place.
  • HintBefore you write this function, ask yourself: is there any other path by which a caller could reach another seat's cards? If your game object exposes its raw hand array publicly, you have not actually built this boundary — you've built a suggestion.
  • HintThe real bot never breaks a legal-move guarantee even at its noisiest setting — noise perturbs which legal move it picks, never whether the move is legal. Keep that invariant no matter how you implement difficulty.

Track B checklist — the offline app (modules 4–8)

Everything in Track A, plus:

  • HintModule 5's real test for whether this abstraction is right: could you write the UI against it before the local implementation exists at all, using a fake? If the interface leaks anything specific to "runs on this device," it's not yet abstract enough.
  • HintThe real one uses one self-cancelling, self-rescheduling timer, not a fixed tick. Every state change re-decides what the next scheduled action should be, and cancels whatever was previously scheduled first.
  • HintThe genuinely hard part isn't the visuals, it's the gesture-state machine: what happens if a drag starts, then the underlying legal-moves set changes mid-drag (the player bid, the trick cleared)? Decide on that behavior deliberately, don't let it fall out of whatever code happens to run.
  • HintModule 7's real lesson here isn't the storage mechanism, it's the failure mode: what does your app do the very first time it runs, with nothing stored yet? And what does it do if the storage read itself throws? Neither should be a crash.
  • HintDecide your failure policy for "the audio plugin isn't available on this platform/simulator" before you write a single play() call, and apply it consistently everywhere rather than an ad hoc try/catch per call site.

Track C checklist — a minimal Go server (modules 11–15)

  • HintPick your one unsafe-to-default setting deliberately (module 11's is the token-signing secret) — the exercise here is drawing that line honestly, not defaulting everything or nothing.
  • HintDecide, and write down for yourself, what "absent" versus "present but zero" means for at least one field (a bid of 0 versus no bid). If your language's JSON decoding can't distinguish them by default, that's the actual design problem this item is testing.
  • HintThe real test of whether you've actually built this: could two goroutines (or threads, or async tasks) ever call a mutating method on the same table's state at the same time in your design? If the honest answer is "no, because there's only ever one owner," you've built it. If it's "no, because I remembered to lock," you've built something else.
  • HintDecide what happens to a frame that arrives before a join, and a frame that arrives after the socket has been told to close but before the socket has actually closed. Both are real states your handler will be in.
  • HintUse a constant-time comparison for the signature check, and write yourself a one-sentence justification for why — if you can't state the actual attack it prevents, look up timing side- channels before moving on.

When you're stuck

Getting stuck on a specific decision — not a syntax error, an actual "I don't know which way to go here" — is the point of this module, not a sign you're doing it wrong. Before re-reading the matching module in this course, try writing down, in one sentence, the trade-off you're actually weighing. Often the act of naming both sides is enough to decide. If it isn't, go back and reread that module's Decision section specifically — not the code, the reasoning — and see whether the real project's trade-off matches the one you'd already identified.
