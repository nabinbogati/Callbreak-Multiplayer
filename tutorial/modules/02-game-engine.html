Game State Machine

card.dart defines what a card is; rules.dart defines what's legal. Neither knows what phase the game is in, whose turn it is, or what's been scored. That's frontend/lib/engine/game.dart — the 594-line file that turns "rules" into an actual playable, turn-by-turn game.

Where this fits

Prerequisite terms

sealed class, Stream (used by the layer above this one, in module 5) — see the Glossary.

Phase & player identity

frontend/lib/engine/game.dart:11–73
Purpose

A game isn't always in the same mode — you can't accept a card play during bidding, or a bid once play has started. GamePhase makes "what kind of input is even valid right now" a single checkable value instead of an implicit tangle of booleans. PlayerInfo answers the parallel question of who is in each of the four seats — human or bot, and (critical for the networked modes built later) whether they're currently connected or being played by the server on their behalf.

Decision

An explicit five-value enum (lobby, bidding, playing, handOver, gameOver) instead of inferring phase from other state (e.g. "if every seat has bid, we must be in the playing phase"). The enum is one source of truth that every guard clause in this file checks first (if (phase != GamePhase.bidding...) return false;), rather than each method re-deriving "are we in bidding" from bids/tricks state and risking disagreement. The cost is one more field to keep in sync with the state transitions below — miss updating phase in a new code path and every guard silently breaks.

Explanation
enum GamePhase { lobby, bidding, playing, handOver, gameOver }
enum PlayerKind { human, bot }
enum BotDifficulty { easy, normal, hard }

class PlayerInfo {
  const PlayerInfo({
    required this.seat,
    required this.name,
    required this.kind,
    this.difficulty = BotDifficulty.normal,
    this.connected = true,
    this.autoplay = false,
  });
  ...
  /// True while the server is playing this seat because its human stopped
  /// responding. The player is still here and still owns the seat — they take
  /// it back the moment they touch the table.
  final bool autoplay;
  ...
}

Five phases map to five stages of one hand's lifecycle: nobody's arrived yet (lobby) → everyone bids in turn (bidding) → cards are played (playing) → the hand is scored and the table waits before the next deal (handOver) → the whole game (all totalHands hands) is finished (gameOver). Note connected and autoplay on PlayerInfo are both meaningless in this module — a solo offline game never has a seat go offline — but the field exists here, in the shared model, because the networked session (module 5, 9) needs to represent it and this is the one PlayerInfo both use.

Improvement note
GamePhase is a plain enum, not a sealed class hierarchy carrying phase-specific data — so a field like bids exists on CallBreakGame at all times even during lobby, when it's meaningless (all null). Dart's type system can't stop code from reading it too early; only the runtime guard clauses in each method do. A phase-tagged sealed state (the way GameEvent below is modelled) would make an invalid read a compile error instead of a guarded no-op — worth it only if this class grows more phase-specific fields than it has today.

GameView — the redacted read model

frontend/lib/engine/game.dart:111–294
Purpose

Four seats are playing one game, but no seat should ever be able to see another seat's cards. If the UI simply held a reference to the whole CallBreakGame and was trusted to only render "your own" cards, that trust could be broken by any future line of UI code — a debug print, a copy-paste from another seat's widget. GameView makes that structurally impossible instead: it is built once per seat and simply does not contain the other three hands, only how many cards each holds.

Decision

A dedicated, JSON-serializable snapshot type built fresh per seat, versus handing the UI the live CallBreakGame plus a "which seat am I" parameter. The redacted-by-construction approach means "can this UI leak another player's hand" is answered by reading one place — viewFor at the bottom of this file — instead of auditing every widget that might render a hand. The cost is real: GameView duplicates most of CallBreakGame's fields, so the two must be kept in sync by hand whenever a new piece of state is added to the game.

Explanation
int? get secondsLeft {
  if (turnDeadlineMs <= 0 || serverTimeMs <= 0) return null;
  final remaining = turnDeadlineMs - serverTimeMs;
  return remaining > 0 ? (remaining / 1000).ceil() : 0;
}

bool get isMyTurn => you != null && turn == you;
bool get iHaveBid => you != null && bids[you!] != null;
bool canPlay(PlayingCard card) =>
    phase == GamePhase.playing && isMyTurn && legalMoveIds.contains(card.id);

These getters are the entire contract the UI (module 6) codes against — it never inspects phase/turn raw, it asks canPlay(card) or reads isMyTurn. legalMoveIds is a Set<String> of wire ids rather than a List<PlayingCard> — cheap O(1) containment checks per card the hand-fan widget renders, and it's already computed server/host-side via legalMoves from module 1, so the UI never re-derives legality itself.

The three clock fields explain themselves in their own doc comments in the file — worth reading verbatim, because the reasoning ("a bot's think delay... is not something to show a countdown for") is exactly the kind of decision that isn't obvious from the field names alone:

/// Wall-clock instant (unix millis, server clock) at which the seat on the
/// clock is played for automatically. Zero on a locally hosted table, and on
/// a networked one whenever a bot is thinking — a countdown only makes sense
/// for a turn a person can actually take.
final int turnDeadlineMs;

Notice the engine keeps no wall clock of its own — withClock() (lines 203–231) is how whoever is hosting the table (module 5's LocalSession, or the Go room actor in module 13) stamps deadlines onto an otherwise clock-free view on the way out. That's deliberate: a Timer or DateTime.now() call inside the engine would make it non-deterministic and unable to be driven by a test with a fake clock.

Try it yourself — why might withClock return a new GameView instead of mutating the existing one?

Think about what else in this file is declared final.

Show solution

Every field on GameView is final — it's an immutable value, like PlayingCard in module 1. Mutating it in place isn't an option; the only way to "add" clock info is to construct a new instance carrying the old fields plus the new ones, which is exactly what withClock does. Immutability here means a GameView handed to a widget can never change out from under it mid-build() — the widget rebuilds with a whole new one instead.

GameEvent — the event stream

frontend/lib/engine/game.dart:297–381
Purpose

A GameView only tells you the current state — it can't tell you what just happened, which is what the UI needs to trigger a card-flip animation or a trick-won sound. GameEvent is a discrete log of happenings (a card was played, a trick was won, a hand ended) emitted alongside state changes, purely for the presentation layer to react to.

Decision

A sealed class hierarchy of concrete event types, instead of one GameEvent class with a type string and a generic payload map (the shape the wire protocol itself actually uses — see backend/PROTOCOL.md's event frame). Inside pure Dart code, a sealed hierarchy lets every switch over a GameEvent (in the UI's event listener, module 6) be checked exhaustively by the compiler — add a tenth event type and every unhandled switch in the codebase becomes a compile error, not a silent no-op at runtime. The cost shows up at the network boundary: JSON has no native concept of a sealed type, so remote_session.dart (module 9) still has to decode a wire type string back into one of these concrete classes by hand.

Explanation
sealed class GameEvent {
  const GameEvent();
}

class CardPlayed extends GameEvent {
  const CardPlayed(this.seat, this.card);
  final int seat;
  final PlayingCard card;
}

class TrickWon extends GameEvent {
  const TrickWon(this.seat);
  final int seat;
}

Each subtype carries only the data relevant to that event — CardPlayed needs a seat and a card, TrickWon needs just the winning seat, GameOver needs the final List<SeatRanking>. There are seven concrete subtypes in total; PresenceChanged and AutoplayChanged stand out because, per their own doc comments, they're not really about game rules at all — they exist purely so a networked table can announce "a seat dropped" or "the server took over this seat" as a one-time notification, not something a player has to notice on their own.

Improvement note
No weakness tied to this hierarchy itself — it's a textbook use of sealed classes. The cost noted above (dual representation: sealed classes in Dart, stringly-typed frames on the wire) is inherent to crossing a JSON boundary at all, not a defect in this file.

CallBreakGame — the state machine

frontend/lib/engine/game.dart:383–594
Purpose

Everything above this point is data. CallBreakGame is the one class that actually owns a game in progress and mutates it in response to player actions — placeBid, playCard, clearTrick, nextHand — while enforcing that those actions only succeed when the current phase and turn allow them.

Decision

Every mutating method returns a plain bool (accepted / rejected) rather than throwing an exception on an illegal action. A rejected move is an entirely expected, routine outcome here — a client trying to play out of turn, or a stale UI tap after the turn already advanced — not an exceptional one. Modelling it as a return value keeps the call sites (the session layer, and later the Go room actor handling untrusted network input) as plain if checks instead of try/catch around every player action. The cost: it's easy to forget to check the boolean and assume the action always succeeded.

Explanation

Starting a hand (lines 436–455):

void _startHand(int index) {
  handIndex = index;
  dealer = (dealer + 1) % 4;
  _hands = dealHands(_random);
  bids = List.filled(4, null);
  ...
  phase = GamePhase.bidding;
  turn = (dealer + 1) % 4;
  _pendingEvents.add(HandStarted(index));
}

dealer starts at 3 in the field declaration (line 404) specifically so this first (dealer + 1) % 4 lands on seat 0 — "dealer starts at 3 so the first hand is dealt by seat 0 and led by seat 1," per the doc comment. Every subsequent hand rotates the dealer by one seat, which is standard trick-taking-game etiquette encoded directly in arithmetic rather than a separate rotation table.

Try it yourself — write placeBid before looking

Write a method bool placeBid(int seat, int bid): reject (return false, change nothing) unless the phase is bidding, it's that seat's turn, and that seat hasn't already bid. On success, clamp the bid with clampBid from module 1, store it, emit a BidPlaced event, and then either advance turn to the next seat, or — if all four seats have now bid — switch phase to playing, set turn to the seat after the dealer, and emit a BiddingComplete event.

Show solution 
bool placeBid(int seat, int bid) {
  if (phase != GamePhase.bidding || turn != seat || bids[seat] != null) {
    return false;
  }
  final value = clampBid(bid);
  bids[seat] = value;
  _pendingEvents.add(BidPlaced(seat, value));

  if (bids.every((b) => b != null)) {
    phase = GamePhase.playing;
    turn = (dealer + 1) % 4;
    _pendingEvents.add(const BiddingComplete());
  } else {
    turn = (seat + 1) % 4;
  }
  return true;
}

    return false;

    _pendingEvents.add(TrickWon(winner));
  } else {
    turn = (seat + 1) % 4;
  }
  return true;
}

/// Called by the host once the finished trick has been on screen long enough.
void clearTrick() {
  if (!awaitingTrickClear) return;
  ...
}

Notice a finished trick doesn't clear itself — playCard sets awaitingTrickClear = true and turn = null, and stops. Nobody can act (no seat is "on turn," and the guard clause blocks a fifth play). A separate clearTrick() call, made by whoever's hosting after a pause (so players can actually see the four cards on the table before they're swept away), is what advances to the next trick or ends the hand. This two-step split is what makes the "finished trick lingers on screen" pacing possible at all — module 5's LocalSession is what actually calls clearTrick() on a timer, not this file.

Handing out a view — the redaction boundary (lines 570–593):

GameView viewFor(int? seat, {int? hostSeat}) => GameView(
  phase: phase,
  ...
  hand: seat == null ? const [] : sortForDisplay(_hands[seat]),
  legalMoveIds: seat == null ? const {} : legalMovesFor(seat).map((c) => c.id).toSet(),
  handCounts: [for (final h in _hands) h.length],
  ...
);

This is the one line in the whole engine that decides what a seat is allowed to see: hand: is that seat's own cards in full, but every seat's card count — never their cards — goes into handCounts for everyone. Pass seat: null and you get a spectator view with no hand and no legal moves at all. There is exactly one method that builds a GameView; nothing else in the codebase is allowed to construct one, which is what makes this the enforcement point rather than a convention someone could forget to follow.

Improvement note
CallBreakGame has no persistence or serialization of its own internal state (only the redacted GameView is serializable) — an in-progress game exists only in this object's memory. That's fine for the offline mode this module targets, but it's the root cause of a gap flagged later, at the server: a networked table is "in memory only" (see Module 18 / the Roadmap) — a process restart loses every hand in progress, because there was never a serialized form of CallBreakGame to snapshot in the first place.

Checkpoint

Why does GameView duplicate most of CallBreakGame's fields instead of the UI just reading the game object directly with a "my seat" parameter?
So that "can another player's hand ever leak to this seat" is guaranteed by what data GameView physically contains, not by trusting every future widget to filter correctly. The cost is duplication that must be kept in sync by hand as the game gains new state.
Why does the engine keep no wall clock of its own — no Timer, no DateTime.now() anywhere in game.dart?
So the state machine stays deterministic and can be driven entirely by explicit method calls in a test, with no real time dependency. Clock info (turnDeadlineMs etc.) is stamped on afterward by whoever is hosting, via withClock() — the engine itself never decides when a turn times out.
Why is a finished trick a two-step process (playCard sets awaitingTrickClear, a separate clearTrick() advances) instead of one method that plays the fourth card and immediately starts the next trick?
Because the finished trick needs to actually be visible on screen for a beat before it's swept away — if the fourth card immediately triggered the next trick, there'd be no state in which "four cards sit on the table, nobody's turn yet" exists for the UI to render and pace against.
placeBid/playCard return bool instead of throwing on an illegal move. What kind of caller does this design assume, and where might it be the wrong choice?
It assumes callers expect rejection as a routine outcome, not an exceptional one — true for a UI reacting to a stale tap, and true for a server handling untrusted network input from a client that might be malicious or buggy. It would arguably be the wrong choice inside test code, where a silently-ignored false can mask a test bug that meant to assert the move succeeded.
