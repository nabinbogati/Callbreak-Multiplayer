Sessions & Offline Play

This is the module where the game becomes playable end-to-end for the first time — entirely offline, against bots, with no server. It builds net/session.dart (the contract every playing mode will implement) and net/local_session.dart (the first, and simplest, implementation of it).

Where this fits

net/session.dart — the contract

frontend/lib/net/session.dart:30–79
Purpose

The table screen (module 6) needs to render a hand of cards, show whose turn it is, and send a bid or a play — and it needs to do that identically whether the game is offline, on the internet, or over LAN. Without one shared contract, the table screen would need a different code path per mode, and any UI bug fix would need to be made three times. GameSession is that one contract.

Decision

An abstract class extending Flutter's ChangeNotifier, plus a separate Stream<GameEvent> — two different push mechanisms on the same object, deliberately, not one. ChangeNotifier holds "the current snapshot" (view) — a widget wrapped in ListenableBuilder just re-reads session.view whenever notifyListeners() fires, no manual subscription bookkeeping. A Stream, by contrast, is a history of one-shot happenings — "a card was played" needs to trigger an animation exactly once, which a rebuild-on-latest-value model like ChangeNotifier can't express (if two cards get played between two rebuilds, a snapshot model has already lost the first one). Two mechanisms for two genuinely different needs, at the cost of the class carrying two separate subscription models a consumer has to know about, instead of one.

This is also the file's second real decision: the contract lives in package:flutter/foundation.dart's ChangeNotifier, not in a Flutter-independent form, unlike every file in Part I. That's intentional here — this layer's whole job is bridging domain state to the UI, so coupling it to Flutter's own listener mechanism is the right trade, at the cost of this file (unlike the engine) not being reusable outside a Flutter app.

Explanation
abstract class GameSession extends ChangeNotifier {
  GameView? get view;
  SessionStatus get status;
  String? get errorMessage;
  GameMode get mode;
  Stream<GameEvent> get events;

  bool get isReady => status == SessionStatus.ready && view != null;

  void placeBid(int bid);
  void play(PlayingCard card);
  void continueToNextHand();
  void restart();
}

Four getters describe "what's true right now" (view, status, errorMessage, mode), one stream describes "what just happened," and four methods are the entire vocabulary of things a player can do. Every screen in module 6 is built against exactly this surface — nothing in the table screen ever imports LocalSession or a network class by name.

Try it yourself — turnDeadline converts a server-clock timestamp into something usable. What problem is it solving?

Read the doc comment on GameView.turnDeadlineMs from module 2 again: it's a unix millis value on the server's clock. What goes wrong if a widget just compared it directly to DateTime.now() on the phone?

Show solution 
/// The view carries the deadline on the server's clock, which is useless to
/// compare against `DateTime.now()` on a phone whose clock is minutes off. A
/// session therefore converts it once, when the view lands, by treating the
/// view's own `serverTimeMs` as "now". What survives is a duration, which
/// both clocks agree on.
DateTime? get turnDeadline => null;

A phone's clock can be minutes off from the server's (wrong timezone, no NTP sync, whatever) — comparing a raw server timestamp to the device's DateTime.now() would make the turn clock lie. The fix is to only ever trust the relative gap: "the deadline is X ms after the moment this view was sent" (turnDeadlineMs - serverTimeMs), then add that duration to the device's own DateTime.now() once, on arrival. Both clocks then agree on the duration even though they disagree on absolute time. Note the default implementation here just returns null — it's overridden per session type that actually has a clock to convert.

Improvement note
No weakness in this contract itself. It's worth noting as a maintainability observation for later: because GameSession has three real implementations (this module's LocalSession, plus RemoteSession and LanHostSession in modules 9–10), any new capability added to the interface (a new getter, a new method) must be implemented — or explicitly no-op'd, as several methods here already do with default bodies — in all three. The default no-op bodies on methods like wakeUp() are exactly that safety valve already in use.

net/session.dart — NetworkSession

frontend/lib/net/session.dart:175–227
Purpose

A networked table has states an offline game never does: waiting in a lobby for friends, a hostless quickplay table counting down, reconnecting after a dropped connection. Without somewhere to put that, either GameSession itself would carry lobby/reconnect fields that mean nothing for a solo game, or the table screen would need type-specific knowledge of which network class it's holding.

Decision

A second abstract class, NetworkSession extends GameSession, carrying only the networked-only surface, instead of adding nullable lobby fields to GameSession itself. LocalSession never has to implement lobby, countdown, canResume or any reconnect logic — its surface stays exactly the four getters and four methods above. The cost lands on the table screen: to reach lobby-only state it has to check session is NetworkSession and narrow the type, an extra branch that a flatter, single-class design wouldn't need.

Explanation
abstract class NetworkSession extends GameSession {
  LobbyState? get lobby;
  int? get countdown;
  void leaveLobby();

  bool get isResuming;
  bool get canResume;
  Duration? get seatHeldFor;
  void retryNow();

  void startGame();
  void setHandsPerGame(int hands) {}
}

lobby being nullable is itself meaningful: null once play has begun, non-null only while the table is still filling. isResuming vs. a first-time connecting status matters to the player — "your seat is being held, hang on" reads very differently from "connecting" on a fresh join, per the doc comment on isResuming.

Improvement note
No weakness tied to this file. It's a clean example of an interface segregated by capability rather than by implementation.

net/local_session.dart — TablePacing

frontend/lib/net/local_session.dart:14–43
Purpose

A bot that plays instantly feels like a machine, not an opponent; a bot that takes ten seconds feels broken. TablePacing is the one place every timing constant for a locally-hosted table lives — how long a bot "thinks," how long a finished trick lingers before clearing, how long a human gets to bid or play before autoplay takes over.

Decision

These constants are duplicated in Go, not shared — the backend's own README states outright: "The pacing defaults deliberately match TablePacing in frontend/lib/net/local_session.dart, so a networked table feels the same as the offline one." That's a real, accepted trade-off: there's no single source of truth for these numbers across the two languages, only a documented intention to keep them equal by hand.

Explanation
class TablePacing {
  static const botThinkMin = Duration(milliseconds: 550);
  static const botThinkExtra = Duration(milliseconds: 450);
  static const trickLinger = Duration(milliseconds: 1100);
  static const bidTimeout = Duration(seconds: 5);
  static const playTimeouts = [
    Duration(seconds: 10), Duration(seconds: 8),
    Duration(seconds: 6),  Duration(seconds: 5),
  ];
  static const handAdvanceWait = Duration(seconds: 5);
}

playTimeouts is indexed by trick position — the leader of a trick gets the longest clock (10s), the fourth player to act gets the shortest (5s), because per its doc comment "each seat after has less to decide with more of the trick already on the table." bidTimeout and the play timeouts are explicitly documented as mattering only when someone else is at the table — "a solo game against bots is never hurried" — which is a decision enforced in LocalSession itself, not in this constants file.

Improvement note
Because these constants are hand-duplicated rather than shared (see Decision, above), changing one side without the other silently desyncs the offline and networked feel — e.g. edit PLAY_TIMEOUTS in the backend's env config without touching this file, and a networked table's turn clock stops matching what a solo game trains a player to expect. A generated or config-driven single source (e.g. the server sending its actual pacing values to the client once, at connect time) would close this gap; today it depends on a developer remembering to touch two files in two languages.

net/local_session.dart — LocalSession

frontend/lib/net/local_session.dart:47–263
Purpose

This is the class that makes "vs Bots" playable: it owns a CallBreakGame (module 2), a BotBrain per bot seat (module 3), and a self-driving clock that plays bot turns and clears finished tricks on a timer — entirely on-device, no server involved at all.

Decision

The session drives its own pacing with an internal Timer, rather than requiring the UI to call some tick() method on a frame callback. A self-scheduling session means the table screen has zero responsibility for pacing the game — it just renders whatever view currently is. The cost is lifecycle discipline: a Timer running inside a non-widget object must be explicitly cancelled when the session is done, or it fires a callback into a now-meaningless, disposed object. dispose() (line 257) exists specifically to prevent that.

Explanation

The publish/schedule loop — the engine of the whole class (lines 154–219):

void _publish() {
  if (_disposed) return;
  _view = _game.viewFor(humanSeat);
  for (final event in _game.takeEvents()) {
    _record(event);
    if (!_events.isClosed) _events.add(event);
  }
  notifyListeners();
  _scheduleNextAutoAction();
}

void _scheduleNextAutoAction() {
  _timer?.cancel();
  if (_disposed) return;

  if (_game.awaitingTrickClear) {
    _timer = Timer(_scaled(TablePacing.trickLinger), () {
      _game.clearTrick();
      _publish();
    });
    return;
  }

  final seat = _game.turn;
  if (seat == null || seat == humanSeat) return;
  final brain = _brains[seat];
  if (brain == null) return;
  _timer = Timer(_thinkTime(), () => _takeBotTurn(seat, brain));
}

Every mutation to the game funnels through _publish(): pull a fresh redacted view for the human seat, drain and forward the engine's pending events (module 2's takeEvents()), tell listeners to rebuild, then decide what the table should do next on its own. That last step is either "a trick just finished — clear it after a pause" or "it's a bot's turn — think, then act" — and each of those branches calls _publish() again when it fires, which is what keeps the whole game moving forward without the UI ever driving it.

Try it yourself — write placeBid and play before looking

Both are one-liners: call the matching CallBreakGame method (module 2) for the human's fixed seat, and if it returns true (accepted), call _publish().

Show solution 
@override
void placeBid(int bid) {
  if (_game.placeBid(humanSeat, bid)) _publish();
}

@override
void play(PlayingCard card) {
  if (_game.playCard(humanSeat, card)) _publish();
}

Notice what happens on rejection: nothing. No error surfaced, no exception — the engine's bool return (module 2's Decision) is exactly what makes this safe to call from a UI tap handler with no try/catch, at the cost that a caller who forgets to check what happened has no way to tell an accepted move from a silently rejected one.

Cleanup (lines 256–262):

@override
void dispose() {
  _disposed = true;
  _timer?.cancel();
  _events.close();
  super.dispose();
}

Three things happen, in order that matters: the _disposed flag is set first so any already-scheduled timer callback that fires between now and cancellation still no-ops via its own if (_disposed) return guard; the timer is cancelled so it doesn't fire at all in the common case; the event stream is closed so nothing can subscribe to a dead session. This is a model of a leak-free Dart object — contrast it with the gap flagged in module 4, where main() has no equivalent guard around its own async setup.

Improvement note
_record (lines 171–198) hands a finished game to GameUploader.enqueue and the file's own comment says the quiet part out loud: "Entirely fire-and-forget... a phone with no signal finishes the game exactly as fast as one with a connection and the player is never told anything went wrong." That's the right call for not blocking the win screen on a network call, but it means a permanently-failing upload (not just an offline one — a genuinely broken account link, say) looks identical to a healthy one from the player's point of view, forever. See module 9's own note on GameUploader for where that queue's retry behaviour actually lives.

Checkpoint

Why does GameSession expose both a ChangeNotifier-style view getter and a separate Stream<GameEvent>, instead of putting everything through one mechanism?
They serve different needs: view is "the current snapshot," fine to just re-read on rebuild and safe to miss intermediate states. Events are one-shot happenings (a card played) that must each be reacted to individually — if two cards are played between two rebuilds, a snapshot-only model has already lost the first one, but a stream delivers both.
NetworkSession adds lobby/reconnect capability as a subclass rather than nullable fields on GameSession itself. What's the concrete cost of that choice, paid where?
LocalSession stays minimal — it never implements lobby or reconnect logic it doesn't need. The cost is paid in the table screen (module 6), which has to type-check session is NetworkSession and narrow before it can read lobby-only state, an extra branch a flatter design wouldn't require.
Why does LocalSession drive itself with an internal Timer instead of the UI calling a tick() method?
So the table screen has zero responsibility for pacing — it only ever renders whatever view is. The cost is that a Timer living inside a plain object (not a widget with a framework-managed lifecycle) needs explicit, careful cancellation on dispose, or it can fire into an object that no longer means anything.
TablePacing's constants are deliberately duplicated in the Go backend rather than shared. What real failure mode does that open, concretely?
The two sets of numbers can drift: change a timeout on one side (say, the backend's PLAY_TIMEOUTS env var) without updating this file, and a networked table's turn clock stops matching the pacing an offline game trained the player to expect — a UX inconsistency with no compiler or test to catch it, since nothing enforces the two files agree.
