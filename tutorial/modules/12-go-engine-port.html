Part III — Go backend · Module 12 of 20

Engine Port to Go

The Go server needs its own copy of the rules — it cannot import Dart code, and it must never trust a client to enforce them. This module builds engine/card.go, engine/rules.go, engine/game.go, engine/event.go and engine/json.go: a second, independent implementation of exactly what modules 1 and 2 built in Dart, plus the test strategy (golden_test.go) that keeps the two from silently drifting apart.

Where this fits

engine/card.go

backend/internal/engine/card.go
Purpose

Same job as module 1's card.dart: a card type, a stable wire id, a full deck, and a way to shuffle and deal it — except now it's the version the server actually trusts, because a client's own idea of what cards it holds is never taken on faith.

Decision

The Go version is not a 1:1 port — it's a superset. The package comment at the top of this file claims: "It is a faithful port of the Dart engine ... Every exported symbol below has a named counterpart in the Dart source." That's true for Card, Suit, FullDeck, SortForDisplay — but ShuffleKind, DealStyle, DealConfig, DealConfigFromPreset, and the entire riffle / overhand / balancedDeal machinery (lines 175–444, roughly a third of this file) have no counterpart in frontend/lib/engine/card.dart at all — that file's own dealHands is three lines: shuffle the full deck with Dart's built-in List.shuffle, then cut it into four 13-card blocks. Real, verified by grep against the Dart source: no match for ShuffleKind, DealStyle, riffle, balancedDeal anywhere in card.dart. See this file's Improvement note.

Why the extra machinery exists at all: the deal presets (fair / physical / balanced) are a player-facing table option, chosen at join time and carried on the wire by protocol.ClientFrame.Deal (module 11). Only the server deals cards for a networked table, so only the server needs to know how to deal them three different ways — the Dart client's offline mode (LocalSession, module 5) never offered this choice, so its card.dart never needed it.

Rejection sampling for balancedDeal, not a deterministic "fix" of an unbalanced hand. The comment on balancedDeal explains the reasoning: "Rejection sampling keeps every returned deal uniformly random subject to the balance constraint — the strength filter is the only bias." The alternative — directly constructing a "balanced" hand by hand-picking cards to spread evenly — would be simpler code but would introduce a much stronger, harder-to-reason-about bias than "reject and re-roll a genuinely random deal until it happens to be close enough," capped at 60 attempts so a pathological run can't loop forever.

ID() produces the exact same wire string Dart's PlayingCard.id does ("AS", "10H"), which is what keeps a card played on one side of the wire recognizable on the other.

func handStrength(hand []Card) int {
	s := 0
	for _, c := range hand {
		v := c.Rank - MinRank // 0..12
		if c.IsTrump() {
			v = v*2 + 6
		}
		s += v
	}
	return s
}

Every card contributes its rank above the minimum (0 to 12), but a trump card's contribution is doubled and bumped by a flat 6 — reflecting that in Call Break, spades are permanent trumps that can win a trick even when they weren't led, so holding them is worth substantially more than holding a plain high card of the same rank. This is only used to measure a hand for the balanced-deal filter — it never influences bidding or play.

engine/rules.go

backend/internal/engine/rules.go
Purpose

The actual Call Break rulebook, encoded as functions: what you're allowed to play, who wins a trick, how a hand is scored. This is the part of the port that has to be exactly right — a divergence here between Dart and Go means the server would reject a move the offline mode allows, or score a hand differently than the client predicts.

Decision

Round1 uses math.Round, deliberately, over Go's more common truncating conversion. The comment is explicit: "The rounding must match Dart's (raw * 10).round() / 10, whose .round() ties away from zero — which is exactly math.Round's behaviour." A careless port might reach for int(raw*10), which truncates toward zero rather than rounding — subtly wrong for exactly the negative and half-way values a losing bid's score (a straight negative number) would produce. Choosing the specific standard-library function whose rounding rule matches Dart's, rather than hand-rolling one, is what makes the two languages agree on the same score for the same hand.

LegalMoves is a pure function of a hand and a trick, not a method on Game. This mirrors the same choice made in rules.dart (module 1): keeping the rules engine free of any table state means it can be called standalone — from Game.LegalMovesFor, from a future bot, or from a test — without constructing a whole game first.

Explanation

	// void in the led suit: must trump, and overtrump if the trick is already trumped

Identical three-tier logic to Dart's version, walked in module 1: leading is unrestricted; holding the led suit, you must follow it and beat the best card of that suit already down if any of your cards can ("heading"); holding none of the led suit, you must trump, and overtrump an already- trumped trick if you're able to. Only unable to overtrump may you discard freely. 

func TrickWinner(trick []TrickPlay) int {
	led := trick[0].Card.Suit
	var contenders []TrickPlay
	for _, p := range trick {
		if p.Card.IsTrump() { contenders = append(contenders, p) }
	}
	if len(contenders) == 0 {
		for _, p := range trick {
			if p.Card.Suit == led { contenders = append(contenders, p) }
		}
	}
	best := contenders[0]
	for _, p := range contenders[1:] {
		if p.Card.Rank > best.Card.Rank { best = p }
	}
	return best.Seat
}

Any trump beats any non-trump regardless of what was led, so the contender pool is every trump played if there's at least one, and otherwise every card of the led suit; the highest rank among the contenders wins. WouldWin (used by the bot in module 3's Dart equivalent, and reused server-side) reuses this exact function by constructing a hypothetical trick with the candidate card appended under sentinel seat -1, rather than duplicating the winner logic — the same "ask the real function a hypothetical question" pattern rules.dart used.

Improvement note
No weakness found in this file. It is pure, has no I/O, no shared state, and is covered by rules_test.go (264 lines) — the kind of code this port strategy is supposed to produce.

engine/game.go

backend/internal/engine/game.go
Purpose

The state machine itself — the Go counterpart to Dart's CallBreakGame from module 2. It owns one table's phase, hands, bids, trick, and running scores, and exposes exactly two ways in (PlaceBid, PlayCard) and one way for state to leave (ViewFor).

Decision

Explicitly not safe for concurrent use — by contract, not by mutex. The doc comment on Game states it directly: "It is not safe for concurrent use: exactly one goroutine (the room actor) owns an instance." The alternative — a sync.Mutex guarding every field, so any goroutine could call PlayCard safely — is the more conventional Go answer to shared mutable state. This codebase instead commits to the actor model built in module 13: one goroutine per table owns its *Game completely, and every external request is a message sent to that goroutine, never a direct concurrent call. The payoff is that none of this file needs locks, and none of its logic has to reason about interleaving — at the cost that the invariant is enforced by convention and code review, not by the compiler or a runtime check.

Mutating methods return bool, not an error, and leave state completely untouched on failure. PlaceBid and PlayCard both start with a guard clause that returns false immediately — wrong phase, wrong turn, already bid, illegal card — before mutating anything. This mirrors Dart's CallBreakGame pattern from module 2 exactly: the caller (the room actor) turns a false into a protocol error frame with zero rollback logic of its own, because there's nothing to roll back.

Explanation
func (g *Game) PlayCard(seat int, card Card) bool {

	g.pending = append(g.pending, CardPlayed{Seat: seat, Card: card})

Four checks — phase, turn, card actually in hand, card legal under the rules — all have to pass before a single field changes. The fourth trick card triggers the exact same two-step clear you saw in Dart's game.dart (module 2): the trick freezes (AwaitingTrickClr = true, Turn = nil) so nobody can play into a trick that's already decided, and a separate ClearTrick() call — driven by the room actor's own timer, not by this method — banks it after the "linger" delay the client shows the finished trick for.

The redaction boundary — this is the only function in the entire backend that turns full table state into something safe to send a specific seat. Because "the room actor is the only caller" describes today's callers, not a guarantee the type system enforces. A future bug — a duplicate timer firing twice, a race in how the room schedules the next-hand advance, a test calling it out of order — would otherwise silently corrupt game state (for example, dealing a second hand mid-trick) instead of harmlessly doing nothing. The guard costs one comparison and turns a whole category of programmer error into a no-op instead of corrupted state.

Improvement note
The concurrency-safety contract ("exactly one goroutine owns an instance") is documented but not enforced anywhere in this file — no build tag, no runtime owner-goroutine check (Go's race detector would catch a violation in tests, but only if a test actually exercises concurrent access, and none of game_test.go's 425 lines appear to). This is the same shape of risk as module 10's three-implementations note: correct today because every real caller happens to follow the rule, with nothing short of the race detector (run manually, not as a gate) to catch a future caller that doesn't.

engine/event.go

backend/internal/engine/event.go
Purpose

The Go counterpart to Dart's sealed GameEvent hierarchy from module 2 — a discrete record of something that happened (a hand started, a bid was placed, a trick was won) that the room actor forwards to clients as an event frame for them to animate.

Decision

An interface with one method, not a sealed hierarchy — because Go has no sealed classes. Dart's version is a compiler-enforced closed set: a switch over a sealed GameEvent that misses a subtype fails to compile. Go's type system has no equivalent — the closest available tool is an interface (Event, with a single Wire() map[string]any method) that any of the six event structs can satisfy. The trade-off is real and asymmetric: any Go code that switches on a concrete event type (a type switch) to handle each one specially gets no compiler warning if a new event variant is added later and that switch isn't updated to handle it — it simply falls through to whatever default case exists, silently, where Dart's sealed-class switch would refuse to compile until every case was handled.

Explanation
type Event interface {
	Wire() map[string]any
}

type CardPlayed struct {
	Seat int
	Card Card
}
func (e CardPlayed) Wire() map[string]any {
	return map[string]any{"event": "play", "seat": e.Seat, "card": e.Card.ID()}
}

Each event is its own small struct, and its Wire() method returns the frame body as a bare map — deliberately without the outer "type": "event" envelope key, which protocol.EncodeEvent (module 11) injects afterward. Six events cover everything the client needs to animate: HandStarted, BidPlaced, BiddingComplete, CardPlayed, TrickWon, HandOver, GameOver — matching Dart's seven-variant GameEvent hierarchy from module 2 minus the two client-only variants (PresenceChanged, AutoplayChanged) that the server instead sends as raw maps directly from protocol/server.go (module 11's AutoplayChanged function), since those never originate from the engine itself.

Improvement note
The lack of compiler-enforced exhaustiveness (see Decision) is a real, if narrow, risk: Game only ever appends known event structs to g.pending and nothing in this package currently does a type switch over Event — the room actor (module 13) instead just calls .Wire() polymorphically through the interface, which sidesteps the risk entirely for the code that exists today. The risk is purely forward-looking: the day some future code needs to special-case one event type (metrics, logging, a feature that behaves differently per event) via a type switch, adding a new event variant later would not force that switch to be revisited the way Dart's sealed class would.

engine/json.go

backend/internal/engine/json.go
Purpose

Go's encoding/json would happily marshal a Card as {"Rank":14,"Suit":0} and a View with its actual Go field layout — neither is what GameView.fromJson on the Dart side expects. This file hand-writes the marshaling so the bytes leaving the Go server are byte-compatible with what the Dart client already decodes.

Decision

Hand-written MarshalJSON/UnmarshalJSON, not struct tags alone, and not a code generator. The same convention module 2 established on the Dart side (hand-written toJson/fromJson, no codegen, as a zero-build-step house style) is mirrored here. Struct tags alone can't produce "AS" for a card — the wire format is a computed string, not a direct field — so Card.MarshalJSON is written by hand to call c.ID(). A code generator (like protoc or a Go-specific JSON codegen tool) could produce equivalent code, but would add a build step neither language's engine otherwise needs.

Nil slices are explicitly normalized to empty arrays before marshaling. Nine separate if out.X == nil { out.X = []Y{} }-shaped checks in View.MarshalJSON. Go's zero value for a slice is nil, which encoding/json marshals as JSON null — but Dart's fromJson reads these as Lists and calls methods on them directly; decoding null where a list is expected throws in Dart rather than producing an empty list. This normalization is the entire reason a freshly dealt hand with an empty legal-moves list doesn't crash the client.

Explanation
func (c Card) MarshalJSON() ([]byte, error) { return json.Marshal(c.ID()) }

func (c *Card) UnmarshalJSON(data []byte) error {
	var id string
	if err := json.Unmarshal(data, &id); err != nil { return err }
	parsed, err := ParseCard(id)
	if err != nil { return err }
	*c = parsed
	return nil
}

A Card marshals to and from a bare JSON string — not an object — which is exactly the shape module 1's Dart PlayingCard.id uses on the wire. Because Card implements the standard library's json.Marshaler/Unmarshaler interfaces, every place a Card appears inside a larger struct (a hand, a trick) encodes correctly automatically — encoding/json calls these methods for you at every nesting level, no manual wiring required at each call site. 

type viewJSON struct {
	Phase        Phase           `json:"phase"`
	...
	Bids         []*int          `json:"bids"`
	...
}

func (v *View) MarshalJSON() ([]byte, error) {
	out := viewJSON{ ... Bids: v.Bids[:], ... }
	if out.Hand == nil { out.Hand = []Card{} }
	...
	return json.Marshal(out)
}

View itself uses Go arrays ([4]*int for Bids) internally for the compile-time guarantee of exactly four seats, but a private mirror struct viewJSON with slice fields and explicit json tags is what's actually marshaled — v.Bids[:] converts the array to a slice at the boundary. This is the same "internal representation optimized for the language, wire representation matched to the contract" split you'd expect, kept in one small private type rather than leaking JSON tags onto the array-typed fields game logic actually works with.

Improvement note
No weakness found. The nil-to-empty-array normalization is exactly the kind of defensive measure this codebase's cross-language contract needs, and it's directly exercised by golden_test.go below rather than left to hope.

Testing strategy: golden_test.go

backend/internal/engine/golden_test.go
Purpose

Two independent implementations of the same rules, in two different languages, are only as trustworthy as the mechanism that catches them drifting apart. This file is that mechanism: it captures real server output to a checked-in file, which a matching Dart test then has to be able to decode.

Decision

Golden JSON files checked into testdata/, decoded by a test in the other language, instead of maintaining two parallel unit test suites that assert the same things independently. The file's own comment states the risk this avoids plainly: "The Dart client decodes these frames with GameView.fromJson, which reads its keys unconditionally and throws on anything it does not recognise the shape of. A Go change that alters the encoding therefore breaks every connected client — and would do it at runtime, on a phone, not here." Two separate test suites, one per language, could both pass while each testing a slightly different (and both self-consistent) idea of the wire shape — they would never actually prove the two sides agree with each other. A golden file that one side writes and the other side is graded against makes disagreement a hard failure in CI rather than a silent runtime crash on a user's phone.

Explanation
func goldenViews(t *testing.T) map[string]*View {

A seeded RNG makes the whole sequence deterministic, and the game is driven through every phase that produces a structurally different view — bidding (nullable bids populated differently than in play), mid-trick, hand-over (round scores populated), game-over (rankings populated), a spectator with no cards, and a view carrying the server-only turn clock fields. These are "exactly the ones a decoder trips over," per the file's own comment — the nullable and server-only fields are where a shape mismatch would actually bite.

Improvement note
As surfaced in the try-it-yourself above: the golden-file safety net covers view frames only, not event frames. Both are produced by this same engine package and consumed by the same "reads keys unconditionally and throws on the unexpected" Dart decoding style the comment warns about — an accidental change to an event's field names or types (in event.go) has exactly the same blast radius (a runtime crash on a connected client) as a view change, but only the view side has a regression test that would catch it before it shipped. Extending goldenViews's pattern to capture one frame per event type would close this gap with the same mechanism already proven to work.

Checkpoint

The package comment on card.go says every exported symbol has a named Dart counterpart. What's actually true, and why does the gap exist?
Roughly a third of the file — the ShuffleKind/DealStyle/DealConfig deal-preset system — has no Dart equivalent at all; Dart's own dealHands is a three-line shuffle-and-cut. The gap exists because deal presets are a networked-table option chosen at join time, and only the server ever deals cards for a networked table — the offline mode never needed a choice.
Why does Game get away with having no mutex, given it holds mutable shared state?
Because "shared" is the wrong word for how it's actually used: the codebase commits to an actor model where exactly one goroutine (the room actor, built next module) ever touches a given Game instance, so nothing is ever actually concurrent. The safety comes from that convention being followed everywhere, not from a lock — which is both the appeal (no lock contention, simpler code) and the risk (nothing stops a future caller from breaking the convention).
Why does Round1 specifically use math.Round instead of a more common truncating int conversion?
Because Dart's own `.round()` ties away from zero, and math.Round matches that exact behavior — a truncating conversion would silently disagree with Dart on negative and half-way values, which is precisely where a losing bid's score (a plain negative number) would land.
Why does this codebase use a checked-in golden JSON file plus a cross-language decode test, instead of one unit test suite per language that separately asserts the wire shape?
Two independent suites could each pass while quietly encoding two different, self-consistent assumptions about the shape — neither would ever actually prove the two sides agree. A golden file one side writes and the other is graded against turns any real disagreement into a hard, visible CI failure instead of a runtime decode crash on a user's phone.
