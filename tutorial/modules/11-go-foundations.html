Go Backend Foundations

Part III starts here. Before any networking or game logic, the server needs two things every other package will depend on: a way to turn environment variables into settings (config), and a shared definition of what a JSON message over the wire actually looks like (protocol). Neither package imports anything from the rest of the backend — that's deliberate, and it's this module's main thread.

Where this fits

config/config.go

backend/internal/config/config.go
Purpose

Every tunable the server has — the port it listens on, turn clocks, rate limits, database and Redis addresses, the JWT signing secret — has to come from somewhere at process start. This file is that single place: it reads environment variables, applies sane defaults, and hands every other package one populated Config struct instead of each package calling os.Getenv on its own.

Decision

Environment variables, not a config file. The package comment states the goal directly: "Every field has a default that makes go run ./cmd/server work with no environment at all, so local development needs no setup file." The concrete alternative — a YAML or JSON config file — would need a path convention (where does the server look?), a parser dependency, and a way to layer environment-specific overrides on top of it. Environment variables need none of that, and they're exactly what Docker, Kubernetes, and every common PaaS already inject natively. The trade-off: no comments, no nesting, no validation until Load() actually runs — a config file could be checked by a linter before the process even starts.

Unsafe defaults fail loud instead of being silently guessed. JWTSecret is the clearest example (lines 146–155): in development, a missing secret gets a random one generated per process start — tokens simply stop working on restart, which is a mild inconvenience while iterating. In production (IsProduction() true), the exact same missing value is a hard startup error. The alternative — generating a random secret in production too — would boot successfully and then invisibly invalidate every issued token on every restart or every horizontally-scaled replica, which is a far worse failure to debug than a process that refuses to start.

Explanation
type Config struct {
	Addr      string
	Env       string // "development" or "production"
	...
	JWTSecret []byte
	AdminToken string

	BotThinkMin    time.Duration
	BotThinkExtra  time.Duration
	TrickLinger    time.Duration
	StartCountdown time.Duration

	BidTimeout time.Duration
	PlayTimeouts [4]time.Duration
	...
}

One flat struct, no nested sub-configs. The comment above the pacing fields is worth reading literally: "Defaults mirror TablePacing in the Flutter client (frontend/lib/net/local_session.dart) so a networked table feels the same as the offline one" — the same pacing values you already saw as Dart constants in module 5 reappear here as Go time.Duration defaults, independently declared. PlayTimeouts is a fixed 4-element array indexed by how many cards are already down in the current trick, so whoever leads a trick gets the most time to think and the last player to follow gets the least. 

func Load() (Config, error) {
	c := Config{
		Addr:             env("ADDR", ":8080"),
		...
		MaxRooms:         envInt("MAX_ROOMS", 50_000),
		MsgRatePerSecond: envFloat("MSG_RATE_PER_SECOND", 20),
		...
	}
	if port := os.Getenv("PORT"); port != "" {
		c.Addr = ":" + port
	}
	...
	return c, c.validate()
}

Load() populates every field from a typed helper (env, envInt, envBool, envDuration, ...) that reads one environment variable and falls back to a default if it's unset. PORT — what most PaaS providers inject automatically — is checked afterward and overrides ADDR if present, so the same binary works whether you set ADDR=:9000 yourself or deploy somewhere that sets PORT for you. 

func (c Config) validate() error {
	if c.MaxRooms <= 0 {
		return fmt.Errorf("config: MAX_ROOMS must be positive")
	}
	...
	if c.IsProduction() && len(c.AllowedOrigins) == 0 {
		return fmt.Errorf("config: ALLOWED_ORIGINS is required in production")
	}
	return nil
}

validate() is the second half of the "fail loud" philosophy: every invariant the rest of the server assumes holds (positive rate limits, a database URL if persistence is required, allowed CORS origins in production) is checked exactly once, at startup, in one place — not re-checked defensively throughout the codebase every time a field is read.

Try it yourself — before looking, guess what happens if you set MAX_ROOMS=abc (not a number) in the environment and start the server.
Show solution 
func envInt(key string, def int) int {
	if v := os.Getenv(key); v != "" {
		if n, err := strconv.Atoi(v); err == nil {
			return n
		}
	}
	return def
}

Nothing visibly happens. strconv.Atoi("abc") fails, the if guard on err == nil is false, and the function silently falls through to return def — MaxRooms quietly becomes 50_000, exactly as if MAX_ROOMS had never been set at all. There is no log line, no error, nothing in validate() to catch it, because from validate()'s point of view the value is perfectly valid — it's just not the value whoever set the environment variable meant to provide. See this module's Improvement note.

Improvement note
Every env* helper (envInt, envFloat, envBool, envDuration, envDurationList4 — lines 214–272) silently discards a value that fails to parse and falls back to the default, with no log line anywhere in the package. A deployment config with a typo — MAX_ROOMS=5oo, or a malformed PLAY_TIMEOUTS list — boots successfully and quietly runs with defaults instead of the operator's intended override. This is exactly the kind of bug that's invisible in every environment except the one where the default happens to be wrong: staging behaves fine because the default is close enough, and the misconfiguration only surfaces as a mystery in production. A one-line log.Printf on the parse-failure branch of each helper would make this loud instead of silent, at effectively zero cost. There is also no test file in this package (confirmed: backend/internal/config/ contains only config.go) — this parsing behavior, and the production-vs-development branches in Load(), are entirely unverified by anything but manual inspection.

protocol/protocol.go

backend/internal/protocol/protocol.go
Purpose

The Flutter client and the Go server are two independent codebases in two different languages that have to agree, byte for byte, on what a JSON message means. This file is that agreement written down in code: every frame type name, every field, every validation rule a client-sent frame must pass before any game logic ever sees it.

Decision

Optional fields are pointers, not zero-valued primitives. Bid *int, not Bid int. The struct's own comment explains why: "so 'absent' and 'zero' stay distinguishable — a bid of 0 is a different thing from no bid at all." A plain int can't tell you whether the client sent {"bid": 0} or omitted the field entirely — both decode to zero. A pointer that's nil means "wasn't there"; a pointer to 0 means "there, and it's zero." The alternative would be a separate boolean flag next to every optional field (HasBid bool, Bid int) — it works, but doubles the field count for the same information a pointer already carries for free.

Validation happens once, at decode time, not scattered through the game logic that consumes the result. DecodeClient (below) is the single boundary: anything it returns without an error is guaranteed to have a known type, in-bounds strings, and the required fields for that type already present. Every package downstream — room, ws — can trust a ClientFrame completely rather than re-checking "does this bid frame actually have a bid?" at every call site.

DefaultHandsPerGame = 5 is declared here independently, not imported from the engine's own constant. The comment is explicit about why: "protocol has zero internal dependencies and stays that way, so this is not derived from that constant." The engine package could easily export engine.HandsPerGame for this file to import — but doing so would make the wire-format package depend on the game-rules package, coupling two things that should be free to change independently. The trade-off is named directly in the comment: two numbers, in two packages, that have to be kept in sync by a human remembering to update both.

Explanation
type ClientFrame struct {
	Type string `json:"type"`
	V    int    `json:"v,omitempty"`

	Room         string `json:"room,omitempty"`
	Mode         Mode   `json:"mode,omitempty"`
	...
	Bid  *int   `json:"bid,omitempty"`
	Card string `json:"card,omitempty"`
	...
}

One struct holds every possible field of every frame type the client can send — join, bid, play, and so on all share it, each frame only populating the fields relevant to its Type. This is a "union by convention" rather than a Go-native tagged union (Go has no sealed enum like the Dart GameEvent hierarchy from module 2); the type-specific validation below is what enforces the convention. 

func DecodeClient(data []byte) (ClientFrame, error) {
	if len(data) > MaxFrameBytes {
		return ClientFrame{}, fmt.Errorf(...)
	}
	var f ClientFrame
	if err := json.Unmarshal(data, &f); err != nil {
		return ClientFrame{}, fmt.Errorf(...)
	}
	switch f.Type {
	case TypeJoin:
		f.Room = strings.ToUpper(strings.TrimSpace(f.Room))
		if f.Room == "" { return f, errors.New(...) }
		if len([]rune(f.Room)) > MaxRoomRunes { return f, errors.New(...) }
		f.Name = SanitizeName(f.Name)
		...
	case TypeBid:
		if f.Bid == nil { return f, errors.New("protocol: bid needs a value") }
	...
	default:
		return f, fmt.Errorf("%w: %q", errUnknownType, f.Type)
	}
	return f, nil
}

Three layers of defense, in order: a hard size cap (MaxFrameBytes = 4096) rejects oversized junk before it's even parsed as JSON; json.Unmarshal rejects malformed JSON; and the type switch enforces per-type invariants — a bid frame without a bid value, a join with an empty or too-long room code, and an entirely unrecognized Type string are all rejected here, before any of it reaches the room actor built in module 13. 

func SanitizeName(name string) string {
	cleaned := strings.Map(func(r rune) rune {
		if r < 0x20 || r == 0x7f { return -1 }
		return r
	}, name)
	cleaned = strings.TrimSpace(cleaned)
	runes := []rune(cleaned)
	if len(runes) > MaxNameRunes {
		cleaned = string(runes[:MaxNameRunes])
	}
	if cleaned == "" { return "Guest" }
	return cleaned
}

Notice what SanitizeName does not do: it never rejects a frame over a bad name. Control characters are stripped, length is clamped, and an empty result becomes "Guest" — every input produces some valid output. This is the same graceful-degradation house style you saw for storage and audio in modules 7 and 8: a display name is cosmetic, so the correct response to a bad one is to clean it up, never to lock a player out of a card game over what they typed.

Improvement note
The duplicated DefaultHandsPerGame constant is a named, deliberate trade-off (see Decision above) rather than an oversight — but it's still a real drift risk with nothing enforcing it. If the engine's hand-count default ever changed in backend/internal/engine/ without a matching edit here, protocol.go would keep resolving unspecified joins to the old value with no compiler error, no test failure, and no runtime signal — just tables silently created with the wrong hand count. There is no test in this package (only protocol.go and server.go exist under backend/internal/protocol/, no _test.go file) that cross-checks this constant against the engine's, which is the kind of guard that would turn a silent-drift bug into a loud, immediate one.

protocol/server.go

backend/internal/protocol/server.go
Purpose

Where protocol.go defines what the client sends, this file defines what the server sends back — the joined, lobby, view, event, error and pong frame shapes — and the functions that build and encode them, in one place next to the client-facing contract they implement.

Decision

EncodeView splices JSON manually instead of wrapping the view in a struct with an embedded Type field. 

func EncodeView(v *engine.View) ([]byte, error) {
	body, err := json.Marshal(v)
	if err != nil { return nil, err }
	out := make([]byte, 0, len(body)+16)
	out = append(out, `{"type":"view",`...)
	out = append(out, body[1:]...)
	return out, nil
}

The comment names the reason directly: "The view's own keys are hoisted to the top level, which is the shape RemoteSession._onMessage reads: it passes the whole message straight to GameView.fromJson." The straightforward alternative — define a Go struct embedding *engine.View plus a Type field, and marshal that — would need Go's embedding-plus-JSON-tag machinery to actually flatten the keys the way the Dart side expects, or a second full marshal pass. This instead marshals the view once, then does string surgery: write the literal prefix {"type":"view",, then append everything from the marshaled view except its opening brace (body[1:]), which only works because a JSON object's marshaled form is guaranteed to start with {. It's a real performance win — one marshal instead of two, for what module 2 already told you is a comparatively large payload — at the cost of an invariant that's true today but isn't checked by the type system.

Explanation
func NewJoined(seat int, room string, isHost bool, playerID, guest, resume string, reconnected bool) Joined {
	return Joined{
		Type: TypeJoined, Seat: seat, Room: room, IsHost: isHost,
		PlayerID: playerID, GuestToken: guest, ResumeToken: resume,
		Reconnected: reconnected,
	}
}

Joined carries the two tokens a client needs to keep playing across reconnects — a GuestToken identifying the player, and a ResumeToken identifying this specific seat (module 15 builds where these actually come from). NewError and NewRedirect follow the same pattern: a plain constructor function over a raw struct literal, so every call site gets the same required fields in the same order rather than risking a forgotten Type string. 

func mustEncode(v map[string]any) []byte {
	data, err := json.Marshal(v)
	if err != nil {
		panic("protocol: static frame failed to encode: " + err.Error())
	}
	return data
}

Countdown, AutoplayChanged, ReadyState and SeatChange all funnel through mustEncode, which panics rather than returning an error. That's a deliberate narrowing: every call site passes a literal map[string]any built entirely from plain JSON-safe types (strings, ints, bools) known at compile time — there is no possible runtime input that makes json.Marshal fail on one of these, so a panic here can only mean a programmer wrote a genuine bug (for example, accidentally putting a channel or a function value in the map), which is exactly the class of error a panic is supposed to catch loudly during development rather than have every caller check an error that can never actually occur.

func EncodeEvent(e engine.Event) ([]byte, error) {
	body := e.Wire()
	body["type"] = TypeEvent
	return json.Marshal(body)
}

The frame envelope's "type": "event" key. e.Wire() (the Go engine's equivalent of the Dart GameEvent hierarchy's own JSON shape from module 2) returns the event's own fields as a map, but has no idea it's about to be wrapped in a wire frame — so EncodeEvent injects the outer envelope's type key into that same map before marshaling, the same top-level-hoisting shape EncodeView uses.

Improvement note
EncodeView's byte-splicing (body[1:]) depends on an invariant that's true by construction today — engine.View marshals to a JSON object, so its encoded form always starts with { — but nothing enforces that invariant at compile time, and there is no test file in this package (backend/internal/protocol/ has no _test.go) that locks it in. If a future change gave engine.View a custom MarshalJSON that could, under some condition, marshal to null (a nil pointer, for instance) or an array, this function wouldn't error — it would silently slice the wrong bytes off a string that isn't the JSON object it assumes, producing a frame that fails to decode on the Dart side with no clear signal at the point where the bad frame was actually built. A short unit test asserting json.Marshal(&engine.View{})[0] == '{', or simply switching to struct embedding despite the extra marshal cost, would remove the risk entirely.

Checkpoint

Why does the server fail to start in production with no JWT_SECRET, but generate a random one silently in development?
A random secret regenerated on every restart would boot successfully in production and then invisibly invalidate every previously issued token — a much worse failure to diagnose than a process that simply refuses to start. In development the same behavior is a minor, expected inconvenience while iterating, so it's allowed.
Why is Bid declared as *int instead of int on ClientFrame?
A plain int can't distinguish "the client sent a bid of 0" from "the client sent no bid at all" — both decode to the zero value. A pointer's nil means absent; a pointer to 0 means present and zero, which a bid of zero legitimately can be.
Why does protocol.go redeclare DefaultHandsPerGame = 5 instead of importing the engine's own constant, and what does that decision cost?
Importing it would make the protocol package depend on the engine package, coupling the wire-format definition to the game-rules implementation. The cost, named directly in the code's own comment, is that the two values now have to be kept in sync by hand — nothing catches it if they drift apart.
What does DecodeClient guarantee about any ClientFrame it returns without an error, and why does that matter to the packages downstream?
That the frame's type is one of the known types, its strings are within their length limits, and the required fields for that specific type are present. It matters because every downstream package (room, ws) can then trust a decoded frame completely instead of re-validating it at every call site — validation happens exactly once, at the boundary.
