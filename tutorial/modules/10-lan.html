LAN Multiplayer

The last Flutter-only mode: four phones on the same Wi-Fi, no internet, no Go server at all. One phone becomes the table itself. This module builds net/lan_discovery.dart (finding a nearby table) and net/lan_host_session.dart (being one).

Where this fits

net/lan_discovery.dart

frontend/lib/net/lan_discovery.dart
Purpose

Before two phones can play together over LAN, one has to find the other with no server, no internet, and no manual IP entry expected of an ordinary player. This file is that discovery mechanism — a host advertises itself, guests listen.

Decision

Plain UDP broadcast to a fixed port (47777), not multicast. Per the file's own comment: "Plain broadcast (not multicast), so no extra Android multicast permission is needed." A real, concrete platform constraint decided the mechanism — multicast is arguably the more "correct" tool for this (targeted delivery to interested listeners only), but broadcast avoids an extra permission prompt a player would have to grant for a card game, at the cost of every device on the network receiving every advert whether it's listening or not.

Adverts expire by timeout (4 seconds with no fresh sighting), rather than the host sending an explicit "I'm closing" message. A host that crashes, loses power, or is simply killed by the OS can't be relied on to send a goodbye message — so guests instead just stop trusting a listing once its own periodic re-broadcasts (every second, from LanBroadcaster) stop arriving. The cost is a small window (up to 4 seconds) where a guest might still see a table that's actually already gone.

Explanation
class LanBroadcaster {
  Future<void> start() async {
    final socket = await RawDatagramSocket.bind(InternetAddress.anyIPv4, 0);
    socket.broadcastEnabled = true;
    _socket = socket;
    _timer = Timer.periodic(interval, (_) => _sendOnce());
    _sendOnce();
  }

  void _sendOnce() {
    final payload = utf8.encode(jsonEncode({
      'type': 'callbreak-lan', 'room': roomCode, 'host': hostName,
      'port': wsPort, 'players': _playerCount,
    }));
    socket.send(payload, InternetAddress('255.255.255.255'), lanDiscoveryPort);
  }
}

The host side is almost the entire mechanism: bind a UDP socket, and every second, blast a small JSON packet to the network's broadcast address (255.255.255.255) with the room code, host name, and — crucially — the port its actual WebSocket server (built next) is listening on, since that's assigned dynamically at bind time. 

class LanDiscovery extends ChangeNotifier {
  final Map<String, (LanGameAdvert, DateTime)> _seen = {};

  void _onEvent(RawSocketEvent event) {
    ...
    final key = '${datagram.address.address}:$room';
    _seen[key] = (advert, DateTime.now());
    notifyListeners();
  }

  void _prune() {
    final cutoff = DateTime.now().subtract(_advertTtl);
    _seen.removeWhere((_, entry) => entry.$2.isBefore(cutoff));
    if (_seen.length != before) notifyListeners();
  }
}

The guest side is a live, self-cleaning map: every received advert refreshes its entry's timestamp, and a periodic prune drops anything not refreshed recently enough. The key ('${datagram.address.address}:$room') combines sender address and room code, so the same room code broadcast by two different hosts (a collision, however unlikely) is still tracked as two separate, distinguishable tables rather than overwriting each other.

Improvement note
No weakness — this is a small, self-contained, and appropriately defensive mechanism (a malformed or foreign UDP packet on the same port is simply ignored, lines 122–128).

net/lan_host_session.dart

frontend/lib/net/lan_host_session.dart
Purpose

A LAN game needs an authority — something has to hold the real deck and decide whose turn it is, the same job the Go server does for online play. Without a central server available, this file makes one phone become that authority: it runs an embedded WebSocket server, speaks the exact same wire protocol as the Go backend (Part III), and lets nearby guest devices connect to it precisely as if it were a real server.

Decision

The host runs a real, if minimal, dart:io HttpServer + WebSocketTransformer — the same primitives any server would use — rather than some lighter peer-to-peer scheme with no server role at all. Because it speaks the identical frame shapes the Go server does (joined, lobby, view, event), every guest simply connects with the exact same RemoteSession class built in module 9 — nothing about the client needs to know or care whether the far end is a phone or a data-center server. That reuse is the entire payoff of the wire protocol's own compatibility rules (module 9's Decision on total, defensive decoding). The cost is that this project now has three separate implementations of "run a Call Break table" — LocalSession (module 5), this file, and the Go room actor (module 13) — each hand-written, each needing to agree on pacing and rules.

The file's own class doc comment says this almost exactly: "this mirrors [LocalSession]'s publish/schedule loop, just fanned out over every connected socket instead of one local field," and separately: "Unlike a local game it also runs the table's clocks, because a table with other people at it cannot wait indefinitely on any one of them" — which is precisely the same turn-timeout/autoplay responsibility the Go server owns for online tables. Architecturally, LanHostSession sits exactly between LocalSession (on-device, no clocks, no other players) and the Go backend (networked, with clocks, running on a real server) — same shape as the server, running on a phone instead.

Future<void> startHosting() async {
  _claimHostSeat();
  final server = await HttpServer.bind(InternetAddress.anyIPv4, 0);
  _server = server;
  server.listen((HttpRequest request) async {
    if (WebSocketTransformer.isUpgradeRequest(request)) {
      final socket = await WebSocketTransformer.upgrade(request);
      _handleClient(socket);
    } else {
      request.response.statusCode = HttpStatus.forbidden;
      await request.response.close();
    }
  });

  final broadcaster = LanBroadcaster(
    roomCode: roomCode, hostName: playerName, wsPort: server.port,
  );
  _broadcaster = broadcaster;
  await broadcaster.start();
  notifyListeners();
}

Binding to port 0 asks the OS to pick any free port — that's why LanBroadcaster is constructed only after the bind succeeds, with wsPort: server.port reading back whatever port the OS actually assigned. A plain HTTP request that isn't a WebSocket upgrade is rejected outright (403) — this embedded server has exactly one job and nothing else to serve.

Improvement note
As named in the Decision above: this project maintains three separate hand-written implementations of table-running logic (LocalSession, LanHostSession, and the Go room actor in module 13), each of which must independently agree on pacing, turn-timeout behaviour, and rules enforcement. The engine itself is shared (module 2's CallBreakGame is reused directly here, unlike the Go side which is a full port), which narrows the risk considerably, but the *scheduling* logic — when a trick clears, when a bot acts, when a timeout fires — is written three separate times with no shared abstraction between them. A behavioural difference between LanHostSession's timeout handling and the Go server's would be a real, easy-to-introduce bug with nothing to catch it beyond manual testing.

Checkpoint

Why does LAN discovery use UDP broadcast instead of the more "correct" multicast?
Multicast requires an extra permission on Android that broadcast doesn't — the platform constraint decided the mechanism, at the cost of every device on the network (not just interested listeners) receiving every advert packet.
Why does a LAN table's discovery entry expire by timeout instead of the host sending an explicit "closing" message?
A host that crashes or is killed outright never gets the chance to send a goodbye message, so relying on one would leave guests seeing a phantom table forever in that case. Timing out an advert that's stopped being refreshed is self-healing regardless of how the host went away, at the cost of a brief window where a just-closed table can still appear live.
LanHostSession reuses RemoteSession unmodified on the guest side. What design decision from an earlier module made that possible?
Module 9's wire protocol decoding is total and defensive — it reads whatever frames arrive in the documented shape without caring which process produced them. Because LanHostSession emits the identical frame shapes the Go server does, RemoteSession connects to either one with zero code changes.
What real maintainability risk does having three separate table-running implementations (LocalSession, LanHostSession, the Go room actor) create, and what limits its blast radius?
Each one hand-writes its own pacing and turn-timeout scheduling, so a behavioural difference between them (say, a timeout edge case handled differently) is a real bug with no shared code to catch it. What limits the risk: all three route actual game-rule decisions through the same engine (module 2's CallBreakGame in two of the three; a tested Go port in the third) — it's the scheduling logic around the engine, not the rules themselves, that's triplicated.
