Going Online: RemoteSession, REST & Uploads

This is the module that makes the app actually multiplayer. It builds net/remote_session.dart — the third GameSession implementation, this time talking to a real Go server over a WebSocket — plus the REST support around it: net/api_client.dart, net/api_models.dart, and the offline-game upload queue in net/game_uploader.dart.

Scope note: api_models.dart (560 lines) is mostly repeated instances of one JSON-decoding pattern — it's shown once in full here, not per model class. remote_session.dart (710 lines) gets the deepest coverage in this module, since it's where the interesting networked-client decisions live.

net/remote_session.dart — connecting & reconnecting

frontend/lib/net/remote_session.dart:189–434
Purpose

A real network drops. Wi-Fi flickers, a phone walks out of range, a server restarts. Without deliberate reconnect logic, any of those would end the game for a player who did nothing wrong. This is the piece of the app that decides "is this seat still worth trying to get back," and does the retrying so the player mostly never has to.

Decision

Client-driven exponential backoff (1s, 2s, 4s, then every 8s), bounded by a server-issued grace window — not a fixed retry interval, and not a server-pushed "retry at this time." A fixed short interval would hammer a server that's genuinely down; a long fixed interval would feel sluggish for a one-second Wi-Fi blip. Backing off is a proven middle path, at the cost of extra bookkeeping (_attempts, the switch table) for what a fixed delay would do in one line.

A dedicated _connecting guard flag prevents two overlapping connection attempts from ever running at once — a real race is possible here: a "Try again" tap landing while a scheduled backoff timer is also mid-connect. Without the guard, both attempts could each open a socket and leave the session holding two live connections fighting over its state. The cost is one more boolean to remember to check, and to reset in a finally block (line 272) so it's never left true after an attempt ends, however it ends.

Explanation

Detecting a silent drop the OS didn't report (lines 237–245):

// A network switch (Wi-Fi ↔ cellular, a changed IP) does not always
// close the underlying TCP connection — it can just go silent, with no
// FIN or RST ever arriving. Without this, neither onError nor onDone
// fires and the session sits in SessionStatus.ready forever, showing a
// frozen table. Enabling protocol-level pings makes the socket itself
// notice: if a pong does not come back in time, it closes the
// connection and onDone runs, which is what actually drives the
// reconnect logic below.
socket.pingInterval = const Duration(seconds: 10);

This single line is the difference between a real network failure being detected at all, or the app just... sitting there, showing a table that will never move again, with no error and no signal that anything is wrong. It's a genuinely non-obvious platform behavior (a switched network interface doesn't always tell TCP it's gone) that the comment is careful to spell out rather than leave as an unexplained magic number.

Distinguishing a deliberate leave from a real drop (lines 324–351):

void _onDisconnected() {
  if (_status == SessionStatus.error) return;
  _subscription = null;
  _socket = null;

  if (_left) {
    _status = SessionStatus.closed;
    notifyListeners();
    return;
  }

  if (_resumeToken != null && _view != null && _view!.phase != GamePhase.gameOver) {
    _seatHeldUntil ??= DateTime.now().add(_reconnectGrace);
    _scheduleReconnect();
    return;
  }

  _status = SessionStatus.closed;
  notifyListeners();
}

Every path to a closed socket runs through this one method, and its first job is figuring out why the socket closed: _left (the player tapped leave, leaveLobby() already sent the frame) means "closed on purpose, nothing to recover." Otherwise, if there's a resume token and a live, non-final game view, this was an involuntary drop worth fighting for — start the grace clock and try to reconnect. Anything else (dropped from a lobby, say — module 5's doc comment on NetworkSession notes rejoining a lobby you already left would take a seat off whoever's waiting) is just... closed.

Try it yourself — canResume gates whether a reconnect attempt is even worth scheduling. Write it before looking.

It should be true only when: there's a resume token, the player hasn't deliberately left, the seat-held-until deadline hasn't passed, there's a view in hand, and that view isn't already gameOver.

Show solution 
@override
bool get canResume {
  final until = _seatHeldUntil;
  return _resumeToken != null &&
      !_left &&
      until != null &&
      DateTime.now().isBefore(until) &&
      _view != null &&
      _view!.phase != GamePhase.gameOver;
}

The backoff schedule itself (lines 375–407):

void _scheduleReconnect() {
  _retryTimer?.cancel();
  if (!canResume) {
    _resuming = false;
    _fail("We couldn't get you back in time, so your seat was given to "
        'another player. Start a new table to play again.');
    return;
  }
  _resuming = true;
  _status = SessionStatus.connecting;
  notifyListeners();

  final backoff = Duration(seconds: switch (_attempts) {
    0 => 1, 1 => 2, 2 => 4, _ => 8,
  });
  _attempts++;
  _retryTimer = Timer(backoff, () {
    if (_status == SessionStatus.closed || _left) return;
    _connect();
  });
}

Notice this checks canResume before scheduling anything — if the grace window has already run out, it doesn't even try; it tells the player plainly that the seat is gone, per the file's own comment: "Say so plainly instead of spinning forever." Only when there's genuinely still time left does it queue the next attempt, doubling the wait each time up to the 8s ceiling.

Improvement note
The backoff schedule (lines 394–401) is a fixed sequence with no random jitter added. If a server restart (or a brief network partition) drops many clients at once, every one of them schedules its first retry at exactly 1 second, the second at exactly 2 seconds, and so on — all in lockstep. At real scale that's a synchronized retry storm hitting the server the moment it comes back, rather than a smoothed-out trickle. Adding a small random jitter to each backoff step (e.g. ±20%) is the standard fix and would cost only a few lines here.

net/remote_session.dart — decoding the wire

frontend/lib/net/remote_session.dart:470–642
Purpose

The server (Part III) speaks the JSON frames documented in backend/PROTOCOL.md. Something on this side has to turn those raw bytes into the typed GameView/GameEvent/ LobbyState objects the rest of the app already knows how to render — this is that translation layer.

Decision

A switch on the frame's type string, not a sealed-class decode — because JSON crosses a language boundary (this is decoding what a Go process sent), there's no shared type to pattern match on the way module 2's GameEvent sealed hierarchy allows inside pure Dart. This is exactly the cost flagged back in module 2's Decision section: crossing a wire means falling back to a stringly-typed protocol no matter how strongly typed either side is internally.

Explanation
void _onMessage(dynamic raw) {
  late final Map<String, dynamic> message;
  try {
    message = Map<String, dynamic>.from(jsonDecode(raw as String) as Map);
  } catch (_) {
    return; // Ignore anything that is not a protocol frame.
  }

  switch (message['type']) {
    case 'joined': ...
    case 'lobby': _lobby = LobbyState.fromJson(message); ...
    case 'view':
      _view = GameView.fromJson(message);
      _syncDeadlines(_view!);
      ...
    case 'event': _handleEvent(message);
    case 'error': _handleError(message);
    case 'pong': break;
  }
}

Notice GameView.fromJson(message) — the exact same factory constructor built in module 2, now decoding a frame that came from a different process, written in a different language, and it works unmodified. That's the entire payoff of module 2's redaction-at-construction decision: the server built this GameView's JSON with the same shape the offline engine already produces, so the client-side rendering code never needs to know or care whether the view came from a local CallBreakGame or a real server.

Fatal vs. non-fatal server errors (lines 594–614):

void _handleError(Map<String, dynamic> message) {
  final code = message['code'] as String?;
  final text = message['message'] as String? ?? 'The server rejected the request.';

  if (code == 'redirect') {
    _error = '$text Please reconnect.';
    _status = SessionStatus.error;
    notifyListeners();
    return;
  }

  // Non-fatal errors are corrections, not failures: an out-of-turn tap or an
  // illegal card. The server sends a fresh view straight after, so the table
  // resyncs on its own and there is nothing to show the player.
  if (message['fatal'] != true) return;

  _fail(text);
}

This is a real design choice worth sitting with: not every rejection from the server is worth interrupting the player over. Tap a card a beat after the server already moved the turn on, and you get an error frame — but the very next view frame already reflects reality, so the UI silently resyncs rather than flashing an error dialog for something the player will never even perceive as wrong.

Improvement note
No weakness beyond the sealed-vs-stringly-typed cost already noted as inherent to any wire boundary — this decode layer is otherwise defensive throughout (every field read defaults rather than throws, matching api_models.dart's own stated "deliberately total" decoding philosophy, covered below).

net/api_client.dart — ApiException

frontend/lib/net/api_client.dart:1–89
Purpose

REST calls (auth, profile, match history — module 17 covers the server side) can fail in a lot of different ways: no network, a timeout, a 4xx, a 5xx, a server with no database configured. Every caller needs one consistent way to react to any of them without a different catch clause per failure kind.

Decision

One ApiException type for every kind of REST failure — network-level, timeout, and every HTTP status — instead of a separate exception class per failure kind (a more idiomatic Dart pattern would often be NetworkException, TimeoutException, HttpException as distinct types). The file's own comment states the payoff directly: "every caller has exactly one thing to catch." The cost: callers lose Dart's type-based catch dispatch and instead branch on a stringly-typed code field and boolean getters (isTransient, isUnauthorized...) — a runtime check instead of a compile-time-exhaustive one.

Explanation
bool get isTransient => statusCode == 0 || statusCode == 429 || statusCode >= 500;

String get _fallbackMessage => switch (code) {
  network => 'No connection to the game server.',
  timeout => 'The server took too long to answer.',
  _ when statusCode >= 500 => 'The server hit a snag. Please try again in a moment.',
  _ when statusCode == 429 => 'A little too fast. Give it a moment, then try again.',
  _ when statusCode == 404 => 'This server does not recognise that request — '
      'it may be an older version. Please try again.',
  _ when statusCode >= 400 => 'That request did not go through. Check your '
      'input and try again.',
  _ => 'Something unexpected happened. Please try again.',
};

isTransient is the single most important getter here — it's what lets a caller (like GameUploader.drain(), next) decide "worth retrying" versus "this exact request will never succeed" with one boolean, instead of re-deriving that logic at every call site. Status 0 means the request never reached the server at all (a real network failure) — grouped with 429 (rate limited) and 5xx (server-side trouble) because all three describe the world, not the request: try again later and it might just work.

Improvement note
No weakness — this is a well-reasoned trade-off, explicitly justified in its own doc comment rather than left implicit.

net/api_models.dart — the decoding pattern

frontend/lib/net/api_models.dart:1–41
Purpose

Every REST response needs to become a typed Dart object, the same problem GameView.fromJson solved for the WebSocket in module 2. This file is that layer for the whole REST surface — profiles, match history, stats.

Decision

Every decoder is total — a missing key falls back to a zero value, an unknown key is silently ignored — rather than throwing on an unexpected shape. The file's own comment explains why this matters more here than it might elsewhere: "the document is explicit that adding a field is a safe, unversioned change on the server — so a client that throws on an unexpected shape would turn a routine backend deploy into a crash on every phone that had not updated yet." The cost is that a genuinely malformed response (a bug, not a new field) fails silently into default values instead of surfacing loudly as a decode error.

Explanation
int _int(Object? value, [int fallback = 0]) =>
    value is num ? value.toInt() : fallback;

Map<String, dynamic> _object(Object? value) =>
    value is Map ? Map<String, dynamic>.from(value) : const {};

List<Map<String, dynamic>> _objects(Object? value) => value is List
    ? [for (final entry in value) if (entry is Map) Map<String, dynamic>.from(entry)]
    : const [];

Five tiny helpers (_int, _double, _string, _bool, _time, plus the two collection ones shown above) are the entire toolkit every model's fromJson in this 560-line file is built from — a field that isn't the type expected, or isn't present at all, degrades to a safe fallback rather than throwing. This is the identical philosophy modules 7 and 8 already applied to disk storage and audio, now applied a third time to network responses: a whole file built around "degrade gracefully, never crash," repeated consistently enough across the codebase to call it a house style rather than a one-off.

Its doc comment also makes a second, sharper point worth remembering: "Nothing derived is decoded... because two sources for one number always end up disagreeing" — win rate, average score, and similar are computed client-side from raw counters, never trusted as a value the server might also compute slightly differently.

Improvement note
No weakness — the same trade-off already named above (a genuine bug decodes identically to "a field the client doesn't know about yet") is the accepted cost of the compatibility guarantee this design buys.

net/game_uploader.dart

frontend/lib/net/game_uploader.dart
Purpose

Games played in bots or lan mode never touch the server while they're being played — the device is the only witness. Without this file, those games would simply vanish the moment the app closes: no history, no stats, nothing to show on the profile screen.

Decision

The upload's idempotency key (clientGameId) is minted at game start, inside GameRecorder's constructor — not at upload time, and not at game end. Per the doc comment: "the id is part of the payload before the first upload attempt, so every retry of a failed upload carries the id the server may already have seen and gets the original game back instead of creating a second one." Minting it any later (say, when the upload is actually attempted) would leave a window where a request that reached the server but whose response was lost could be retried as a second, duplicate game. The cost is essentially none here — it's almost free correctness, which is presumably why it was worth doing this way from the start.

The queue is capped at 50 entries, dropping the oldest first. An unbounded queue that never syncs (a player who plays offline for months) is a slow, unbounded memory/storage leak. Capping it trades that away for silently losing the oldest unsynced games once the cap is hit — accepted because "the newest games are the ones a player expects to see in their history," per the comment.

Explanation

Draining the queue — retry only what's worth retrying (lines 222–260):

Future<void> drain() async {
  if (_draining || _queue.isEmpty) return;
  _draining = true;
  try {
    while (_queue.isNotEmpty) {
      final entry = _queue.first;
      final payload = _decode(entry);
      if (payload == null) {
        _queue.removeAt(0);
        await _persist();
        continue;
      }
      try {
        await client.uploadGame(payload);
      } on ApiException catch (error) {
        if (error.isTransient) return;
        // A 4xx says the payload itself is wrong — drop it rather than retry forever.
      } catch (_) {
        return;
      }
      _queue.removeAt(0);
      await _persist();
    }
  } finally {
    _draining = false;
  }
}

This is ApiException.isTransient (from api_client.dart, above) doing exactly the job it was designed for: a transient failure (no network, a 5xx, a rate limit) stops the whole drain loop right there — the entry stays queued, nothing after it in the queue even gets attempted, preserving upload order for next time. A non-transient failure (a genuine 4xx — the payload itself is malformed) falls through instead, and the entry is dropped: retrying an identical bad payload indefinitely would never succeed, so there's no point keeping it.

Show solution 
GameUploader({required this.client, ...}) : ... {
  // A successful call of any kind is the cheapest possible proof that the
  // network is back, and costs nothing to listen for.
  client.onServerReachable = () => unawaited(drain());
}

Rather than polling "is the network back yet?" on a timer, the uploader piggybacks on whatever REST call the rest of the app happens to make successfully for its own reasons (checking the profile, say) — any successful round trip is proof the server is reachable right now, which is the cheapest possible signal to trigger a retry drain on.

Improvement note
enqueue() (lines 203–214) silently drops the oldest queued game the moment the queue exceeds 50 entries (lines 206–208), with no signal to the player that a game fell out of their history. For most players this never matters — 50 unsynced offline games is a lot — but a player who genuinely plays offline for an extended stretch loses history with zero warning, which contradicts the comment's own framing of the queue as "the worst outcome of a failed upload is that the game shows up in their history later" — past 50 entries, that promise quietly stops being true. A small on-screen notice when the cap is hit (rather than a hard silent drop) would close that gap.

Checkpoint

Why does RemoteSession use exponential backoff instead of retrying at a fixed interval?
A short fixed interval risks hammering a server that's genuinely down; a long fixed interval feels sluggish for a brief Wi-Fi blip. Backing off starts fast (catches quick blips promptly) and slows down the longer the outage persists (doesn't spam a server that's truly gone) — at the cost of more bookkeeping than a single fixed delay would need.
Why does _handleError only surface an error to the player when the server marks it fatal: true?
Because most rejections (an out-of-turn tap, a stale illegal-card attempt) are corrected automatically by the very next view frame — the table resyncs on its own, and the player never perceives anything was wrong. Only failures the client genuinely can't recover from on its own (a redirect to the wrong node, a fatal protocol violation) are worth interrupting the player for.
Why is GameRecorder's clientGameId minted when the game starts, rather than when the finished game is first handed to the uploader?
So the id already exists inside the very first upload attempt — which means every retry of that same upload (after a lost response, a timeout, whatever) carries the identical id, and the server's idempotency check on that id returns the original game instead of recording a second copy. Minting it any later would leave a window where a lost response could cause a genuine duplicate.
ApiException unifies every REST failure mode into one exception type with a code field, instead of distinct exception classes per failure. What's the real cost of that choice?
Every caller only needs one catch clause, which is a genuine simplification — but it trades away Dart's compile-time-exhaustive type dispatch for runtime string/boolean checks (code == 'redirect', isTransient). Forget to check a particular code value somewhere and nothing catches the omission at compile time, unlike a missing case in an exhaustive sealed-class switch.
