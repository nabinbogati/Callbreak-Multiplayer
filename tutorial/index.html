Overview

Build Call Break From Scratch

A hands-on course that rebuilds the real CallbreakMultiplayer project — a Flutter card-game client and its Go multiplayer backend — one file at a time, in the order a competent developer actually wrote it. Every code excerpt in this course is copied verbatim from the real project on your disk; nothing here is invented for teaching purposes.

What this project is, in plain English

Call Break is a 4-player trick-taking card game (similar to Spades/Whist family games). This project is a full client-server implementation of it:

  • A Flutter app (Android/iOS/web/desktop from one codebase) that can be played three ways: solo against bots entirely offline, over the internet against strangers or friends ("quickplay" / private rooms), or against nearby devices over local Wi-Fi with no internet at all ("LAN mode").
  • A Go server that is the single source of truth once a game is networked: it holds the real deck, decides which moves are legal, and tells each player only what they're allowed to see.

The interesting design idea that shapes the whole codebase: the rules of the game are written twice, once in Dart and once in Go — deliberately, so the same rules can run fully offline on a phone and be enforced authoritatively by a server, and the two are tested against each other so they can never quietly disagree.

Architecture — the pieces and how they fit

Both PostgreSQL and Redis are optional — the server starts and plays full games with neither configured (see Module 16).

Tech stack, and why each piece was picked

LayerChoiceWhy
Client frameworkFlutter / DartOne codebase compiles to Android, iOS, web, Linux, macOS, Windows — this game targets phones and desktops from the same UI code.
Client stateChangeNotifier + Stream (Flutter/Dart stdlib)No external state-management package (no Provider/Riverpod/Bloc) — the app is small enough that stdlib primitives are enough, and it avoids a dependency the whole team would need to learn.
Client↔server wire formatHand-written JSON over one WebSocketA trick-taking game is a stream of small, frequent, bidirectional events (bid, play, turn clock) — a perfect fit for a persistent socket over request/response HTTP polling.
Server languageGoCheap goroutines make "one goroutine per game table" affordable at thousands of tables; a static binary with no runtime deploys trivially.
Server concurrency modelActor per room (internal/room)Each table's state is touched by exactly one goroutine, so turn ordering is correct by construction — no mutexes on the hot path.
PersistencePostgreSQL, optionalMatch history/accounts are relational and low-volume; the server is fully playable with it absent, which keeps local dev dependency-free.
Cross-node routingRedis, optionalOnly needed once you run more than one server process; advisory, not authoritative — an outage degrades routing, never gameplay.

Prerequisites

  • Comfortable with basic programming (variables, functions, classes, HTTP) in any language — this course assumes you're new to Flutter, Dart, Go, and this project's specific patterns, and defines every term the first time it's used (see the Glossary).
  • Flutter SDK installed (flutter doctor green) — for Part I & II.
  • Go 1.26+ installed, or Docker (the project's scripts/go.sh falls back to the golang:1.26 image automatically) — for Part III.
  • A terminal and a text editor. No IDE required, though VS Code + the Flutter/Go extensions are the smoothest.

Learning outcomes

By the end you will be able to:

  • Rebuild every layer of this project from an empty folder, in the order its real dependencies demand.
  • Explain why each non-trivial decision was made — actor-per-room, dual-language engine, optional persistence, session abstraction — against a concrete alternative that was not chosen.
  • Locate this project's real weak points (cited to exact files) and know, with a concrete starting direction, how you'd fix each one before it needs to be production-grade.

How this course is organised

Twenty modules, in real build order — the order in which each file's actual dependencies (not folder alphabetisation) make it buildable. Every file or function introduced follows the same four-part structure: PURPOSE (why it must exist), DECISION (why this approach over a real alternative), EXPLANATION (a line-by-line walkthrough), and, where this project has a known weak spot in that exact code, an IMPROVEMENT NOTE. Before most non-trivial code is shown, you get a "try it yourself" prompt with the real solution behind a toggle. Each module ends with a few conceptual checkpoint questions.

Part I and II build the Flutter app to a fully playable offline game before any server exists — exactly the order the real project was built in. Part III then builds the Go backend as a port of what you already built in Dart. Part IV is a build-from-memory challenge and a prioritised list of this project's real gaps.
